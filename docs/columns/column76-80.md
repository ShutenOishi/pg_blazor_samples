## 設計の基本：速さを理由に安全条件を省かない

一覧をキャッシュすると速度が向上しても、DB正本のcan_readが無効になった後まで機密データを返す設計は誤りです。30秒のキャッシュTTLは「30秒閲覧を許可する」という意味ではありません。Step77は安全な学習用ヒントだけをキャッシュし、業務データはStep74の監査付きサービスを通します。

楽観排他は上書き事故を防ぎますが、本人認証や権限そのものの代わりにはなりません。PostgreSQL xmin・既存台帳のFOR UPDATE・監査を同一トランザクションで確定する境界が重要です。原本がFDWや別DBなら実証なしの更新は拒否します。

## 監視と証跡の読み方

HTTP livenessが200でも、FDW切断・監査INSERT失敗・権限失効で業務画面は正しく拒否されます。むしろこれが安全です。監視は原因を運用者に伝え、利用者に他部署の内容・機微ログを見せません。

## 確認問題と解答

**Q1. キャッシュが期限内ならDB照会を省ける？** いいえ。認可と監査の要件が優先です。

**Q2. 保存競合を検出したら自動的に最新データへ上書きしてよい？** いいえ。差分を確認して利用者が再実行します。

**Q3. GitHub ActionsのChrome CIが通ればSPNも合格？** いいえ。実ADとIISの証跡が必要です。

**Q4. 監査DB停止時の最も安全な動作は？** 業務データを返さず、更新をロールバックし、制限付き障害ログへ記録することです。
