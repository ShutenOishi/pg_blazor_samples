# 学習コラム04：設定、テスト、サービス分離を整理する

**対象：ステップ16〜20**

## 5ステップのつながり
| 学んだこと | 選んだ仕組み | なぜ？ |
| --- | --- | --- |
| 設定の受け取り | IOptions | 設定ファイルの読み込みを画面から分離 |
| ログ・非同期 | ILogger、CancellationToken | 標準機能を再利用し、処理の中断に備える |
| テスト | IClockとFixedClock | 外部要因を取り除いて結果を固定 |
| Application分離 | IStepSummaryService | 画面に依存しない処理を切り出す |
| 課題管理 | ITodoServiceとScoped実装 | 画面は操作の契約だけを知る |

## 実務で何が変わる？
画面に設定読み込み、ログ出力設定、DB接続処理をすべて詰め込むと、修正箇所とテスト条件が増えます。利用するサービスを整理すると、画面は「何をしたいか」を表現しやすくなります。

## よくある誤解
- **DIを使えばデータが保存される？** いいえ。DIは部品の組み立ての仕組みです。保存の有無は実装次第です。
- **インターフェイスを作るだけで分離が完成する？** いいえ。参照方向と生存期間を意識する必要があります。
- **標準サービスも自分でnewする必要がある？** いいえ。ILoggerやIOptionsなど、登録済みの機能はDIで受け取れます。

## 確認問題と答え
**Q1. 1ユーザーの課題リストをSingletonで保管してよい？**

A. いけません。複数利用者で状態が混在する危険があります。

**Q2. 固定時計のテストとブラウザー操作テストは同じ？**

A. 違います。前者はC#サービスの結果、後者は画面描画とイベントの結び付きまで確認します。

**Q3. 課題の保存先をDBへ変更するとき、Webの画面も作り直す必要がある？**

A. `ITodoService`の契約を維持できれば、主として実装とDI登録を交換して対応できます。DBの実装そのものは後のステップで学びます。
