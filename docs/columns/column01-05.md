# 学習コラム01：画面が変わるしくみを言葉で説明する

**対象：Step01〜05／学習ページ：** `/learn/column/05`

## 結論：画面の変化は「状態の変化」と「描画」
ステップ01で画面を表示し、02でURLを切り替え、03でC#の値を表示しました。04のボタンクリックで値を変更し、05の`@bind`で入力文字をC#の状態へ結びつけました。

- Razorコンポーネント：HTMLとC#の状態を結びつける画面の単位
- 状態：`learnerName`やカウンターのように、画面の表示を左右する変数
- イベント：利用者の操作を受けて処理を実行する入口
- 描画：状態をもとにHTMLの見え方を更新する処理

## プログラムの流れ
1. サーバーでBlazorコンポーネントが初期状態を持つ。
2. 画面へHTMLが表示される。
3. 利用者がボタンを押す、または入力欄へ文字を入れる。
4. Interactive Serverが操作を受け、C#の状態が変更される。
5. 変更に応じて差分が画面に反映される。

この教材は**Blazor Interactive Server**のため、C#処理は主にサーバー側で実行されます。通信が切断されると操作の反映が途切れる場合がある点を、デスクトップGUIと区別してください。

## コード比較
イベントを使うとき：
~~~razor
<button type="button" @onclick="ClearName">入力を消去する</button>
~~~
このボタンは`ClearName`を実行するための入口です。

双方向バインディングを使うとき：
~~~razor
<input @bind="learnerName" @bind:event="oninput" />
~~~
入力中の文字が`learnerName`へ伝わります。`oninput`を指定しているので、入力ごとに変更が反映されます。

## 実務に結び付ける
社内システムで「検索条件を入力したら件数が変わる」画面を考えます。入力の状態、検索を開始するイベント、結果の表示を分離して考えると設計しやすくなります。ただし、学習ステップ01〜05には実DB接続はありません。

### 間違えやすい点
- 入力時の再描画とDB保存は同じではありません。
- `@bind`があるから入力値が自動で安全になるわけではありません。
- ユーザー入力を`MarkupString`などで無条件にHTMLへ変換すると、スクリプト注入の危険があります。通常のRazor表示を使います。

## 確認問題
**問題1：** `@onclick`と`@bind`の違いは何ですか？

**解答：** 前者は操作が発生したときに処理を呼び出します。後者は入力値とC#の状態を同期する仕組みです。

**問題2：** Step05で`@bind:event="oninput"`を外すと何が変わりますか？

**解答：** 既定の`onchange`を使うため、通常は入力欄の確定・フォーカス移動などのタイミングで状態が反映されます。

**問題3：** 入力してすぐ表示が変わるならサーバーへの永続保存は完了していますか？

**解答：** いいえ。状態と描画の変化であり、DBへの保存処理は別途実装します。
