# 特別コラム：1万人規模の認証・既存台帳認可・セッション・監査

## なぜ通常のSID・アプリ利用者登録モデルと分けるのか

今回の社内システムは、Active Directoryを**本人認証と認証済みユーザー名の取得だけ**に使い、アプリは利用者を登録しません。利用者情報は既存の通常テーブルまたは外部テーブルに揃っています。

実装はその契約に合わせ、`DOMAIN\user`を読み取り専用ビューから照合します。SIDに依存する構成や独自の利用者登録・ロール付与画面を必要条件にはしません。アカウントの名前変更と再使用が重大な弱点となるため、原本側の管理・同期・失効も設計に含めます。

## 選択早見表

| 必要なこと | 第一候補 | 避けること |
| --- | --- | --- |
| 自動ログイン | IIS Windows認証 + Kerberos | 自前ADパスワード入力 |
| 業務別の認可 | 既存DBから正規化ビューを作成し操作時に判定 | ADグループだけで権限を決定 |
| 既存外部台帳を参照 | FDW/ビュー、条件pushdown、タイムアウト | 全1万人を毎回取得 |
| 大規模接続 | 短命DbContextとNpgsqlプール、circuit負荷試験 | 利用者ごとにDB接続を固定 |
| 認証だけ維持するログイン | 明示的なWindows認証HTTP endpoint → 短命Cookie | 長寿命circuitのイベントでSignIn |
| 業務監査 | アプリ監査を主証跡・DB相関を補助 | application_nameを本人証明にする |

## 1万人が使えることと1万人が同時につなぐことの違い

1万人の氏名・所属を含むテーブルは、単一の認証済みログイン名で索引検索すれば通常は巨大な問題ではありません。しかし1万人同時にInteractive Serverへ接続すると、circuitごとの状態メモリ・SignalR・再接続・負荷分散を考える必要があります。

## 既存テーブルを更新しない

アプリ側で登録機能や資格情報テーブルを設けません。DB管理者が読み取り専用ビュー（login_name、is_active、can_read、can_edit、unit_code、authorization_versionなど）を設定する方式です。原本列を追加できない場合はビューで既存の権限表などを結合します。権限を持たない人のデータがCountやCSVから漏れないようにします。

## ログイン画面を作る場合

ログイン画面とは**ADパスワードを入力させるページではなく、Windows認証の開始ボタンを押す案内画面**です。必要ならHTTPの認証エンドポイントで認証し、暗号化Cookieを短期間発行します。匿名の開始ページとWindows認証の終端を分ける必要があります。アプリCookieを消してもWindowsサインアウトにはなりません。

## PostgreSQLの監査

共有DB接続では`Application Name`をサービス名の固定値とし、操作した人はサービス側で監査記録します。DBで相関する必要があるときだけトランザクションローカルの設定とcorrelation_idを併用します。UPDATEと同じトランザクションに成功監査、失敗や拒否は別のログ経路を選びます。

## 確認問題と答え

**Q1. DBの1万人に合わせてPostgreSQLのコネクションを1万本確保する？**

A. いいえ。DB接続はプールし、同時操作の実測に基づいて上限を決めます。

**Q2. ユーザー名だけを取り出すためにADへLDAP検索する？**

A. いいえ。Windows認証済みPrincipalのNameを使います。

**Q3. DBから全ユーザーを取得してメモリで1件探す？**

A. いいえ。正規化したキーでDB側検索し、必要列だけ投影します。

**Q4. application_nameの値がユーザー名なら完全な監査証明？**

A. いいえ。共有DBロールやプールでは書換可能な診断情報です。サーバー側監査を主にします。

**Q5. 認証Cookieが有効ならDB上で剥奪された権限も使える？**

A. いいえ。Cookieは本人識別に限定し、重要な操作はその都度DB権限を再確認します。
