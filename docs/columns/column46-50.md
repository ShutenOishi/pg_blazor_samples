# 学習コラム11：関連DTO・キーセット・仮想化・検索UXの選択

## 5ステップの関係

Step46では関連テーブルを一度のSQLでDTOへ射影し、Step47では一意キーの「続きから」を実現しました。Step48はすでに読み込まれたItemsの部分描画、Step49はDBから可視範囲だけ取得するVirtualizeServerData、Step50は連続入力時の待機・キャンセル・失敗後の再試行です。

## 実務で方式を選ぶ

| 要件 | 第一候補 | 避けたい誤解 |
| --- | --- | --- |
| マスタ件数が固定で少ない | Items | DBの全件検索を安易にItemsへ持たせない |
| 一覧にページ番号や総件数が必要 | ServerData | CountとRowsの条件を食い違わせない |
| 連続して次の結果を読む | 一意キーのキーセット | 任意ソート時にIdだけのカーソルを使わない |
| すでにメモリへ取得した大量の固定行 | Items + Virtualize | DBの全件取得コストは残る |
| スクロールをDB取得へ連動 | VirtualizeServerData | 高さ・行高・安定順序・取消を忘れない |
| 関連表の項目を並べる | DTO射影 | N+1や不要なIncludeを避ける |

## DIとEF Core 10の再確認

Web内のサービスがIDbContextFactoryから操作ごとにDbContextを作り、画面へ渡すのはDTOだけです。複数の層別プロジェクトを増やす必要はありません。MudBlazorの既存DI・翻訳をそのまま利用します。

## 重要な注意点

1. N+1はDB問い合わせ回数の問題です。関連列をSelectでDTOにするとSQLのJOINへ翻訳できます。
2. キーセットは連続取得が得意ですが、番号指定のページジャンプは苦手です。
3. Virtualizeはレンダリングの最適化、VirtualizeServerDataはDB取得の最適化にも関係します。
4. CountとRowsは同一条件、ソートは一意順序、取消はEFの実クエリまで渡します。
5. デバウンスはユーザーの無駄な問い合わせを減らしますが、業務認可・DB障害対応とは別です。

## 確認問題と答え

**Q1. 画面で使う分類名を取得するため、各課題行の描画時にDBへアクセスしてよい？**  
**A1.** いいえ。SelectでDTOへ射影し、関連列の取得をDB側でまとめます。

**Q2. スクロール時に100件ずつDBへ要求するならItems + Virtualizeでよい？**  
**A2.** いいえ。DBに範囲要求するVirtualizeServerDataを使います。

**Q3. ユーザーが1秒に5文字入力したら5回必ず検索すべき？**  
**A3.** いいえ。一定時間入力が止まってから検索し、前の要求の取消も検討します。
