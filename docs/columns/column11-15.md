# 学習コラム03：DI（依存性注入）を理解する

**対象：ステップ11〜15**

## まず結論
DIは「クラスが使う部品を、そのクラスの中で直接生成せず、外側で組み立てて渡してもらう」仕組みです。便利な理由は、**実装の交換・単体テスト・責任分担**を容易にすることです。

## 5つのステップはどうつながる？
1. **Step11**：`new`で直接生成する場合と、DIから受け取る場合を比べた。
2. **Step12**：`IClock`というインターフェイスで実装の約束を決め、実際の時計と固定時計を入れ替えた。
3. **Step13**：サービスの生成範囲にはSingleton、Scoped、Transientの3種類があることを観察した。
4. **Step14**：同じcircuitの親子コンポーネントでScopedサービスのカウンターを共有した。
5. **Step15**：画面は`@inject`、通常のC#クラスはコンストラクターで部品を受け取った。

## 実務の例：「現在時刻に応じた挨拶」
```csharp
public interface IClock
{
    DateTimeOffset GetNow();
}
```

```csharp
public sealed class GreetingService(IClock clock)
{
    public string GetMessage() => clock.GetNow().Hour < 12
        ? "おはようございます"
        : "こんにちは";
}
```

実際の時計を使うと、テストを実施した時刻によって結果が異なります。固定時計へ差し替えれば「午前8時なら必ず『おはようございます』」と確認できます。

## よくある誤解

**DIとインターフェイスは同じもの？** 違います。DIは依存部品の受け渡しの仕組み、インターフェイスは機能の約束です。具象クラスの注入もDIです。

**Scopedは毎回のボタン操作で作り直される？** Interactive Serverではそうではありません。通常は同じcircuitの間、同じScopedインスタンスが使われます。

**Singletonを使えば高速で便利？** 共有してよい、変更されない状態などには向きますが、利用者ごとの情報を入れると漏えいにつながります。

## 理解度を確認する問題

**Q1. 画面の中で`new FixedClock()`を直接書いた場合、DIによる入れ替えはできていますか？**

A. 直接生成しただけではDIではありません。依存部品を引数で受け取る設計やコンテナーから解決する設計へ変える必要があります。

**Q2. 別の利用者の値を絶対に共有してはいけないとき、Singletonに保存してよいですか？**

A. いけません。Singletonは全利用者の接続で共有され得ます。

**Q3. `Transient`を`@inject`した画面でボタンを押すたびに、自動的に新インスタンスになりますか？**

A. なりません。DIに解決を要求した時に生成されます。画面のイベントとサービス解決は同義ではありません。
