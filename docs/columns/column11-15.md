# 学習コラム03：DIの登録・交換・寿命・画面への注入を理解する

**対応するステップ：11〜15。** このコラムは、5つの画面で観察した現象を一つの設計として結び付けます。

## このコラムの到達目標
WinFormsではフォームが`new`で業務クラスを作る構成が一般的に見られます。Blazorでは起動時のDI登録と利用側への注入を使い、部品の組み立てを画面から分離できます。5ステップを終えた時点で、**どこで登録し、誰が受け取り、どの範囲で共有され、どうやって交換できるのか**を説明できるようにします。

## 5ステップの関係

| ステップ | 動かしたもの | 実務で判断すること |
| --- | --- | --- |
| 11 | 直接生成した時計とDIから受け取った時計 | サービスの組み立てを誰が担当するか |
| 12 | 実際の時計と固定時計の切り替え | インターフェイスを使う意味と切り替えの方法 |
| 13 | Singleton・Scoped・Transientの識別子 | サービスの寿命と共有する状態の範囲 |
| 14 | 親子で共有するScopedCounter | 同じcircuitの状態共有と再描画通知 |
| 15 | 名前入力とGreetingFormatter | Razorの`@inject`とC#のコンストラクター注入 |

最初に**依存関係そのもの**、次に**依存先の交換**、その後**寿命**と**コンポーネント間の共有**を学び、最後に画面とサービスへの注入を確認した流れです。

## WinFormsでの処理と比較する

直接生成するWinFormsの考え方：

```csharp
// フォームの中で具体的な依存先を決めています。
var greeting = new GreetingService(new SystemClock());
var message = greeting.GetMessage();
```

BlazorでDIを利用する考え方：

```csharp
// Program.cs
builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddTransient<GreetingService>();
builder.Services.AddTransient<GreetingFormatter>();
```

```razor
@inject GreetingFormatter Formatter

<p>@Formatter.Format("練習太郎")</p>
```

`GreetingFormatter`は`GreetingService`を、`GreetingService`は`IClock`をコンストラクターで受け取ります。Webアプリの`Program.cs`で一度登録した内容を、必要な場所でDIから利用します。DIがHTMLを生成するのではありません。表示するのはRazorコンポーネントです。

## 依存関係の図を文章で追う
1. コンポーネントが`GreetingFormatter`を要求する。
2. DIが`GreetingFormatter`のコンストラクターを調べる。
3. 必要な`GreetingService`を生成するため`IClock`を解決する。
4. この構成では`SystemClock`を`IClock`として渡す。
5. 完成した`GreetingFormatter`をRazorへ渡し、Razorが画面表示に使用する。

この登録に対し、固定時計で試験したい場合は、**試験用DI構成で`IClock`を固定実装へ切り替える**設計を検討します。ステップ12のボタン操作はDI登録の交換ではなく、画面上で選択した時計を`GreetingService`へ渡して比較するデモです。

## 寿命とWeb特有の注意

| 種類 | 同じインスタンスになる範囲 | 避ける誤解 |
| --- | --- | --- |
| Singleton | サービス提供元全体で共有 | 利用者別の認証情報や検索条件を保存してよい、ということではない |
| Scoped | Interactive Serverの通常の対話中はcircuitに関連 | 一つのボタン操作を終えると必ず破棄される、ということではない |
| Transient | DIから新しく解決するたび | 再描画するたびに`@inject`済みのオブジェクトが自動交換されるわけではない |

Blazor Interactive Serverではイベント処理のC#はサーバーで動きます。**ブラウザーのページ状態、circuit内の状態、永続化したDB状態は別**です。DIの生存期間だけではDBのトランザクションや本人認可は保証されません。

## 実務での使い分け
画面は入力と表示、サービスは業務処理、時計やDB接続などの依存先は明示的に設計します。DIでサービスを受け取っても、個人情報の共有先や失効条件を誤ると事故になります。後続のEF Core編では`IDbContextFactory`を登録して短命なDbContextを作る構成を使用し、単純にScopedのDbContextを長時間画面へ保持する構成と区別します。

ライブラリのDIは自作サービスと同じ仕組みで利用できます。例えばMudBlazorの登録方法を読み、どのサービスが提供され、どのコンポーネントから使えるかを把握することも、DIを理解する実務上の利点です。

## 統合演習と解答

**問1：** `GreetingFormatter`をRazorへ注入し、その依存先である`GreetingService`と`IClock`のうち`IClock`だけ登録を外しました。画面は動きますか。

**答え：** 動きません。DIは最も内側の依存先`IClock`を解決できず、`GreetingFormatter`まで組み立てられません。まず登録とコンストラクターを確認します。

**問2：** ステップ14で子が`Counter.Increment()`を呼び、`OnChanged`を実行しなかった場合、親の表示は確実に変わりますか。

**答え：** 確実には変わりません。共有しているカウンター値が更新されても、親の再描画には通知が必要です。

**問3：** 別利用者の画面にも見えるSingletonへ、現在の利用者の名前を入れてよいですか。

**答え：** いけません。Singletonは利用者ごとに分離されず、別の利用者と状態を共有し得ます。

**問4：** 固定時計を用意する意味を、DIとテストの観点から説明してください。

**答え：** 時刻による出力の違いを再現可能にし、同じサービスの振る舞いを安定して試せます。依存先の交換を容易にする設計はテストにも役立ちますが、DIを使うだけではテストは実行されません。

**問5：** Razor画面で`@inject`を使うことと、C#サービスのコンストラクター注入は矛盾しますか。

**答え：** 矛盾しません。どちらも必要な依存先を外部から受け取るDIの使い方です。受け取り方が異なるだけです。
