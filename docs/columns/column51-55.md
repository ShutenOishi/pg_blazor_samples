# 学習コラム12：編集DTO・Dialog・一括操作・競合・詳細取得

## 5ステップの関係

Step51は画面入力DTO、Step52はDialogと取消、Step53は選択した複数件の原子的な一括処理、Step54はxminによる更新競合の表示、Step55は関連テーブルを含む詳細DTOです。どれも操作ごとにIDbContextFactoryから短命なDbContextを作ります。

## 要件で選ぶ

| 要件 | 利用する仕組み | 注意点 |
| --- | --- | --- |
| 一覧から1件編集 | 入力DTO、EditForm、ServerDataとは独立した保存 | 入力のサーバー再検証とVersion |
| 閉じられる小画面 | MudDialog + IDialogService | 取消は保存を呼ばず、二重送信を防ぐ |
| 50件以内の一括完了 | ID+xmin、EF Coreトランザクション | 1件でも古ければ全件取消 |
| 競合を安全に表示 | xmin・DbUpdateConcurrencyException | 自動上書きや無条件再試行を禁止 |
| 関連情報つき詳細 | AsNoTracking + DTO射影 | N+1を避け、必要な行だけ取得 |

## 重要な落とし穴

- 編集中のEntityやDbContextをBlazorのcircuitに長期間保持すると、古い追跡状態や並列操作の問題を招きます。DTOだけ保持し、操作単位でFactoryを使います。
- UI入力検証とサービス側の検証は両方必要です。入力用DTOだけに検証があってもDB書込が直接呼ばれる可能性があります。
- 一括処理では全件成功か部分成功かを仕様化します。本教材は全件成功・全件取消を採用し、再送時にはVersionを照合します。
- 詳細を表示するボタンの非表示は認可ではありません。閲覧・更新・一括更新ともサーバー側の業務認可が必要です。ここでは未実装なので開発用データに限定します。
- 削除済みと更新競合を同一扱いにしません。利用者へ最新の状態と再読み込みを案内します。

## 確認問題と答え

**Q1. MudDialogを閉じればDB変更も取り消される？** いいえ。保存前の取消ならDBを書き換えず、すでにコミットした処理は別途取り消す必要があります。

**Q2. IDだけを渡して50件一括更新してよい？** いいえ。読込時のxminと重複・件数・認可を確認します。

**Q3. 保存直前に他者がUPDATEしたときは？** EF CoreのDbUpdateConcurrencyExceptionを検出し、自動で上書きせず再読込を案内します。

**Q4. 100行の詳細で分類名を100回問い合わせる？** いいえ。必要な関連列をDTO射影しN+1を避けます。
