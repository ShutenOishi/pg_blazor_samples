# 学習コラム02：コンポーネントの責任を決める

**対象：学習順012〜10／学習ページ：** `/learn/column/10`

## 5ステップのつながり
学習順012は状態に応じた表示、07は親から子へ値を渡す`[Parameter]`、08は子から親へ操作を返す`EventCallback`、09は初期化から破棄までの生存期間、10は`EditForm`と入力検証です。

### 1. 親と子はどちらが値を持つ？
学習順013の`ParametersPage`は`learnerName`を管理します。子`GreetingCard`はそれを受け取るだけです。学習順014では、子`TopicPicker`が`OnSelected.InvokeAsync`で親`CallbackPage`へ通知し、親が`selectedTopic`を書き換えます。

~~~
親：状態を持つ ── [Parameter] ──> 子：表示・利用者操作
親：状態を更新 <── EventCallback ── 子：選択した結果を通知
~~~

**なぜこの形？** 複数の部品が同じ状態を自由に変更すると、変更箇所を追跡しづらくなるからです。

### 2. 作られた部品は永久に残る？
学習順016の`LifecycleTracker`は初期化、パラメーター更新、破棄を観察できます。ページ再描画と初期化は同義ではありません。Interactive Serverの事前レンダリングでは初期化が別インスタンスで重複する場合があります。タイマー・イベント購読・キャンセル可能な処理は、破棄時のクリーンアップを検討します。

### 3. 入力が正しければ業務処理を許可してよい？
学習順018の`PracticeEntry`は日本語の`[Required]`と`[StringLength]`で書式を検証します。しかし実務の処理には次の4段階が必要です。

1. **入力検証**：必要な項目があるか、長さなどの制約を満たすか
2. **本人認証**：誰が操作しているか（後続ではWindows統合認証）
3. **業務認可**：その人は操作できるか（後続ではPostgreSQLの利用許可）
4. **永続化**：権限確認後に正しくDBへ保存する

学習順018は1のみの教材です。ADやDBの操作に成功したと見なしてはいけません。

## よくある誤解
- `[Parameter]`を子が変更しても問題ない → **誤り**。親側の状態管理・通知の契約を明確にする。
- `OnInitializedAsync`はページURLにつき必ず一回 → **誤り**。プリレンダリングなどで別インスタンスが作られる。
- 画面上の検証メッセージが出ればセキュリティ対策は十分 → **誤り**。サーバーの認可・DB処理を別途守る。
- Serviceを先にすべて作れば初心者も理解しやすい → **誤り**。必要になるタイミングを分けて学ぶ。

## 理解を確かめる3問
**問題1：** 子から親へ「選んだ行番号」を返すには？
**解答：** 子の`EventCallback<int>`などで親へ通知し、親側で選択状態を変更します。

**問題2：** 画面を隠して再表示したとき、初期化回数がリセットされるのはなぜ？
**解答：** `@if`で子を取り除いて破棄し、再表示時に新しい子インスタンスが作られるためです。

**問題3：** 学習順018の「確認」ボタンはPostgreSQLへ書き込みますか？
**解答：** いいえ。`ConfirmEntry`は画面内の確認用フィールドだけを書き換えます。

## 次のステップ：なぜDIを学ぶ？
現段階では画面と小さな部品だけで完結します。今後、時計・ユーザー情報・データ検索等の機能を画面へ直接実装すると、画面のテストと修正が難しくなります。学習順021から**依存性注入（DI）**を学び、「何を行うか」という役割と「どう実装するか」を切り離します。新しいプロジェクトを増やす前に、Web内部の小さなサービスでその必要性を体験します。
