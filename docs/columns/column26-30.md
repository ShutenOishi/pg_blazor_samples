# 学習コラム07：MudBlazorの検索・確認・通知・操作性を実務設計につなぐ

**対象：Step26〜30。** 第3段階の総まとめです。部品の見た目だけでなく、**何が画面上で動き、何がサーバーで処理され、何が永続化されないか**を説明できるようにします。

## 5ステップの関係
| ステップ | 画面で操作したもの | 実務で区別すること |
| --- | --- | --- |
| 26 | MudDataGridの検索・列フィルター・ソート・ページング | `Items`のメモリ操作とDBの`ServerData` |
| 27 | IDialogServiceと確認ダイアログ | 明示的な同意と業務の認可 |
| 28 | Snackbar、処理中表示、本文の状態 | 短い通知と後から確認できる結果 |
| 29 | ダークモード、キーボード、表示の拡大 | テーマとアクセシビリティ全体 |
| 30 | 架空利用者の検索・追加を模した画面 | UI練習と実業務の既存台帳・認証・保存 |

## 第3段階の総合処理を追う
1. MudBlazorのサービスを`Program.cs`で登録し、`MainLayout`にProviderを置く。
2. `/learn/30`のRazorが、6件ではなく**3名の架空利用者**を`_users`へ保持する。
3. 検索欄の入力で`QuickFilter`がC#の`Matches`を評価する。
4. 名前を入力し追加ボタンを押すと、サーバーの`AddAsync`が文字数を検査する。
5. `IDialogService`が確認ダイアログを表示する。
6. 中止なら変更しない。`true`のときだけメモリの一覧へ架空行を加える。
7. `ISnackbar`が通知し、`role="status"`の本文に結果を残す。

この一連の操作に**PostgreSQLやActive Directoryは関与しません**。

## 要件から一覧表示方式を選ぶ

| 要件 | 学習した方式 | 後続で学ぶ方式 |
| --- | --- | --- |
| 上限が決まった少数行 | `MudTable/MudDataGrid Items` | そのまま利用できる条件を検討 |
| DBに数万〜数百万行 | `Items`への全件取得は避ける | `MudTable/MudDataGrid ServerData` |
| 大きな一覧のスクロール | 描画と取得を別に考える | `Virtualize`・`VirtualizeServerData` |
| 編集や一括処理 | 画面で確認・入力 | サービス側認可、短命DbContext、競合制御 |
| 利用者固有のテーマ | Scopedのテーマサービス | 接続・失効・永続化の要否を判断 |

`RowsPerPage=3`は**表示の区切り**であり、DBから3件だけ取得したことにはなりません。これをWinFormsの全件バインドと比較できれば、Webデータ連携へ進みやすくなります。

## 見落としやすいWeb固有の点
- **検索とSQL**：`QuickFilter`は取得済みデータに対するC#の判定です。後続の`ServerData`では適切な`WHERE`・`ORDER BY`・`Count`を使います。
- **確認と認可**：ダイアログで「実行」を選んだことは、権限が確認できたことではありません。
- **通知と監査**：Snackbarを表示しても、業務の永続監査をDBに記録したことにはなりません。
- **テーマと操作性**：ダークモードだけでは十分ではありません。キーボード、拡大、読み上げ、フォーカスとコントラストを確認します。
- **模擬登録と業務台帳**：Step30は架空行をメモリへ追加するUI実習です。後半の認証・認可では、事前に既存DBへ整備済みの利用者台帳を参照し、登録UIは作らない前提を維持します。

## 確認問題と解答

**問1：** DBが100万件のとき、`Items`に全件を読み込んでページャーを付ければ取得量は減りますか。

**答え：** 減りません。DB側で条件・ソート・取得件数を制限する`ServerData`方式が基本候補です。

**問2：** Step26の「簡易検索の一致件数」は列フィルター適用後の結果を必ず表しますか。

**答え：** いいえ。`_rows.Count(Matches)`は簡易検索だけを計算しており、列フィルターの結果と必ずしも一致しません。

**問3：** ダイアログで`bool?`の`null`を受け取ったら、実行済みと扱えますか。

**答え：** 扱えません。実行扱いは`confirmed == true`の場合に限定します。

**問4：** Snackbarで成功と表示した場合、サーバー上のDBへ監査が保存されたと判断できますか。

**答え：** できません。UIの通知と監査の永続性は別の機能です。

**問5：** この段階のEF Coreの学習で、Webに加えてDomain・Infrastructure・Repositoryの新プロジェクトを必ず作るべきですか。

**答え：** 必須ではありません。この教材はWeb内の`Data`と`Services`を使い、`IDbContextFactory`とEF Core 10/Npgsqlを学びます。
