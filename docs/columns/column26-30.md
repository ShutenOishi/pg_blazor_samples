# 第8組の復習：MudBlazorの検索・確認・通知・操作性を実務設計につなぐ

**対象：学習順036〜040（旧Step26〜30）。** 第4段階・第8組の復習です。部品の見た目だけでなく、**何が画面上で動き、何がサーバーで処理され、何が永続化されないか**を説明できるようにします。

## 5ステップの関係
| ステップ | 画面で操作したもの | 実務で区別すること |
| --- | --- | --- |
| 26 | MudDataGridの検索・列フィルター・ソート・ページング | `Items`のメモリ操作とDBの`ServerData` |
| 27 | IDialogServiceと確認ダイアログ | 明示的な同意と業務の認可 |
| 28 | Snackbar、処理中表示、本文の状態 | 短い通知と後から確認できる結果 |
| 29 | ダークモード、キーボード、表示の拡大 | テーマとアクセシビリティ全体 |
| 30 | 架空利用者の検索・追加を模した画面 | UI練習と実業務の既存台帳・認証・保存 |

## 第3段階の総合処理を追う
1. MudBlazorのサービスを`Program.cs`で登録し、`MainLayout`にProviderを置く。
2. `/learn/30`のRazorが、6件ではなく**3名の架空利用者**を`_users`へ保持する。
3. 検索欄の入力で`QuickFilter`がC#の`Matches`を評価する。
4. 名前を入力し追加ボタンを押すと、サーバーの`AddAsync`が文字数を検査する。
5. `IDialogService`が確認ダイアログを表示する。
6. 中止なら変更しない。`true`のときだけメモリの一覧へ架空行を加える。
7. `ISnackbar`が通知し、`role="status"`の本文に結果を残す。

この一連の操作に**PostgreSQLやActive Directoryは関与しません**。

## 要件から一覧表示方式を選ぶ

| 要件 | 学習した方式 | 後続で学ぶ方式 |
| --- | --- | --- |
| 上限が決まった少数行 | `MudTable/MudDataGrid Items` | そのまま利用できる条件を検討 |
| DBに数万〜数百万行 | `Items`への全件取得は避ける | `MudTable/MudDataGrid ServerData` |
| 大きな一覧のスクロール | 描画と取得を別に考える | `Virtualize`・`VirtualizeServerData` |
| 編集や一括処理 | 画面で確認・入力 | サービス側認可、短命DbContext、競合制御 |
| 利用者固有のテーマ | Scopedのテーマサービス | 接続・失効・永続化の要否を判断 |

`RowsPerPage=3`は**表示の区切り**であり、DBから3件だけ取得したことにはなりません。これをWinFormsの全件バインドと比較できれば、Webデータ連携へ進みやすくなります。

## 見落としやすいWeb固有の点
- **検索とSQL**：`QuickFilter`は取得済みデータに対するC#の判定です。後続の`ServerData`では適切な`WHERE`・`ORDER BY`・`Count`を使います。
- **確認と認可**：ダイアログで「実行」を選んだことは、権限が確認できたことではありません。
- **通知と監査**：Snackbarを表示しても、業務の永続監査をDBに記録したことにはなりません。
- **テーマと操作性**：ダークモードだけでは十分ではありません。キーボード、拡大、読み上げ、フォーカスとコントラストを確認します。
- **模擬登録と業務台帳**：Step30は架空行をメモリへ追加するUI実習です。後半の認証・認可では、事前に既存DBへ整備済みの利用者台帳を参照し、登録UIは作らない前提を維持します。


## 学習順036〜040の業務UIをつなぐ判断

WinForms＋Dapperの経験があれば、DataGridViewで取得済みの行を検索していたのか、DapperのSQLで必要な行だけを検索していたのかを思い出してください。MudDataGridの`Items`へ渡す方法は前者に近く、`ServerData`を正しく実装する方法は後者に近い設計です。画面のデータ量が増えたら、検索・ページング・Countの責任をSQL側へ移し、権限付き検索にします。画面で条件をかけただけでは認可になりません。

| 学習順 | 実際に起こること | 起こらないこと |
| --- | --- | --- |
| 036 | 6件のItemsをC#で絞り込む | PostgreSQLのWHERE |
| 037 | ダイアログの選択が状態文になる | データの保存や認可 |
| 038 | 400ms模擬待機・Snackbar通知 | ジョブ投入や監査の永続化 |
| 039 | Scopedサービス経由のテーマ変更 | OSの表示設定・永続保存 |
| 040 | 架空のListへ1名を追加する | 実利用者台帳への登録 |

### 複数画面の実コードを読む

```csharp
private bool Matches(PracticeUser user) =>
    string.IsNullOrWhiteSpace(_keyword)
    || user.Name.Contains(_keyword.Trim(), StringComparison.OrdinalIgnoreCase);
private Func<PracticeUser, bool> Filter => Matches;
```

このコードは学習順040の画面で使う検索条件です。上部の検索結果は`_users.Count(Matches)`で計算します。追加した名前が検索語に一致しなければ画面に出ませんが、リストへは追加されています。画面表示と保持データが同じ意味だと思わないことが大切です。

```csharp
var answer = await Dialogs.ShowMessageBoxAsync(
    "追加内容の確認", $"架空の利用者「{name}」を追加しますか？",
    yesText: "追加する", cancelText: "中止");
if (answer != true)
{
    _state = "追加を中止しました。";
    return;
}
```

`bool?`のtrueだけで先へ進める条件です。利用者が選んだ結果であり、サーバーの権限証明ではありません。Step40で追加したデータは画面内のListだけです。実業務で必要な本人認証、DB台帳による都度認可、入力検証、監査、競合制御は、後続の段階で別に確認します。

## 失敗時の切り分け

| 症状 | 先に調べるもの | 想定される説明 |
| --- | --- | --- |
| MudDataGridの結果が少ない | QuickFilterと列フィルター | 独立した条件が重なっている |
| 中止後に内容が変わらない | answer != true | 中止なら不実行で正しい |
| 通知が消えて結果を失った | role=statusの本文 | 一時通知と結果表示を混同 |
| 別ページでテーマが変わる | ThemePreferenceService | Scopedを通じて共通表示へ伝播 |
| 架空の追加行が見えない | 検索文字列 | 追加した名前が検索に不一致 |
| 実業務の台帳が更新されない | List.Addの保存先 | 実DB保存は未実装 |

## 総合問題と詳しい解答

**問6：** 利用者が検索欄で部署外の情報を見えなくした場合、権限処理は省略できますか。

**詳しい解答：** 省略できません。画面で隠した行が、サーバーから取得してよい行であったかを保証できないためです。事前整備済みDB・外部台帳による業務認可は一覧取得・総件数・詳細・CSV・更新の都度判定します。認可不可や監査保証失敗時は必要な操作を拒否します。

**問7：** WinFormsのMessageBoxでYESが返る場合とBlazorの`bool?`がtrueを返す場合の共通点は何ですか。

**詳しい解答：** どちらも利用者が操作の意図を表した結果です。保存の成功、権限の有無、DBトランザクションの成立を証明する値ではありません。画面の同意とサーバー側の判定を分けます。

**問8：** Snackbarの成功表示をDB監査と読み替えられますか。

**詳しい解答：** 読み替えられません。通知は一時表示であり、この演習の400ms待機は模擬処理です。実DBの監査はサーバー処理と整合させる必要があり、保証できない更新は拒否します。

## 確認問題と解答

**問1：** DBが100万件のとき、`Items`に全件を読み込んでページャーを付ければ取得量は減りますか。

**答え：** 減りません。DB側で条件・ソート・取得件数を制限する`ServerData`方式が基本候補です。

**問2：** Step26の「簡易検索の一致件数」は列フィルター適用後の結果を必ず表しますか。

**答え：** いいえ。`_rows.Count(Matches)`は簡易検索だけを計算しており、列フィルターの結果と必ずしも一致しません。

**問3：** ダイアログで`bool?`の`null`を受け取ったら、実行済みと扱えますか。

**答え：** 扱えません。実行扱いは`confirmed == true`の場合に限定します。

**問4：** Snackbarで成功と表示した場合、サーバー上のDBへ監査が保存されたと判断できますか。

**答え：** できません。UIの通知と監査の永続性は別の機能です。

**問5：** この段階のEF Coreの学習で、Webに加えてDomain・Infrastructure・Repositoryの新プロジェクトを必ず作るべきですか。

**答え：** 必須ではありません。この教材はWeb内の`Data`と`Services`を使い、`IDbContextFactory`とEF Core 10/Npgsqlを学びます。
