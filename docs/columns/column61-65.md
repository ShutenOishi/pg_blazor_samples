# 学習コラム14：Windows本人認証と既存台帳による認可

## 5ステップのつながり

| ステップ | 内容 | 拒否する条件 |
| --- | --- | --- |
| 61 | IIS/Negotiateが本人認証 | 認証未成立 |
| 62 | DOMAIN\\userを認証済みPrincipalから読む | 名前形式不正・未取得・偽装スキーム |
| 63 | 既存テーブル/外部テーブルの統一ビュー | 未登録（0件）・同名重複（2件以上） |

| 65 | can_edit・unit_codeなどの業務別制御 | 許可対象外の操作・部署・データ |

## ADの担当は認証とユーザー名まで

ADへのLDAP照会やSID取得は必須ではありません。サーバーのWindows認証済み主体からDOMAIN\\userを得て既存の利用者台帳へ照合します。DOMAINを落として同名利用者と混同してはいけません。ユーザー名の変更や再使用では既存台帳との同期・権限の無効化が必要です。

## 業務DB側を読み取り専用にする

人事・業務台帳はすでにユーザー情報を持つ前提です。アプリは登録・ロール付与を行いません。任意の既存通常テーブル・外部テーブルの必要列をlearning_user_access_vの形へ投影し、運用時は各システムに合うビュー定義を採用します。DBから全利用者を読み出さず、キーで1件だけ探します。

## Step66〜70へ継続する理由

この段階のサービスは**認可判定を観察する教材**です。既存の一覧、Count、詳細、CSV、編集、APIにまだ認可が強制されていません。Step66〜70で操作単位・部署などの行レベル条件まで適用し、監査・IIS実機認証を受け入れます。

## 確認問題と解答

**Q1. 認証だけ成功した未登録ユーザーに既存業務情報を表示してよい？** いいえ。DB上の利用者行がないときは拒否します。

**Q2. ユーザー名を受け取るためにADへ都度問い合わせる？** いいえ。Windows認証済み主体のユーザー名を使います。

**Q3. 1万人分を毎回メモリへ読み込み、名前を探す？** いいえ。既存正本の索引・検索条件を使い、必要な行だけ取得します。

**Q4. 権限が途中で剥奪された場合、古いcircuitで操作できる？** 操作単位にDB判定して拒否します。サンプル既存サービスへ適用するのは次のステップです。
