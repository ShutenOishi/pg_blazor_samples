# 学習コラム14：Active Directory本人認証とDBの業務認可

## 5ステップのつながり

Step61はWindows統合認証（Negotiate/IIS）、Step62は認証済みSID、Step63はSIDとapp_userの対応、Step64は未登録や無効利用者の拒否、Step65はロールと許可コードの対応を学びます。

| 条件 | 認証の結果 | DB判定 |
| --- | --- | --- |
| 匿名 | 拒否 | 実行しない |
| 認証成功・SIDなし | SID不明で拒否 | 実行しない |
| SIDあり・未登録 | 本人の認証成功 | 利用不可 |
| 登録済み・無効 | 本人の認証成功 | 利用不可 |
| 有効・無効ロールのみ | 本人の認証成功 | 権限なし |
| 有効・有効ロールが必要な許可を持つ | 本人の認証成功 | 指定操作のみ利用可 |
| DB停止・照合失敗 | 本人認証自体とは別 | **拒否** |

## 認証ハンドラーとSID

ASP.NET Coreの標準Negotiate/IISハンドラーでWindows認証を行います。ヘッダーやフォームから送られたユーザー名・SIDは本人証明に使用できません。ADのユーザー名が変わってもSIDで対応付けられますが、アカウントの再作成でSIDが変われば再登録の判断が必要です。

## DI・EF Coreの境界

AuthenticationStateProviderはInteractive Serverの認証状態を取得します。WindowsUserAccessServiceは操作ごとにDbContextFactoryを使い、DBのapp_userと有効なロール・許可を読み取ります。Scopedのキャッシュが認可判断を永続化しないようにします。

## 実務導入前の重要な不足

- Step61〜65は認証とロール照合のサンプルであり、既存の一覧・集計・CSV・編集・内部APIを保護する機能ではありません。
- Step66ではルーティング認可、Step67では業務サービス全経路の認可、Step68〜69では管理・監査、Step70ではIIS/Kerberos実機試験を行います。
- CIはWindows/Linuxのビルド、PostgreSQL 18のDB照合試験、匿名拒否のChrome操作まで。実際のADドメイン参加端末やIISのKerberos使用可否は別の受入試験が必要です。

## 確認問題と答え

**Q1. ADで認証されたらDB側で権限を調べなくてよい？**

A. いいえ。本人確認とアプリ操作許可は別の判断です。

**Q2. SIDを入力欄から選択させると簡単？**

A. 不可です。本人のSIDは認証済みPrincipalから取得します。

**Q3. DB停止時だけは一時的に許可してよい？**

A. 不可です。権限確認できないなら拒否します。
