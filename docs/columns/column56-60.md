# 学習コラム13：期間・キャッシュ・集計・性能・選定

## 5ステップのつながり

Step56は日付Rangeの境界を検索SQLまで一致させます。Step57はキャッシュキーに本人と権限版が必要な理由を架空データで学びます。Step58は集計と少量CSV、Step59は実行計画と遅延分布、Step60は一覧方式の第一候補を選ぶ演習です。

| 要件 | 適切な候補 | よくある誤解 |
| --- | --- | --- |
| 小規模な固定一覧 | Items | どんな件数でも全件読む |
| 大量データの一覧 | ServerData | UI列フィルターを認可にする |
| 次ページのみ | キーセット | 非一意の順番でも欠落しない |
| 巨大データをスクロール | DB取得つき仮想化 | 描画だけ仮想化すればDB負荷も減る |
| 関連列を表示 | DTO射影 | 行ごとに別SQLを発行する |
| CSV | 最大100行、式注入対策 | 101件以上でも全件と表示する |
| 期間検索 | daterangeのOverlaps | 終了日を含む画面と半開区間を混同 |
| 性能 | EXPLAINと十分な実測 | 20回のP99を保証値とみなす |

## 認証とキャッシュの関係

Step57で選ぶ架空利用者A/Bは本人認証ではありません。Scopedサービスは同じcircuitに閉じた演習用の例です。実務ではAD SIDから利用者を確定し、DBの業務権限をCount・Items・詳細・CSV・更新すべてに適用する必要があります。権限変更や更新が発生した場合のキャッシュ失効も必要です。

## 確認問題と答え

**Q1. UIの終了日を検索SQLの終端にそのまま指定する？**

A. いいえ。半開区間なら翌日を上端にします。

**Q2. キャッシュを利用者名で分割すれば認可は完成？**

A. いいえ。サーバーで本人確認と認可を実行する必要があります。

**Q3. 集計結果とCSVで別の認可条件を使用してよい？**

A. いいえ。見えないデータの件数や内容が漏れる原因になります。

**Q4. 20回計測したP99は本番SLOの証拠になる？**

A. なりません。データ規模や負荷を揃えて十分に観察します。
