## 利用者10,001人と同時接続は違う

登録済みアカウント数は台帳検索索引の設計対象です。同時利用者数はサーバー負荷、Blazor Serverのcircuit数はメモリ・SignalRの負荷、Npgsql物理プール数はDBの最大接続数に関わります。1利用者に1DB接続を固定する設計は避けます。

## ADとDBの責任分離

ADは本人認証とドメイン付きログイン名だけを提供します。業務権限・部署は既存DBが正本で、アプリに利用者登録UIは必要ありません。Cookieは本人認証だけを保持し、毎操作でDB権限を再確認します。FDWの原子性や正本の失効反映が保証できない場合は更新を拒否します。

## 監査の落とし穴

物理接続の `application_name` はアプリ識別であり、個人操作の監査証跡ではありません。監査INSERTと業務更新は同じトランザクションで確定させます。監査DB停止中は業務データを返さず、障害ログは別経路でも追跡します。

## 確認問題と解答

**Q1. 編集画面を開いたとき権限があれば保存してよい？** いいえ。保存時の権限失効を確認します。

**Q2. 監査を記録できなくても更新だけ確定してよい？** いいえ。同じトランザクションを取り消します。

**Q3. GitHub ActionsのCIが成功すれば本番のIIS・ADも受入済み？** いいえ。実機Kerberos/SPN/HTTPSとDB/FDWを検証します。

## 第20組で確認する業務シナリオ

この復習では、学習順096〜100を一つの架空の申請業務へ当てはめます。利用者がブラウザーから一覧を表示して編集するまでに、本人認証、既存DB台帳への都度照合、部署限定データ取得、更新時の権限ロック、監査INSERT、画面への応答がどの順序で起こるか説明してください。5テーマの役割は独立しています。認証した事実から部署権限を推測してはいけません。成功した単体試験から現地Windows環境の受入が完了したと判断してもいけません。

| 学習順 | 画面で確かめる動作 | サーバー・DBで成立させる契約 | 未受入の現地条件 |
| --- | --- | --- | --- |
| 096／学習順096 | 台帳照合の結果を表示 | DOMAIN\userを正規化し、Take(2)で重複拒否 | 正本の名前再利用規則、FDW索引と照合規則 |
| 097／学習順097 | 明示ログインの有無を確認 | 専用HTTP POST、CSRF、10分Cookie | 実Kerberos、鍵共有、複数ノード復元 |
| 098／学習順098 | 編集可能性を問い合わせ | 権限行FOR UPDATEとxmin・監査を同一DB確定 | 外部正本の失効とロックの原子性 |
| 099／学習順099 | 監査付き一覧取得を試す | 本人・操作・結果・UTC・相関IDの永続化 | 監査者の権限、改ざん対策、障害時運用 |
| 100／学習順100 | 実機受入の前提を照合 | CI結果を現地受入と混同しない | IIS/AD/FDW/1万人超負荷、復旧 |

### 実コード例1：照合名を少数行で検索

```csharp
var login = WindowsUserAccessService.ReadTrustedLoginName(principal);
if (login is null) return Deny("not_authenticated");
var candidates = await db.ExistingUserAccess.AsNoTracking()
    .Where(x => x.LoginName == login)
    .Take(2).ToListAsync(ct);
if (candidates.Count != 1) return Deny("unknown_or_ambiguous");
```

この例の`Deny`は学習のための表記です。実際の`WindowsUserAccessService.ReadCurrentAsync`の戻り値と例外処理を確認してください。本人名の取得と業務操作ごとの認可を別工程として保ちます。CIの架空ビューを本番台帳へ適用することはしません。

### 実コード例2：保存時に権限と監査を確定する

```csharp
await using var db = await factory.CreateDbContextAsync(ct);
await using var tx = await db.Database.BeginTransactionAsync(
    IsolationLevel.ReadCommitted, ct);
if (!await CheckLockedEditAsync(db, permit.Unit, ct))
    return new(LearningEditStatus.Forbidden, "更新できません。");
// 省略された対象部署とxminの照合が通った場合だけ変更する。
await audit.WriteRequiredAsync(db, "task.update",
    permit.Unit, input.Id, 1, "success", ct);
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

最初に画面で編集権限が見えていても、保存時の`can_edit`、所属部署、正本台帳の行ロックと最新`xmin`が優先されます。FDW側の元データをローカルトランザクションでロックできるとは限りません。保証が確認できなければ更新は禁止します。監査INSERT失敗後は`CommitAsync`へ進めません。

### WinForms＋Dapperから移行するときの比較

| 比較する処理 | WinForms＋Dapper | Blazor＋EF Core |
| --- | --- | --- |
| セッション | クライアント起動状態とWindowsIdentity | 認証チケット・SignalR再接続の状態 |
| 正本照合 | SQL発行前に既存台帳を都度確認 | 画面イベントとは独立したサービス入口で確認 |
| 部署制限 | SQLパラメータを正本値に限定 | IQueryableのVisibleを先に適用 |
| 一括更新 | IDbTransactionで全件検査し確定 | DbContext＋xmin＋監査を同時に確定 |
| 個人監査 | 接続名に依存せずINSERT | 相関ID・UTC・結果コードを永続化 |
| 負荷 | 端末台数と接続プールの観測 | 利用者登録、circuit、DB接続を分離 |

### 操作手順と障害の切り分け

1. `/learn/096`から`/learn/100`まで正規URLで移動し、初期の確認ボタンと状況メッセージを記録します。第8段階の概要ページを先に読み、各画面の責務を一文で説明します。
2. 認証なし・台帳0件・重複2件・無効・閲覧なしを想定し、どの段階で拒否するか表に記入します。実DBにテスト値を入れるのはCI専用スキーマだけにします。
3. 明示ログインの確認GETとPOST、CSRFなしの拒否、10分期限、DB権限失効を順に検討します。Cookieから部署を判断しないことを確認します。
4. 2人の同時更新で`xmin`を変え、台帳権限剥奪と監査INSERT失敗を別々に再現します。どちらも部分保存させないことを確認します。
5. 本番受入票には担当者・SHA・環境・証跡・SLOと実測を記録します。CI未実施項目と実機未実施項目は別欄にします。

| 現象 | 切り分け順 | 期待する安全な応答 |
| --- | --- | --- |
| Cookieは有効だが更新不可 | 操作権限、正本の失効、ロック | 更新せず再確認案内 |
| 監査書込みが失敗 | INSERT権限、DB接続、ロールバック | 一覧非公開、保存取消 |
| 別ノードで再認証 | 鍵保管、共有・暗号化・復元 | 本人再認証を求める |
| 1万人登録で検索が遅い | 正規化索引、FDW pushdown | 上限と計測で設計を修正 |
| 同時circuitが急増 | メモリ、接続プール、再接続 | 合意SLOを満たすか別測定 |

### 演習と詳しい解答

**演習1．** 台帳で同名が2件見つかり、うち1件には管理権限があります。どちらを優先しますか。

**詳しい解答1．** 優先しません。正規化した照合キーが複数件なら許可を一意に決められないため、`Take(2)`で検出し業務操作を拒否します。管理者が正本の重複と名前再利用規則を訂正した後に再検査します。

**演習2．** 有効Cookieで画面を開き、その直後に編集権限を失いました。Cookie期限まで保存できますか。

**詳しい解答2．** できません。Cookieは本人を検証した情報であり業務権限ではありません。保存時に最新の正本台帳と部署条件を再確認し、保証された行ロックとxmin、監査が成立する場合に限り確定します。

**演習3．** 業務更新を先にコミットし、その後監査INSERTが失敗しました。ログだけを再送すれば合格ですか。

**詳しい解答3．** 不合格です。更新と監査は同じ確定単位に置き、監査が失敗したら更新もロールバックします。DB停止時の別系統障害ログは診断手段であり、業務操作の完了を保証しません。

**演習4．** Windows/LinuxのCIとChrome、PostgreSQL18が成功しました。実IIS/Kerberos、FDWと10,001人の負荷受入を完了とできますか。

**詳しい解答4．** できません。CIが確かめた範囲と未実施の現地条件を分けます。SPN/HTTPS、Data Protection鍵共有、実際のAD主体、FDWロックと失効、監査権限、1万人超の登録・同時circuit・接続プールを実機で個別に受け入れます。

## 第21組への準備

学習順101〜105では複数利用者の競合、キャッシュ失効、監視、結合/E2E、配布・復旧へ進みます。第20組の認可と監査の前提を引き継ぎ、故障中は許可へ切り替えないことを各段階で再確認します。
