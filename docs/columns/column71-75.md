## 利用者10,001人と同時接続は違う

登録済みアカウント数は台帳検索索引の設計対象です。同時利用者数はサーバー負荷、Blazor Serverのcircuit数はメモリ・SignalRの負荷、Npgsql物理プール数はDBの最大接続数に関わります。1利用者に1DB接続を固定する設計は避けます。

## ADとDBの責任分離

ADは本人認証とドメイン付きログイン名だけを提供します。業務権限・部署は既存DBが正本で、アプリに利用者登録UIは必要ありません。Cookieは本人認証だけを保持し、毎操作でDB権限を再確認します。FDWの原子性や正本の失効反映が保証できない場合は更新を拒否します。

## 監査の落とし穴

物理接続の `application_name` はアプリ識別であり、個人操作の監査証跡ではありません。監査INSERTと業務更新は同じトランザクションで確定させます。監査DB停止中は業務データを返さず、障害ログは別経路でも追跡します。

## 確認問題と解答

**Q1. 編集画面を開いたとき権限があれば保存してよい？** いいえ。保存時の権限失効を確認します。

**Q2. 監査を記録できなくても更新だけ確定してよい？** いいえ。同じトランザクションを取り消します。

**Q3. GitHub ActionsのCIが成功すれば本番のIIS・ADも受入済み？** いいえ。実機Kerberos/SPN/HTTPSとDB/FDWを検証します。
