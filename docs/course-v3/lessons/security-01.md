# 学習順081：Windows認証・Cookie・HTTP・circuit

## 到達目標
WinFormsでログオン済みの状態は、その端末上のユーザーを前提としていることが多いです。WebではHTTP要求ごとの本人認証、Cookieのチケット管理、Blazor Interactive Serverのcircuit内UI状態の寿命が異なります。ADが証明するのは本人とユーザー名であり、各業務の参照・更新権限は既存DB台帳で照合します。

## 前提条件と学習環境
第6段階のデータ検索・一覧表示と、第5段階のEF Coreの操作単位のDbContextを理解している想定です。Visual Studio 2026・.NET 10・Blazor Interactive Serverで実行します。このページ自体はADやPostgreSQLの実接続を必要としません。

## 画面で確認すること
アプリの `/learn/security-01` を開き、架空の条件を変えてボタンを押してください。**表示される許可・拒否は学習用の模擬判定です。** Windows本人認証や実際の既存台帳認可を代行せず、DBにデータを書き込みません。

## コードを追いかける
```csharp
if (windowsAuthEnabled) { app.UseAuthentication(); }
app.UseAuthorization();
app.UseAntiforgery();
// 個々の業務操作では、信頼できる本人を既存DB台帳と照合する。
```
コードは主要部分の抜粋です。画面とサーバーの処理場所、ミドルウェアや認可サービスの責任を区別してください。

## WinForms＋Dapper経験者向けの比較
デスクトップ画面の入力・イベントと違い、Webではブラウザーからの要求を信用できません。Blazorの対話イベントはサーバーのC#で動きますが、画面に表示される操作ボタンや保存済み状態だけで本人認証・部署別権限は保証できません。

## 間違えやすい点・安全な確認方法
実Windows認証やIISを再現したわけではありません。実際のAD、Kerberos、Cookie検証を行うWindows Server 2025での実機受入は別工程です。

## 演習問題
Windows認証済み、Cookie有効、台帳に未登録なら、DBの一覧を取得できますか？

## 解答
取得できません。認証の成功は業務認可の成立ではなく、本人の台帳行がない場合は拒否します。

## Windows認証・Cookie・HTTP・circuitの固有条件
HTTP要求で確定する本人と、Cookie認証チケット、Interactive Serverのcircuitは寿命も役割も異なる。Program.csではWindowsAuthentication:Enabledのとき認証を登録し、明示ログインにはSecure・HttpOnly・SameSite.Strict、10分、非SlidingのCookieを設定する。

HTTP認証の有無、チケットの有効性、既存台帳の登録、業務の読取権限を架空のチェックで表現している。実際のAD本人認証やDB照合は一切実行しない。

### コード例1：現行実装の抜粋
```csharp
var allowed = SecurityLessonPolicy.PracticeAllowsOperation(
    authenticated, ticketValid, ledgerActive, canRead,
    sameUnit: true, sessionCurrent: true, auditAvailable: true);
```
### コード例2：別の層の確認
```csharp
options.Cookie.HttpOnly = true;
options.Cookie.SecurePolicy = CookieSecurePolicy.Always;
options.Cookie.SameSite = SameSiteMode.Strict;
options.ExpireTimeSpan = TimeSpan.FromMinutes(10);
options.SlidingExpiration = false;
```

## 個別演習
**問：** Cookieが有効でも台帳が無効な利用者の一覧を返すか。

## 詳しい解答
返さない。認証と業務認可は異なり、台帳の本人・部署・操作・行単位を業務サービスで都度確認する。

## 実装照合とサーバー側の責任
HTTP要求で確定する本人と、Cookie認証チケット、Interactive Serverのcircuitは寿命も役割も異なる。Program.csではWindowsAuthentication:Enabledのとき認証を登録し、明示ログインにはSecure・HttpOnly・SameSite.Strict、10分、非SlidingのCookieを設定する。 HTTP認証の有無、チケットの有効性、既存台帳の登録、業務の読取権限を架空のチェックで表現している。実際のAD本人認証やDB照合は一切実行しない。
Webの本人認証と業務認可は異なる責任です。Windows統合認証は信頼できる本人名を取得するために使い、部署・業務・操作・対象行の許可は既存のDB台帳を正本としてサービス側で毎回確かめます。Cookieが有効なこと、画面に保存ボタンがあること、circuitが接続できていることは行単位の許可の根拠になりません。データを読み取るときは一覧と件数にも同じ条件を適用し、集計とCSVから許可されない情報が漏れないようにします。

学習の模擬画面はチェックボックスなどから安全条件を説明するためのものです。実ADを接続したり、本物の業務利用者の権限を発行したり、既存DBの台帳を更新したりしません。模擬上の正常という表示をWindows Server 2025の実機で本人を検証した証拠としてはいけません。AD/IIS/Kerberos、FDWを含む原子性と1万人超負荷の受入は別工程です。

## WinForms＋Dapperとの比較
| 観点 | WinForms＋Dapper | Blazor Interactive Server |
| --- | --- | --- |
| 実行場所 | フォームイベントがクライアントPCで発生 | 対話イベントのC#はサーバーで実行 |
| 本人 | Windowsログオン済みという端末側の前提がある | HTTP認証からサーバーが信頼できる本人を確認 |
| 業務権限 | DapperのWHERE句や呼出し前のチェックを組み込む | サービスが操作・部署・行単位で台帳を都度照合 |
| 画面状態 | ローカルフォーム内で値を保持 | circuitの状態はCookieや最新台帳と別の寿命 |
| 書き込み | DBトランザクションと競合処理を考慮 | 認可・xmin・監査・不明時の拒否を含める |
| 失敗時 | 例外メッセージと処理結果を調査 | HTTP、ブラウザー、サービス、DB監査を区別 |

WinFormsのボタンが無効なときに操作を防ぐ仕組みを、Webの最終認可として使うことはできません。ブラウザーを経由しないHTTP要求や、古い画面状態を保持した対話操作を想定して、実行するサービス側で権限を判断します。画面のチェックボックスは学習用にすぎず、既存台帳の登録情報や認証トークンそのものではありません。

## 障害の切り分け
| 兆候 | 原因を調べる場所 | 安全な扱い |
| --- | --- | --- |
| ボタン操作で拒否が表示 | 学習用の条件が不足 | 実認証の失敗とは区別する |
| HTTPで401または403 | 本人認証・HTTPアクセス権 | 既存DB認可と混同しない |
| Cookieが有効で業務が拒否 | 最新の既存DB台帳 | 一覧、集計、CSV、更新を拒否 |
| POSTの検証が失敗 | Antiforgery・送信元・経路 | 状態変更を進めない |
| 書き込みが競合 | xminと最新行、監査 | 競合を拒否し条件を取り直す |

障害を調べる際は、実HTTP要求が失敗しているのか、Razorに架空の拒否が表示されたのか、業務サービスが台帳を確認して拒否したのかを明確にします。ログに認証チケット、接続文字列、秘密鍵、パスワードなどを出力せず、確認ができない場合は安全に拒否します。監査不可、権限失効、xmin競合、FDW原子性が不明な状況で許可へ倒してはいけません。

## 演習と詳しい解答
**問題1：** Windows認証・Cookie・HTTP・circuitについて、画面の模擬判定が成功したとき、実際に保証できることと保証できないことを整理してください。

**詳しい解答1：** 画面に与えた架空の入力に対し、教材の模擬処理が期待した結果を表示したことのみ確認できます。本当のHTTP本人認証、IIS/Kerberos、DB台帳の操作と行単位認可、監査、鍵復旧と負荷性能までは保証しません。Windows/Linux Release、xUnit、Chrome、PG18実DBのCIを個別に確認しても、現地の実機受入は別と記録します。

**問題2：** 画面上で更新ボタンを非表示にした場合、HTTP側やサービスで権限確認が不要になるでしょうか。

**詳しい解答2：** 不要にはなりません。ボタン表示はUIの操作補助です。ブラウザーを通らず要求が到達する可能性や、既存のcircuitの状態が古い可能性があります。実際の業務サービスが信頼できる本人と既存DB台帳を操作・行単位で都度照合します。更新ならxminと監査も含めて判定し、拒否時にはデータや件数を返しません。

**問題3：** ネットワークが切れて更新が失敗したように見えるとき、再試行の前に何を調べますか。

**詳しい解答3：** ネットワーク切断だけではDBのCOMMIT成否は分かりません。監査記録や行の状態を確認し、重複更新を避けます。現在の本人・部署・業務権限・対象行を既存台帳から再評価し、失効や競合がある場合は再試行せず拒否します。
