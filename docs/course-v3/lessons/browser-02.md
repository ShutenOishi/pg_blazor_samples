# 学習順042：ファイルアップロードと入力制約

## 何を学ぶか
学習順041でサーバーとブラウザーの境界を確認しました。今回はファイル選択と読み取りです。WinFormsのOpenFileDialogで選んだファイルは通常そのPC上のプログラムから読めます。しかしInteractive Serverで利用者がファイルを選ぶと、サーバーはブラウザーから送信された内容をストリームとして読み取ります。ファイル名、拡張子、ContentType、Sizeはいずれも利用者側から提供される情報なので、信頼できる本人確認やファイル内容の証明にはなりません。

この教材の実装は小さな.txtまたは.csvを一時的に読み、バイト数とSHA-256を表示します。内容はメモリで検査するだけで、サーバーのディスクにも業務DBにも保存しません。これはアップロードを本番運用できることの証明ではなく、制限を設ける練習です。実業務では認可、内容・マルウェア検査、保存領域の分離、容量・同時実行制限などを追加します。

## 実行条件とWinFormsとの比較
.NET 10のサンプルWebを起動し、/learn/browser-02へ進みます。画面のInputFileはブラウザーでファイルを選びますが、OnChangeのInspectFileはサーバーのRazorコンポーネントが処理します。上限は64 KiB、拡張子は.txtまたは.csvです。この値は学習用の上限であり、業務ファイルの適切なサイズを一律に定めるものではありません。

| WinForms＋Dapperでの処理 | Blazor Interactive Serverの処理 | 注意する境界 |
| --- | --- | --- |
| OpenFileDialogでパスを取得 | InputFileでIBrowserFileを受け取る | クライアントPCの任意パスはサーバーのパスではない |
| File.ReadAllBytesでローカル読込み | OpenReadStreamの上限付きストリーム | 回線を通して内容を読み取る |
| 拡張子の選択フィルター | accept属性 | 操作補助であり安全検査ではない |
| ローカルのFileInfo.Length | IBrowserFile.Size | 申告値だけでなく実読み取り上限も強制する |
| DBへ登録する前の入力検証 | 入力検証に加えて本人・対象・操作を認可 | UI上の検証合格は業務権限の証明ではない |

## 実際のRazorとサーバー側コード
実装した画面の中心は次の構成です。InputFileはBlazor標準の入力部品です。選択可能な拡張子のヒントをブラウザーに示しますが、サーバーに入る前の確実な拒否とはみなしません。検査結果をrole="status"で伝え、成功時にだけdigestを表示します。

```razor
<label for="browser02-file">練習用ファイル（.txt または .csv、最大64 KiB）</label>
<InputFile id="browser02-file"
           OnChange="InspectFile"
           accept=".txt,.csv,text/plain,text/csv" />
<p data-testid="browser02-result" role="status">@result</p>
@if (digest is not null)
{
    <p>受信した内容のSHA-256：<code>@digest</code></p>
}
```

サーバー側ではまずPath.GetExtension(file.Name)で拡張子を調べ、file.Sizeが64 KiBを超えていないか確認します。その後、OpenReadStreamにも同じ上限を渡します。前段のifだけで済ませず、実際の読み取り自体を制限する点が大切です。現在のサンプルは配列化してSHA-256を計算するため、小さいファイル専用です。

```csharp
private const long Limit = 64 * 1024;
private string result = "ファイルを選択してください。";
private string? digest;

private async Task InspectFile(InputFileChangeEventArgs args)
{
    digest = null;
    var file = args.File;
    var ext = Path.GetExtension(file.Name);
    if (ext is not ".csv" and not ".txt")
    {
        result = "拒否：.txt または .csv のみ選択できます。";
        return;
    }
    if (file.Size > Limit)
    {
        result = "拒否：64 KiBを超えるファイルは受け付けません。";
        return;
    }
    try
    {
        await using var input = file.OpenReadStream(maxAllowedSize: Limit);
        using var output = new MemoryStream();
        await input.CopyToAsync(output);
        var bytes = output.ToArray();
        digest = Convert.ToHexString(SHA256.HashData(bytes));
        result = $"検査完了：{bytes.Length} バイトを読み取りました。保存はしていません。";
    }
    catch (IOException)
    {
        result = "拒否：ファイルの読み取りに失敗しました。";
    }
    catch (InvalidOperationException)
    {
        result = "拒否：許可されたサイズを超えました。";
    }
}
```

このコードは教材の現行実装です。サーバー側でSHA-256を計算する目的は、受信したバイト列が何であったかを確認できるようにすることです。ハッシュ一致はファイルの無害性や送信者の信頼性を示しません。また拡張子の判定は大文字と小文字を区別する現行の学習実装なので、たとえば大文字の.CSVは拒否対象となり得ます。本番での仕様は必要なファイル種別と実際の内容検査に合わせて設計します。

## ブラウザー操作を順に確認する
1. 事前に数行の日本語を記述した小さな.txtを用意し、画面で選択します。表示が「検査完了」に変わり、受信バイト数とSHA-256が出ることを確認します。
2. 同じ内容をもう一度選んだ場合に、受信内容が同一ならハッシュも同一であることを確かめます。改行コードやBOMが違えばハッシュは変わります。
3. 拡張子が.pngの小さなファイルを選択し、「拒否：.txt または .csv のみ選択できます。」を確認します。選択UIの制限を回避できる環境でもサーバーの検査が残ります。
4. 64 KiBを超える.txtを選び、「拒否：64 KiBを超えるファイルは受け付けません。」を確認します。
5. 拒否後にはSHA-256の表示が残っていないことを確かめます。これはInspectFileの冒頭でdigest = nullとしているためです。前の成功値を新しい検査結果と誤認させません。
6. 開発者ツールのNetworkとサーバーログを併せて確認します。ファイル読込みはブラウザーとサーバーの通信を伴うため、通信障害とファイル制限違反を区別します。

このサンプルはInputFileのイベント処理で1つのファイルを扱います。複数ファイルの上限、連続送信、認証後のアップロード権限、保存先、検疫状態の追跡は実装していません。利用者が任意に付けたファイル名を保存先のパスに結合する実装へ変更してはいけません。

## 失敗時の切り分け
| 表示・症状 | 確認箇所 | 正しい解釈・対応 |
| --- | --- | --- |
| .pngが選択できない | ブラウザーのファイル選択UI | acceptの選択補助でありサーバー側の拒否テストとは別 |
| 拡張子の拒否文が出る | Path.GetExtensionと許可リスト | 名前に基づく制限。中身の保証ではない |
| 64 KiB超で拒否される | file.SizeとOpenReadStreamの上限 | 前後両方の容量制限を確認する |
| 読込み失敗の案内が出る | IOException、Network、circuit状態 | 通信やI/O失敗を大容量違反と混同しない |
| 結果が更新されない | OnChange、Interactive Server接続 | イベントの配送から確認する |
| ハッシュが予想と異なる | BOM、改行、文字コード、実バイト列 | 見た目の文字だけでは同じデータと判断しない |
| 成功したので業務ファイルも安全と思う | 内容検査・認可・保存先の実装有無 | この実装には本番の検疫と権限検査がない |

## 本番設計で追加するもの
業務用のアップロードを実装する場合は、本人を認証し、既存DB/外部台帳の権限でその操作を許可した後に、容量と件数を制限して受け取ります。ファイル名は表示用に限定し、サーバーでは独立した名前を割り当て、公開領域から切り離した場所で内容やマルウェアを検査します。CSVや文書形式では、拡張子・MIMEの表示と内容の形式を個別に確認します。成功表示は検査・保存が実際に完了した後に限定し、途中で失敗したものを有効な資料として扱わないようにします。

DapperでアップロードのメタデータをDBへ登録するなら、SQLのパラメーター化、トランザクション境界、失敗時の残存ファイルの扱いを設計します。これらは次のDB・セキュリティ段階で検討する課題で、今の実演がそのまま完成形になるわけではありません。

## 演習と詳しい解答
**問1：** acceptを.txt,.csvにしていれば、サーバーでの拡張子検査は省略できますか。**解答：** 省略できません。acceptは利用者が選ぶ際の補助であり、ブラウザーから送る情報は変更され得ます。現行コードはPath.GetExtensionで拒否し、さらにSizeとOpenReadStreamの上限で容量を制限します。

**問2：** file.Sizeが64 KiB以下であれば、OpenReadStreamのmaxAllowedSizeを省いてよいですか。**解答：** よくありません。前者はメタデータの確認であり、実際に読み取るストリームにも上限を掛ける必要があります。サーバー側の資源消費を制御することが目的です。

**問3：** SHA-256が表示された場合、ウイルスがないことを保証しますか。**解答：** 保証しません。ハッシュはバイト列の識別には使えますが、安全性の判定ではありません。このサンプルにはマルウェア検査も永続保存もありません。

**問4：** WinFormsで使っていたユーザーのC:\Tempを保存先として指定できますか。**解答：** サーバーから利用者PCのそのパスを通常のファイルパスとして読むことはできません。ブラウザーが選んだ内容をストリームで受け取り、サーバー管理下の領域へ保存する方式を別途設計します。
