# 学習順085：接続切断・セッション失効・権限再検証

**実装ソース：** [対応するRazor実装](../../../src/PgBlazorSamples.Web/Components/Lessons/Stage07/L085ReauthorizationPage.razor)。画面の正規URLは `/learn/085` です。

## 到達目標
Interactive Serverのcircuitはネットワーク接続の影響を受けます。再接続できてもHTTP Cookieの期限切れや既存台帳の権限変更を無視して操作を続けてはいけません。表示済みUIや一時キャッシュは最新の認可を保証しません。

## 前提条件と学習環境
第6段階のデータ検索・一覧表示と、第5段階のEF Coreの操作単位のDbContextを理解している想定です。Visual Studio 2026・.NET 10・Blazor Interactive Serverで実行します。このページ自体はADやPostgreSQLの実接続を必要としません。

## 画面で確認すること
アプリの `/learn/085` を開き、架空の条件を変えてボタンを押してください。**表示される許可・拒否は学習用の模擬判定です。** Windows本人認証や実際の既存台帳認可を代行せず、DBにデータを書き込みません。

## WinForms＋Dapper経験者向けの比較
デスクトップ画面の入力・イベントと違い、Webではブラウザーからの要求を信用できません。Blazorの対話イベントはサーバーのC#で動きますが、画面に表示される操作ボタンや保存済み状態だけで本人認証・部署別権限は保証できません。

## 間違えやすい点・安全な確認方法
接続が切れた場合、既に確定したDB書き込みはCancellationTokenで巻き戻せません。トランザクションと監査の原子性を維持し、再試行は重複更新を生まないように設計します。

## 演習問題
circuitが再接続した直後なら、権限が剥奪された人のCSVダウンロードを許可できますか？

## 解答
許可できません。実際のダウンロード・集計・更新などを実行するサービス側で最新の権限を照合し、失効していれば拒否します。

## 接続切断・セッション失効・権限再検証の固有条件
Security05Page.razorは固定したDateTimeOffset、模擬チケットの期限、既存台帳の権限版2または3を扱う。切断チェックは画面内のメッセージだけを切り替え、実際のWebSocketを切断していない。再接続はHTTP Cookieや業務権限の現在性を保証しない。

更新直後のネットワーク切断はDBのCOMMIT成否を示さない。既にコミットした操作をCancellationTokenでは戻せず、再送前に監査・行状態・xmin競合を確認する。権限失効なら必ず拒否する。

### コード例1：現行実装の抜粋
```csharp
var current = SecurityLessonPolicy.PracticeSessionCurrent(
    now, expiresAt, ticketAuthorizationVersion: 2,
    currentLedgerVersion: 3, activeInLedger: true);
```
### コード例2：別の層の確認
```csharp
public static bool PracticeSessionCurrent(
    DateTimeOffset now, DateTimeOffset expiresAt,
    int ticketAuthorizationVersion, int currentLedgerVersion,
    bool activeInLedger) => now < expiresAt
        && ticketAuthorizationVersion == currentLedgerVersion && activeInLedger;
```

## 個別演習
**問：** 回線切断後の再接続が成功したが、台帳権限が変わった。更新を自動再送してよいか。

## 詳しい解答
再送しない。COMMIT成否と監査ID、最新台帳とxminを再確認し、失効していれば安全に拒否する。

## 実装照合とサーバー側の責任
Security05Page.razorは固定したDateTimeOffset、模擬チケットの期限、既存台帳の権限版2または3を扱う。切断チェックは画面内のメッセージだけを切り替え、実際のWebSocketを切断していない。再接続はHTTP Cookieや業務権限の現在性を保証しない。 更新直後のネットワーク切断はDBのCOMMIT成否を示さない。既にコミットした操作をCancellationTokenでは戻せず、再送前に監査・行状態・xmin競合を確認する。権限失効なら必ず拒否する。
Webの本人認証と業務認可は異なる責任です。Windows統合認証は信頼できる本人名を取得するために使い、部署・業務・操作・対象行の許可は既存のDB台帳を正本としてサービス側で毎回確かめます。Cookieが有効なこと、画面に保存ボタンがあること、circuitが接続できていることは行単位の許可の根拠になりません。データを読み取るときは一覧と件数にも同じ条件を適用し、集計とCSVから許可されない情報が漏れないようにします。

学習の模擬画面はチェックボックスなどから安全条件を説明するためのものです。実ADを接続したり、本物の業務利用者の権限を発行したり、既存DBの台帳を更新したりしません。模擬上の正常という表示をWindows Server 2025の実機で本人を検証した証拠としてはいけません。AD/IIS/Kerberos、FDWを含む原子性と1万人超負荷の受入は別工程です。

## WinForms＋Dapperとの比較
| 観点 | WinForms＋Dapper | Blazor Interactive Server |
| --- | --- | --- |
| 実行場所 | フォームイベントがクライアントPCで発生 | 対話イベントのC#はサーバーで実行 |
| 本人 | Windowsログオン済みという端末側の前提がある | HTTP認証からサーバーが信頼できる本人を確認 |
| 業務権限 | DapperのWHERE句や呼出し前のチェックを組み込む | サービスが操作・部署・行単位で台帳を都度照合 |
| 画面状態 | ローカルフォーム内で値を保持 | circuitの状態はCookieや最新台帳と別の寿命 |
| 書き込み | DBトランザクションと競合処理を考慮 | 認可・xmin・監査・不明時の拒否を含める |
| 失敗時 | 例外メッセージと処理結果を調査 | HTTP、ブラウザー、サービス、DB監査を区別 |

WinFormsのボタンが無効なときに操作を防ぐ仕組みを、Webの最終認可として使うことはできません。ブラウザーを経由しないHTTP要求や、古い画面状態を保持した対話操作を想定して、実行するサービス側で権限を判断します。画面のチェックボックスは学習用にすぎず、既存台帳の登録情報や認証トークンそのものではありません。

## 障害の切り分け
| 兆候 | 原因を調べる場所 | 安全な扱い |
| --- | --- | --- |
| ボタン操作で拒否が表示 | 学習用の条件が不足 | 実認証の失敗とは区別する |
| HTTPで401または403 | 本人認証・HTTPアクセス権 | 既存DB認可と混同しない |
| Cookieが有効で業務が拒否 | 最新の既存DB台帳 | 一覧、集計、CSV、更新を拒否 |
| POSTの検証が失敗 | Antiforgery・送信元・経路 | 状態変更を進めない |
| 書き込みが競合 | xminと最新行、監査 | 競合を拒否し条件を取り直す |

障害を調べる際は、実HTTP要求が失敗しているのか、Razorに架空の拒否が表示されたのか、業務サービスが台帳を確認して拒否したのかを明確にします。ログに認証チケット、接続文字列、秘密鍵、パスワードなどを出力せず、確認ができない場合は安全に拒否します。監査不可、権限失効、xmin競合、FDW原子性が不明な状況で許可へ倒してはいけません。

## 演習と詳しい解答
**問題1：** 接続切断・セッション失効・権限再検証について、画面の模擬判定が成功したとき、実際に保証できることと保証できないことを整理してください。

**詳しい解答1：** 画面に与えた架空の入力に対し、教材の模擬処理が期待した結果を表示したことのみ確認できます。本当のHTTP本人認証、IIS/Kerberos、DB台帳の操作と行単位認可、監査、鍵復旧と負荷性能までは保証しません。Windows/Linux Release、xUnit、Chrome、PG18実DBのCIを個別に確認しても、現地の実機受入は別と記録します。

**問題2：** 画面上で更新ボタンを非表示にした場合、HTTP側やサービスで権限確認が不要になるでしょうか。

**詳しい解答2：** 不要にはなりません。ボタン表示はUIの操作補助です。ブラウザーを通らず要求が到達する可能性や、既存のcircuitの状態が古い可能性があります。実際の業務サービスが信頼できる本人と既存DB台帳を操作・行単位で都度照合します。更新ならxminと監査も含めて判定し、拒否時にはデータや件数を返しません。

**問題3：** ネットワークが切れて更新が失敗したように見えるとき、再試行の前に何を調べますか。

**詳しい解答3：** ネットワーク切断だけではDBのCOMMIT成否は分かりません。監査記録や行の状態を確認し、重複更新を避けます。現在の本人・部署・業務権限・対象行を既存台帳から再評価し、失効や競合がある場合は再試行せず拒否します。

## 追加演習：サービス側の都度再認可と失効（個別CI受入待ち）

[架空再認可サービス](../../../src/PgBlazorSamples.Web/Services/Learning/L085ReauthorizationExercise.cs) は学習順081と同じ架空のNegotiate主体で、信頼名検証、期限、台帳版・有効性・権限、監査可否を毎呼出しで検証する。サーバー側のscopedサービスであり、画面のチェック状態を認可の正本にしない。実認証ハンドラー・Cookie・既存DB台帳に接続しない。架空の再接続は回数を記録するだけで、失効した権限を戻さない。

```csharp
var outcome = exercise.Read(fakePrincipal, now, expiresAt,
    ticketAuthorizationVersion: 2, auditAvailable: true);
// 失効後にSimulateReconnect()しても、Readで台帳を再評価して0件を返す。
```

1. 「架空サービスで毎回再認可する」で1件を許可する。
2. 権限失効→架空再接続→再認可で0件拒否を確認する。
3. 初期化後にチケット期限切れと監査不可の拒否を個別に確認し、両方を戻して1件に復帰する。
4. [独立xUnit](../../../tests/PgBlazorSamples.UnitTests/L085ReauthorizationExerciseTests.cs) で無認証・認証方式不一致・期限境界・旧版・失効後再接続を追跡する。
5. 実業務の根拠は別に [SecuredLearningService](../../../src/PgBlazorSamples.Web/Services/Learning/SecuredLearningService.cs) → [PG18統合試験](../../../tests/PgBlazorSamples.UnitTests/SecuredLearningIntegrationTests.cs) をたどる。サービスの都度台帳再取得、監査失敗時の行非公開、権限失効後の一覧/CSV/更新拒否、編集トランザクション中の台帳行ロックを検証する。CI内PG18と実AD/IIS/SITEは区別する。

この追加演習は実WebSocket切断や実Cookie期限満了を引き起こさず、実業務のCookie再検証も代行しない。実AD/IIS/Kerberos/FDW、現地負荷・SITE、FDW原子性が不明な場合の更新は未受入として維持する。
