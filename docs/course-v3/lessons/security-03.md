# 学習順083：XSS・CSRF・SQL注入の防御境界

## 到達目標
XSSはHTMLやスクリプトの実行、CSRFは利用者のCookieを使った別サイトからの要求、SQL注入は入力値がSQLの構文として解釈される問題です。原因と対策は異なるため、それぞれの層で防御する必要があります。

## 前提条件と学習環境
第6段階のデータ検索・一覧表示と、第5段階のEF Coreの操作単位のDbContextを理解している想定です。Visual Studio 2026・.NET 10・Blazor Interactive Serverで実行します。このページ自体はADやPostgreSQLの実接続を必要としません。

## 画面で確認すること
アプリの `/learn/security-03` を開き、架空の条件を変えてボタンを押してください。**表示される許可・拒否は学習用の模擬判定です。** Windows本人認証や実際の既存台帳認可を代行せず、DBにデータを書き込みません。

## コードを追いかける
```csharp
// Razorでは通常のstring表示を使い、信頼できない文字列をMarkupStringにしない。
<p>@inputText</p>
// EF Coreでは利用者入力を値として渡す。
var rows = db.Tasks.FromSqlInterpolated($"SELECT xmin, * FROM learning_task WHERE title = {term}");
```
コードは主要部分の抜粋です。画面とサーバーの処理場所、ミドルウェアや認可サービスの責任を区別してください。

## WinForms＋Dapper経験者向けの比較
デスクトップ画面の入力・イベントと違い、Webではブラウザーからの要求を信用できません。Blazorの対話イベントはサーバーのC#で動きますが、画面に表示される操作ボタンや保存済み状態だけで本人認証・部署別権限は保証できません。

## 間違えやすい点・安全な確認方法
エンコードはXSSのすべてを防ぐ万能策ではありません。属性・URL・JavaScript文字列など文脈に応じた正しい処理が必要です。CSRFにはAntiforgery、SQLにはパラメーター化、業務にはサーバー側認可を適用します。

## 演習問題
Razorの文字列としてscriptタグを表示したら、必ずブラウザーが実行しますか？

## 解答
いいえ。Razorの通常の文字列はHTMLエンコードされます。MarkupString等で信頼できない入力を直接HTMLとして差し込まないでください。
