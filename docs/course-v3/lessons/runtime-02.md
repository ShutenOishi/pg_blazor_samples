# 学習順015：SignalR・circuit・再接続

**実装ソース：** [対応するRazor実装](../../../src/PgBlazorSamples.Web/Components/Lessons/Stage02/L015CircuitReconnectPage.razor)、[一時状態モデル](../../../src/PgBlazorSamples.Web/Services/Learning/L015CircuitCounter.cs)、[隔離Chromeテスト](../../../scripts/browser-circuit-smoke.cjs)、[xUnitテスト](../../../tests/PgBlazorSamples.UnitTests/L015CircuitCounterTests.cs)。画面の正規URLは `/learn/015` です。

## 学習目標とここまでの接続
学習順011では入力欄、012では条件付き一覧、013では親から子の値、014では子から親へのイベント通知を確認しました。どれもInteractive ServerではWebサーバーのC#処理とブラウザー表示が連携して動きます。今回の目的は、この対話を支えるSignalRとcircuitの役割、切断・再接続・再読込で何が保証されるかを説明できるようになることです。

実習URLは`/learn/015`。Visual Studio 2026、.NET 10、Chromeを使います。ネットワークの不安定さを確認できる開発環境で行い、本番のネットワーク機器や認証設定を変えません。この画面はDB・AD・外部サービスに触れず、`L015CircuitCounter`が学習用の整数`Count`とランダムな`InstanceToken`を保持します。個別のcircuit識別子、利用者情報、永続セッションを画面に表示する実装ではありません。学習者は「接続できること」と「以前の状態を復元できること」を区別して説明します。

## WinFormsとInteractive Serverを比較する
| 観点 | WinForms＋Dapper | この教材のInteractive Server |
| --- | --- | --- |
| C#の動く場所 | 利用者PCのアプリプロセス | Webサーバーのプロセス |
| ボタンクリック | ローカルのイベント呼び出し | 接続を経由したサーバーイベント |
| UIの管理 | FormとControl | ブラウザーHTMLとサーバー側コンポーネント |
| 通信 | DB等へ必要時に接続 | 画面操作自体にSignalR接続を使う |
| 一時状態 | フォームのフィールド | circuitとコンポーネントの存続に依存 |
| 永続状態 | 必要ならDapperで保存 | この画面では永続化していない |
| 障害時 | プロセス終了でメモリーが消える | 再接続に失敗すると状態を復元できない場合がある |

SignalRは双方向の対話を提供する仕組みであり、DBトランザクションや認証認可の代わりではありません。circuitはInteractive Serverのコンポーネントインスタンスや状態を扱う論理的な対話の単位です。切断後にサーバー上の同じcircuitへ戻れれば、状態が残る場合があります。しかし保持期間、サーバー再起動、ロードバランサーやネットワーク、セッション失効などの条件で復元できないこともあります。「必ず残る」「必ず消える」のどちらも一般化しません。再読込は新しい画面状態になるため、この教材の回数は0に戻ることを試験します。

## 実コード1：カウンター表示と操作
```razor
@page "/learn/015"
@using PgBlazorSamples.Web.Services.Learning
<p>対話回数：<strong data-testid="runtime02-count">@state.Count</strong></p>
<button type="button" @onclick="Increase">対話回数を1増やす</button>
<p>学習用画面インスタンス識別値：<code data-testid="runtime02-instance">@state.InstanceToken</code></p>
@code {
    private readonly L015CircuitCounter state = new();
    private void Increase() => state.Increment();
}
```

```csharp
public sealed class L015CircuitCounter
{
    public string InstanceToken { get; } = Guid.NewGuid().ToString("N");
    public int Count { get; private set; }
    public void Increment() => Count++;
}
```

`Count`と`InstanceToken`はサーバー側コンポーネントの一時状態です。識別値は本人やcircuitを示す実際の識別子ではなく、同一インスタンスかを比べるためだけの学習用の値です。DB・ブラウザー保存・業務監査を使いません。xUnitはモデルの同一インスタンスの値更新と新しいインスタンスの初期化を検証しますが、SignalRの切断を操作する試験ではありません。

## 実コード2：共通の対話型レンダーモード
```razor
<Routes @rendermode="InteractiveServer" />
```

このアプリの`App.razor`では`Routes`をInteractive Serverに設定しています。したがって学習画面のRazorイベントをサーバーで処理する構成です。学習順009のStatic SSRとの対比を思い出してください。最初のHTMLが見えてもサーバーとの対話回線が未成立なら、`@onclick`の処理が動くとは限りません。SSRの初期HTMLと、対話が始まった後のイベント処理は別の段階です。開発者ツールのNetworkで接続と再接続の挙動を確認できますが、ブラウザーやプロキシによって表示ラベルは変わります。

## 操作手順と観察対象
1. `/learn/015`を開き、初期回数0を確認します。
2. 「対話回数を1増やす」を2回押し、数字が2になることを確認します。
3. Chromeの開発者ツールでNetworkとConsoleを開き、最初のDocument取得と、その後の対話の通信を区別します。
4. 開発環境で一時的なオフライン切替を試す場合は、保存されていない画面の値が失われる可能性を理解してから行います。本番環境や他人の端末では試さないでください。
5. 共通の日本語再接続案内が表示される条件と、表示されなかった場合を区別して記録します。切断時間やブラウザー状態により観察できる現象は変わります。
6. 接続を戻した後、同じcircuitが保持されていれば値が残る場合がありますが、毎回の保証はありません。
7. ブラウザーを再読込し、初期値0へ戻ることを確認します。URLを開き直す操作は、前のC#フィールドの復元を保証しません。
8. 画面の操作ログとサーバーログを照合し、何が実際に観察でき、何が推測にすぎないかを分けて書きます。

## 開発用Chromeの隔離WebSocket試験

`scripts/browser-circuit-smoke.cjs`は通常の画面疎通とは別のChrome BrowserContextを作り、学習用アプリを`127.0.0.1:5186`で起動します。PlaywrightのWebSocket経路制御で`/_blazor`の対話通信だけを短時間切断し、画面が切断を検知して日本語の案内を出すことを確認します。実ネットワーク装置、DB、AD、IISを操作しません。

1. C#イベントを2回実行し、回数2と32桁の学習用識別値を確認します。WebSocketを捕捉できなければ試験失敗とします。
2. 対話WebSocketを閉じ、再接続案内が実際に表示される状態になったこと、切断中に回数が更新されないことを確認します。
3. 切断操作を解除し、同じDocumentで回数2と識別値を保持したまま再接続したことを確認します。追加クリックで3になるかも確認します。
4. Documentを再読込し、別の識別値と回数0を確認します。再接続による状態保持と、新しい画面インスタンスの初期化を区別します。

**この試験で実証できない項目：** 長時間切断後のcircuit保持期限切れ、サーバー再起動、ロードバランサー切替、認証Cookieの失効、既存DB台帳の操作権限失効、実回線の不安定さ。すべてNOT_TESTEDであり、再接続が成功しても業務認可が成立した根拠にはなりません。Chromeの切断検知や再接続を観察できなかった場合は試験をPASSにしません。

## 障害の切り分け
| 症状 | 初めに調べる対象 | 考え方・対応 |
| --- | --- | --- |
| HTMLは出るがボタンが動かない | Networkの対話接続、Console、サーバーログ | 最初の表示だけではSignalR成立を確認できない |
| 「再接続中」の表示が続く | 接続先、DNS、TLS、プロキシ、サーバーログ | 通信経路・サーバー処理を切り分ける |
| 接続が戻っても回数が消えた | circuitの保持期間、サーバー再起動 | 状態の復元は保証されない |
| 再読込で0に戻る | `L015CircuitCounter.Count`の初期値 | 今回の実装では正常 |
| クリックが重複したように見える | 複数クリックとイベント処理の順番 | 業務処理では二重実行を考慮する |
| 再接続案内が出ない | 切断のタイミング・検知方法 | 表示を観察できないだけで正常通信と断定しない |
| DBに記録がない | DB保存処理と監査の実装有無 | このサンプルにはそもそも永続化がない |

## なぜ業務アプリで重要なのか
WinFormsではフォームが表示されている間にC#のフィールドを保持できますが、Webの利用者は別タブを開いたり、画面を再読込したり、回線が切れたりします。職場のネットワークでADの本人認証を行っていても、業務の権限は既存DB台帳から操作ごとに再検証しなければなりません。circuitが継続していることを権限が有効な証拠にしてはいけません。サーバーのメモリーに保存した重要情報は、再起動やスケールアウト時に失われます。永続的な業務データと監査はDB等に保存し、認可・排他・監査の原子性を別途保証します。`application_name`も利用者ごとの永続監査の代わりにはなりません。

## 演習と詳しい解答
**演習1：** `count`が3のとき、ネットワークを数秒間切断して戻したら必ず3が残りますか。

**解答1：** 必ずではありません。同じサーバー上にcircuitが保持され、再接続が成功すれば戻る場合があります。しかし経過時間や構成により失われます。保持の有無を画面の観察とログで確かめ、想像だけで保証しないでください。

**演習2：** `@onclick`が働かず、ページ見出しだけ表示されています。データベースが停止したと判断できますか。

**解答2：** できません。この画面にはDB操作がありません。対話接続が未確立・切断していること、サーバー例外などを先に確認します。初期HTMLが表示されたことと、対話イベント成功は別です。

**演習3：** ブラウザーを再読込すると回数が0に戻ります。復元したければどこへ置くべきでしょうか。

**解答3：** 必要な寿命と機密性に応じてURL・ブラウザー保存・サーバー側永続ストア・DBなどを選びます。業務データは本人認証と既存DB台帳の権限を確認したサーバー側の処理で保存し、クライアント保存を機密情報の正本にしません。次の学習順016〜020で具体的な保存先と初期化を学びます。

**演習4：** 再接続できたら権限判定を省略してもよいですか。

**解答4：** いいえ。対話通信の継続は部署・役割の権限が現在も有効なことを意味しません。閲覧・一覧・件数・CSV・更新など各サーバー処理で既存DB台帳を再検証します。原子的な監査が成立しない更新は拒否します。

**演習5：** 回数を押した直後にタブを閉じ、監査に記録されたと利用者へ伝えてよいですか。

**解答5：** いけません。この画面は永続監査を実装しておらず、クリック結果の表示も保存成功ではありません。業務機能では書込みと監査の成否をサーバー側で確定してから利用者へ通知する設計が必要です。
