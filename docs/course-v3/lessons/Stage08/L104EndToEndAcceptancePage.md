# 学習順104：実DB・ブラウザー・認可の結合/E2E試験

**実装ソース：** [対応するRazor実装](../../../../src/PgBlazorSamples.Web/Components/Lessons/Stage08/L104EndToEndAcceptancePage.razor)。画面の正規URLは `/learn/104` です。

**第8段階・第21組／学習順104・正規URL /learn/104**

## 到達目標

ユニットテストが通っただけでAD/Kerberosを保証したと誤解しないように、検証層と証拠の粒度を分けて受入可能なテスト体系を構成します。

## 自動化するテストの区分

| 種類 | 実行場所 | 確認すること |
| --- | --- | --- |
| xUnit単体 | Windows/Linux | Scopedのキャッシュが本人・部署・権限版・TTLをまたがず、破棄できる |
| PostgreSQL 18結合 | CIの一時DB | EF Core、架空既存台帳の重複拒否・部署制限・xmin競合・監査失敗ロールバック |
| Playwright/Chrome | Ubuntu CI | 学習順101〜80の画面がレンダリングされ、匿名の業務ボタンが拒否される |
| 実機IIS/AD | Windows Server 2025 | SPN/Kerberos、HTTPS、短命Cookie、FDW、SignalR、複数ノード、負荷 |

学習順104画面のボタンはSecuredLearningService.LoadPageAsyncを通り、認可済みの部署内一覧を取得した場合でも返す前に永続監査を要求します。匿名や権限失効時にはデータを表示しません。

## テストデータ管理

本番の利用者登録UIは作らず、CI専用のlearning_existing_user_ciへ架空行だけを投入します。実DB結合テストの後は挿入した課題・監査用データを片付け、本番の既存台帳には書き込みません。ユーザー名をブラウザーのフォームから偽装しないでください。

## 必須の失敗シナリオ

1. 匿名、偽装Cookie、台帳未登録・無効・重複・can_read=false。
2. 二人が同じxminで保存、他部署の課題IDを指定した取得・更新、一括処理への混入。
3. トランザクション中にcan_editを剥奪、行ロック不能なFDWを読み書きしようとする。
4. 監査INSERTをエラーにして一覧・CSVは非公開、更新はロールバック。
5. Blazor Serverの再接続・Cookieの期限切れ・IIS再起動・キー共有は現地実機で確認。

## 確認問題と解答

**Q1. CIのNegotiateという名前のClaimsIdentityで実ADを検証した？** いいえ。CIでは業務認可の境界条件を模擬したにすぎません。

**Q2. 単体・実DB結合・ブラウザーの1種類だけで十分？** いいえ。互いに見つけられない欠陥があります。

**Q3. 業務一覧の内容をE2Eのスクリーンショットへ保存してよい？** 本番の機密データは保存せず、CI専用の架空データを使用します。

## 実装・運用の詳しい検証

この教材はWinForms＋Dapper経験者が、Blazor Interactive Serverのサーバー側処理と既存業務DBの境界を理解するためのものです。ADは本人を認証し信頼済みのドメイン付きログイン名を取得します。業務の閲覧・編集、部署・行単位の認可は既存DB台帳を操作ごとに照合します。Cookieやcircuitの保持値、画面に表示されたボタンだけでは業務権限を証明できません。

### 実コード例1：画面の入口

```csharp
var result = await Business.LoadPageAsync(new LearningPageQuery(0, 1));
_message = result.Message;
// 部署内のCount/Itemsと永続監査を業務サービスが担当。
```


この抜粋は、実際の呼出し経路を追うためのものです。画面で実行するC#は業務サービスを呼ぶ入口にすぎません。認可を通ったように見えても、対象行の部署、現在の権限、監査書込みを確認できなければ結果を公開しません。特に非同期操作をキャンセルした場合やDBから例外が返った場合、古い許可に戻して成功にする処理を追加しないでください。

### 実コード例2：安全な境界の確認

```javascript
await page.goto(base + "/learn/104");
await page.getByRole("button", { name: "監査付き一覧のE2E経路を確認" }).click();
await waitText(page, '[data-testid="step79-state"]', "拒否");
```

### 実装と判断の詳しい説明

xUnitは単体ロジック、PostgreSQL18実DBは台帳重複・部署制限・xmin・監査INSERT失敗のロールバック、Chromeは日本語画面と匿名拒否・互換URLを確認します。実IIS/AD/Kerberos/SPNやFDWと1万人超の負荷は現地の別試験です。CI用のNegotiateという名前のClaimsIdentityは本当のAD本人認証を保証しません。LoadPageAsyncは部署に絞ったCount/Itemsを監査後に返します。架空のCIデータだけを使用し本番台帳にINSERTしません。拒否が期待どおりなら安全試験としてPASSです。

### WinForms＋Dapperとの比較

| 観点 | WinForms＋Dapper | Blazor Interactive Server |
| --- | --- | --- |
| 操作イベント | 各端末のFormで受け付ける | サーバーのRazorとサービスで処理する |
| 権限の正本 | Dapperで既存DBへ毎回照会する | SecuredLearningServiceで操作・行単位を都度判定する |
| 表示状態 | フォーム内の値は古くなり得る | circuitの状態も権限の代わりにならない |
| 監査 | SQLの実行結果と本人・操作を記録 | 永続監査に失敗する場合は業務を安全に拒否 |
| 本番受入 | Windows端末とDB接続を確認 | IIS、Kerberos、SignalR、DBプールと鍵の管理を別途確認 |

### 操作手順

1. 新学習順の目次から正規URLで画面を表示し、前後リンクを確認します。
2. 匿名の開発用ブラウザーで業務の確認ボタンを押し、本人とDB台帳の権限が確かめられないときに拒否されることを確認します。
3. 肯定試験はCI専用の架空PrincipalとPostgreSQL18の架空テーブルだけで行います。本番台帳のレコードや資格情報を教材に投入しないでください。
4. 操作前後の期待結果、実際の画面表示、相関ID、実行日時、コミットSHAを記録します。再操作時もDB正本を確認します。
5. 実AD/IIS/Kerberos/FDWおよび1万人超負荷は、CIとは別に現地で受入票を作ります。

### 障害の切り分け

| 現象 | 最初に確かめる内容 | 合格条件 |
| --- | --- | --- |
| 匿名・台帳未登録・重複 | 認証ハンドラー、ドメイン付き名、照合の0/1/2件 | データを返さず拒否 |
| 権限変更・部署違い | 正本の有効状態、can_read/can_edit、部署 | 過去の許可を再利用しない |
| 競合・行ロック不可 | xmin、トランザクション、FDW条件 | 古いデータを自動上書きしない |
| 監査INSERT・DB障害 | 監査権限、接続、相関ID、ロールバック | 機密の行やCSVを公開しない |
| CI成功・実機未検証 | IIS、SPN、Kerberos、FDW、復旧と負荷 | 現地受入は未完了のままにする |

利用者へSQLエラー、認証Cookie、接続文字列、他部署のデータを表示しません。運用ログは利用者画面と切り分けて保護します。権限失効は再ログインだけで直す問題と決めつけず、現在の正本を確かめます。成功、拒否、競合、通信障害を別の結果として記録してください。

### 演習

匿名拒否、他部署行混入、監査障害、実SPNの不具合をどの層で試験するか。

### 詳しい解答

匿名はChrome、部署と監査原子性は実DB結合、SPN/Kerberosは現地IIS/ADで確認します。CI合格は実機受入の代わりではありません。

### 現場での確認票

WinForms＋Dapperから移行しても認可の根拠は変わりません。本人を確かめたことと、その本人がどの行へどの操作をできるかを分け、監査が不能な場合は安全に拒否します。設定フラグだけで行ロックや監査の原子性が保証されるわけではありません。実AD、IIS、Kerberos、FDW、鍵の管理、1万人超登録アカウントと同時circuit、DBプールの負荷、復旧手順は現地実機で受入します。CI成功の意味を超えて運用を承認しないでください。
