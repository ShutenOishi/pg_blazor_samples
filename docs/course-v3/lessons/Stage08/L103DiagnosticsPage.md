# 学習順103：ヘルスチェック・構造化ログ・運用監視

**実装ソース：** [対応するRazor実装](../../../../src/PgBlazorSamples.Web/Components/Lessons/Stage08/L103DiagnosticsPage.razor)。画面の正規URLは `/learn/103` です。

**第8段階・第21組／学習順103・正規URL /learn/103**

## 到達目標

Windows Server 2025のIIS上で.NET 10のWebアプリの**プロセス稼働**と、PostgreSQL 18・既存台帳・永続監査の**業務可用性**を区別し、機微情報を出さない監視の入口を学びます。

## 実装と確認方法

Program.csのAddHealthChecksとMapHealthChecksにより、HTTP GET /health/live を公開します。200はアプリのlivenessを示すだけで、DB接続・Windows認証・権限・FDW・監査成功を**保証しません**。CIはこのURLをHTTPで検査します。

~~~
builder.Services.AddHealthChecks();
// ルーティングの登録はUseAuthorizationの後でも可能
app.MapHealthChecks("/health/live").AllowAnonymous();
~~~

一方、学習順103の画面の「業務利用の現在の認可を確認」ボタンでは、既存の業務サービスを通して毎回Windows認証済み本人・既存台帳・監査の設定が成立するかを検証します。匿名であれば結果を拒否します。

本番でreadinessを追加する場合は、監視アカウント・接続タイムアウト・負荷制御・非公開のアクセス経路を別設計します。DBを絶えず高頻度で叩くlivenessにしたり、業務データを診断応答へ出力したりしません。

## 見るべき観測量

- HTTP要求の応答時間・失敗率と、SignalR接続・切断・再接続。
- Npgsqlプールの物理接続数・待機時間、PostgreSQLのロック待機とFDW遅延。
- 既存台帳照合失敗、権限拒否、監査INSERT失敗の件数。
- 重要な業務操作の相関ID・操作コード・結果コード・UTC。パスワード・Cookie・CSV本文・DB接続パスワードは**ログに書かない**。

## 否定試験

監査DB停止中でもプロセスが生きていれば/health/liveは成功する場合があります。だからこそ、監視の成功だけでビジネスの操作成功を主張せず、認可・監査障害は業務をフェイルクローズさせます。livenessはプロキシ/IIS側で監視ネットワークに限定してください。

## 確認問題と解答

**Q1. /health/liveの200でログインも正しい？** いいえ。稼働確認と本人認証は無関係です。

**Q2. application_nameを利用者名にすると監査不要？** いいえ。プール接続の識別であり永続的な操作証跡ではありません。

**Q3. 認証失敗の詳細を匿名HTTPへ返してよい？** いいえ。原因の詳細は制限付きログへ残します。

## 実装・運用の詳しい検証

この教材はWinForms＋Dapper経験者が、Blazor Interactive Serverのサーバー側処理と既存業務DBの境界を理解するためのものです。ADは本人を認証し信頼済みのドメイン付きログイン名を取得します。業務の閲覧・編集、部署・行単位の認可は既存DB台帳を操作ごとに照合します。Cookieやcircuitの保持値、画面に表示されたボタンだけでは業務権限を証明できません。

### 実コード例1：画面の入口

```csharp
builder.Services.AddHealthChecks();
app.MapHealthChecks("/health/live").AllowAnonymous();
// livenessはDBや監査の可用性を保証しない。
```


この抜粋は、実際の呼出し経路を追うためのものです。画面で実行するC#は業務サービスを呼ぶ入口にすぎません。認可を通ったように見えても、対象行の部署、現在の権限、監査書込みを確認できなければ結果を公開しません。特に非同期操作をキャンセルした場合やDBから例外が返った場合、古い許可に戻して成功にする処理を追加しないでください。

### 実コード例2：安全な境界の確認

```csharp
private async Task CheckAsync() {
    var result = await Business.AuthorizeAsync();
    _message = result.Message;
}
```

### 実装と判断の詳しい説明

/health/liveはHTTPにプロセスが応答するかのlivenessだけを確認します。IISが応答できてもFDWやPostgreSQL18、本人認証、台帳や永続監査の可用性は別です。業務ボタンはAuthorizeAsyncを通し毎回現在の権限を問い合わせます。本番readinessを追加する場合は監視用権限、タイムアウト、照会頻度、アクセス元制限を設計します。ログは相関ID、操作コード、UTC、結果と所要時間を残し、Cookie・接続パスワード・CSV本文・他部署データを出しません。SignalR再接続、Npgsqlプール待機、ロック待機、監査失敗を別指標にします。

### WinForms＋Dapperとの比較

| 観点 | WinForms＋Dapper | Blazor Interactive Server |
| --- | --- | --- |
| 操作イベント | 各端末のFormで受け付ける | サーバーのRazorとサービスで処理する |
| 権限の正本 | Dapperで既存DBへ毎回照会する | SecuredLearningServiceで操作・行単位を都度判定する |
| 表示状態 | フォーム内の値は古くなり得る | circuitの状態も権限の代わりにならない |
| 監査 | SQLの実行結果と本人・操作を記録 | 永続監査に失敗する場合は業務を安全に拒否 |
| 本番受入 | Windows端末とDB接続を確認 | IIS、Kerberos、SignalR、DBプールと鍵の管理を別途確認 |

### 操作手順

1. 新学習順の目次から正規URLで画面を表示し、前後リンクを確認します。
2. 匿名の開発用ブラウザーで業務の確認ボタンを押し、本人とDB台帳の権限が確かめられないときに拒否されることを確認します。
3. 肯定試験はCI専用の架空PrincipalとPostgreSQL18の架空テーブルだけで行います。本番台帳のレコードや資格情報を教材に投入しないでください。
4. 操作前後の期待結果、実際の画面表示、相関ID、実行日時、コミットSHAを記録します。再操作時もDB正本を確認します。
5. 実AD/IIS/Kerberos/FDWおよび1万人超負荷は、CIとは別に現地で受入票を作ります。

### 障害の切り分け

| 現象 | 最初に確かめる内容 | 合格条件 |
| --- | --- | --- |
| 匿名・台帳未登録・重複 | 認証ハンドラー、ドメイン付き名、照合の0/1/2件 | データを返さず拒否 |
| 権限変更・部署違い | 正本の有効状態、can_read/can_edit、部署 | 過去の許可を再利用しない |
| 競合・行ロック不可 | xmin、トランザクション、FDW条件 | 古いデータを自動上書きしない |
| 監査INSERT・DB障害 | 監査権限、接続、相関ID、ロールバック | 機密の行やCSVを公開しない |
| CI成功・実機未検証 | IIS、SPN、Kerberos、FDW、復旧と負荷 | 現地受入は未完了のままにする |

利用者へSQLエラー、認証Cookie、接続文字列、他部署のデータを表示しません。運用ログは利用者画面と切り分けて保護します。権限失効は再ログインだけで直す問題と決めつけず、現在の正本を確かめます。成功、拒否、競合、通信障害を別の結果として記録してください。

### 演習

FDW停止でも/health/liveが200の場合、業務成功と判断してよいか。

### 詳しい解答

いいえ。業務の正本照合や監査が失敗すれば一覧を拒否します。livenessの200は認証やreadinessの証拠ではありません。

### 現場での確認票

WinForms＋Dapperから移行しても認可の根拠は変わりません。本人を確かめたことと、その本人がどの行へどの操作をできるかを分け、監査が不能な場合は安全に拒否します。設定フラグだけで行ロックや監査の原子性が保証されるわけではありません。実AD、IIS、Kerberos、FDW、鍵の管理、1万人超登録アカウントと同時circuit、DBプールの負荷、復旧手順は現地実機で受入します。CI成功の意味を超えて運用を承認しないでください。
