# 学習順011：入力値を双方向に結び付ける

**実装ソース：** [対応するRazor実装](../../../../src/PgBlazorSamples.Web/Components/Lessons/Stage02/L011TwoWayBindingPage.razor)。画面の正規URLは `/learn/011` です。

## この学習の到達目標
フォームの入力値がどこで保持され、いつC#へ反映され、表示がなぜ変更されるかを理解します。WinFormsのTextBox.TextとTextChangedを知っていても、BlazorではブラウザーがHTMLの入力欄を描画し、Interactive Serverの場合は入力イベントが通信を経由してサーバー側のコンポーネントへ届きます。入力のたびにデータベースへ書き込まれるわけではありません。説明を読んだあと、入力・消去・HTMLエンコード・再読込を順に試し、値の寿命を区別してください。

対象は学習順011、画面URLは `/learn/011` です。Visual Studio 2026、.NET 10のWebアプリ、Chromeを使います。AD、PostgreSQL、MudBlazorは不要で、架空の練習名だけを入力します。画面で見える文字列を業務データの登録結果と混同しないことが重要です。

## WinForms＋Dapperで知っている処理との対応
| 観点 | WinForms | このBlazor画面 |
| --- | --- | --- |
| 入力の表示 | TextBox.Text | HTMLのinput要素 |
| 値の受け口 | フォーム上の文字列変数 | コンポーネントのlearnerName |
| 変更通知 | TextChangedイベント | @bind:event="oninput"による入力時更新 |
| 表示結果 | Label.Textの書き換え | Razorが状態を使ってHTMLを再描画 |
| 値の寿命 | Formインスタンスの寿命 | 対話中のコンポーネントの寿命 |
| 永続化 | Dapperで明示的にSQL実行 | この教材にはDB保存処理がない |

WinFormsでは、TextBoxとLabelは同じプロセスで管理されます。ここでのInteractive ServerではC#のフィールドはWebサーバー側にあります。ブラウザーには入力欄と表示内容があり、イベント情報は通信経路を通ります。デバッグ時には同一PCでサーバーを起動するため差が見えにくくなりますが、配置先がWindows Serverになっても同じ考え方が必要です。値の変更が成功したことと業務DBの保存が成功したことは、明確に区別します。

## 実際に動くRazorの入力欄
次はこの画面に実装された入力要素です。`id`はラベルとの対応にも使われ、`maxlength`はブラウザーの入力文字数の上限を指定します。

```razor
<label for="learner-name" class="field-label">表示する名前（架空の名前を入力）</label>
<input id="learner-name" class="text-input" type="text"
       autocomplete="off" maxlength="40"
       @bind="learnerName" @bind:event="oninput" />
```

`@bind="learnerName"`はC#のフィールドとHTMLの値を結び付けます。`@bind:event="oninput"`は、通常のchangeイベント時ではなく入力途中の変化に応じて値を更新する指定です。通信状態によって反映までにわずかな時間差があり得ます。「文字が見えたから必ずサーバー処理を完了した」とは判断しないでください。IMEによる日本語変換中と確定後の挙動もChromeで確認します。テキスト欄は40文字までですが、将来の業務データ入力では、HTML属性だけでは不十分であり、サーバー側の長さ・形式・権限検証が必要です。

## 表示切替と消去の実コード
```razor
<p class="example-output" data-testid="name-preview">
    @if (string.IsNullOrWhiteSpace(learnerName))
    {
        <span>まだ名前が入力されていません。</span>
    }
    else
    {
        <span>こんにちは、@learnerName さん。</span>
    }
</p>
<button type="button" class="secondary-button" @onclick="ClearName"
        disabled="@string.IsNullOrEmpty(learnerName)">入力を消去する</button>
```

```csharp
// 入力値はこのページの状態に保持します。ADやDBには送信しません。
private string learnerName = "";
// 次の練習のために値を初期状態へ戻します。
private void ClearName() => learnerName = "";
```

表示では`string.IsNullOrWhiteSpace`、消去ボタンの無効化では`string.IsNullOrEmpty`を使っている点に注目してください。空白だけの入力では前者は真になりますが、後者は偽です。したがって空白だけ入力したとき案内は未入力扱いで、消去ボタンは有効です。これは実装上の意図を学ぶ材料であり、必ずしも業務入力の要件に合うとは限りません。ボタンを押すと`ClearName`が文字列を空に戻し、Razorが案内とボタン状態を再描画します。通常の`@learnerName`出力ではHTMLエンコードされます。`<b>学習用</b>`という文字列を入力しても太字のHTML要素として実行されません。HTMLを文字列から安易に組み立てる実装へ変えないでください。

## 操作手順
1. アプリを起動し`/learn/011`へ移動します。ラベルと空の入力欄を確認します。
2. 案内が「まだ名前が入力されていません。」であり、消去ボタンが押せないことを確認します。
3. 練習用の架空名「テスト太郎」を一文字ずつ入力し、「こんにちは、テスト太郎 さん。」になることを確認します。
4. 全角文字を変換し、確定までの画面変化を観察します。Network・Consoleに異常がないかも調べます。
5. 先頭と末尾に空白を入れ、表示上の空白と`IsNullOrWhiteSpace`の判定を区別します。
6. 入力を全消去すると案内が戻ります。再び名前を入れて「入力を消去する」を押し、同じ初期状態になることを確かめます。
7. タグに見える`<b>学習用</b>`を入力してElementsを見ます。要素が増えず文字として出力されることを確認します。
8. 再読込して初期値に戻ることを確認します。画面を閉じたあとでも復元される永続状態は実装していません。

## 故障時の切り分け
| 症状 | 最初に確認する場所 | 理由と対応 |
| --- | --- | --- |
| 入力は見えるが挨拶が変わらない | Networkの接続、Console、サーバーログ | 対話接続が失われるとC#フィールドへイベントが届かない |
| Enterを押すまで反映されない | `@bind:event`の指定 | 既定のchangeとoninputは通知する時機が違う |
| 空白だけで消去可能 | `IsNullOrEmpty`の条件 | 仕様通り。未入力案内の条件とは別 |
| タグの文字列がHTMLとして実行される | `MarkupString`や独自HTML組立ての有無 | この画面の通常のRazor出力では起きない。変更したコードを戻す |
| 再読込後に文字が消える | `learnerName`の初期値 | DBやブラウザー保存先を設けていない正常動作 |
| DBに名前が存在しない | サンプルの範囲 | SQL・Dapper・EF Coreの保存処理は一切呼んでいない |

## 演習と詳しい解答
**演習1：** `@bind:event="oninput"`を外した場合、表示更新の時機はどう変わるでしょうか。実際に教材用コードで試す前に予想してください。

**解答1：** テキスト入力の`@bind`は通常changeイベントで更新されるため、入力中の一文字ごとではなく、フォーカスが外れるなど値の変更が確定した時機が中心になります。業務画面では検索候補を即時更新するか、入力確定後に更新するかを要件で判断します。即時入力をそのまま大量のSQL問い合わせに結び付けるのは避けます。

**演習2：** スペース3文字だけを入力しました。案内とボタンはそれぞれどうなりますか。

**解答2：** `IsNullOrWhiteSpace`が真なので未入力の案内を表示します。一方`IsNullOrEmpty`は偽なので消去ボタンは有効です。同じ変数でも条件の意味が違うことを説明してください。業務要件で空白を禁止する場合は保存前の検証を追加します。

**演習3：** フィールド値が表示されたら、監査記録も保存済みだと判断できますか。

**解答3：** できません。値は対話中のコンポーネント状態です。DB書込み、権限確認、永続監査は未実装です。WinFormsでTextBox.Textを変更するだけではDapper.Executeが実行されないのと同じです。

**演習4：** 空の入力で消去ボタンが無効である理由を、処理側の制約と区別して説明してください。

**解答4：** `disabled`は操作しやすさのための画面指定です。現在の`ClearName`は値を空にするだけなので、空でも呼ばれて問題はありません。しかし業務保存処理や認可を実装するなら、HTMLのdisabledだけで安全性を保証してはいけません。
