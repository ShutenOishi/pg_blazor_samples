# 学習順017：事前レンダリングと初期化の実行回数

**実装ソース：** [対応するRazor実装](../../../../src/PgBlazorSamples.Web/Components/Lessons/Stage02/L017PrerenderInitializationPage.razor)。画面の正規URLは `/learn/017` です。

## この学習の目的
`/learn/017`では、Interactive Serverの「最初にHTMLを返す処理」と「対話を受け付ける処理」を区別します。WinFormsではForm.Loadの実行を一回の画面起動に結び付けて考えがちですが、Blazorは事前レンダリングの設定によって最初の静的HTMLを作るインスタンスと、その後ブラウザーと対話するインスタンスが別になることがあります。表示中の初期化回数だけを見て、サーバー全体のOnInitialized実行回数を数えたつもりにならないでください。

学習順016では子の表示・非表示とIDisposableを扱いました。今回は同じ考えをページの最初の表示に当てはめます。環境は.NET 10、Visual Studio 2026、Chromeで、DB・AD認証・業務登録は使いません。表示に使う数値はこの画面が保持する練習用のフィールドです。

## 事前レンダリングとは何か
ブラウザーがURLを要求すると、サーバーはまずHTMLを返せます。事前レンダリングを有効にしたInteractive Serverでは、初期のHTML作成のためにコンポーネントを実行し、後で対話型の別インスタンスを開始する場合があります。したがって初期化のコードには二度呼ばれる可能性があり、ページ閲覧一回に対して必ず一回しか実行されないと設計してはいけません。一方、画面で現在見えているカウンターは、その時点の対話型インスタンスが持つフィールド値です。事前レンダリングに使われた別インスタンスの実行を合計した数字ではありません。

この教材のApp.razorはRoutesをInteractiveServerで使っています。画面には識別用のランダムな文字列`instanceId`と、`initialized`、`afterFirstRender`、`changes` の三つのintがあり、それぞれ役割が異なります。`OnInitialized` は初期化の回数を増やし、`OnAfterRender(bool firstRender)` は初回の描画後に一回だけ `afterFirstRender` を増やします。クリックイベント `Add` は変更回数だけを増やします。

```razor
<p>初期化回数：
  <strong data-testid="runtime03-init">@initialized</strong>
</p>
<p>初回の描画後処理：
  <strong data-testid="runtime03-after">@afterFirstRender</strong>
</p>
<button type="button" @onclick="Add">状態を変更する</button>
<p>変更回数：
  <strong data-testid="runtime03-change">@changes</strong>
</p>
```

Razorの `@initialized` などは現在のコンポーネントの値をHTMLに表示します。初期HTMLと対話イベントの通信は別の段階です。ボタンの処理が動かなくても見出しや初期HTMLが表示される場合があり、Document取得成功をInteractive Serverの接続成功と取り違えないことが重要です。

### 初回Documentと対話型インスタンスを実際に識別する

画面には`data-testid="runtime03-instance"`で、コンポーネントが作られるたびに新しく生成される32桁の識別子を表示します。これは学習用のランダム値であり、circuit ID、利用者名、サーバー名、監査IDではありません。Chrome試験では初回DocumentのHTMLにある識別子と、Interactive Serverの対話開始後に画面へ表示される識別子を照合し、両者が異なることを確認します。また、初回HTMLの`OnAfterRender`表示0と、対話開始後の表示1を区別して確認します。

```csharp
private readonly string instanceId = Guid.NewGuid().ToString("N");
```

この観察は**このアプリの事前描画構成で別インスタンスが生成されたこと**を示します。すべてのBlazorアプリの初期化が常に2回になる、個別の利用者接続が永久に保持される、といった保証ではありません。

## C#の呼出し条件を読む
```csharp
private int initialized;
private int afterFirstRender;
private int changes;

protected override void OnInitialized() => initialized++;

protected override void OnAfterRender(bool firstRender)
{
    // 事前レンダリング時には実行されない。
    if (firstRender)
    {
        afterFirstRender++;
        _ = InvokeAsync(StateHasChanged);
    }
}
private void Add() => changes++;
```

`firstRender` がtrueなのは、そのインスタンスにおける最初の描画後処理です。このコードはOnAfterRenderの全呼出しを数えるのではなく、条件を満たしたときだけ `afterFirstRender` を増やします。表示更新には `InvokeAsync(StateHasChanged)` を使用します。すべてのOnAfterRenderで無条件にStateHasChangedを呼ぶと描画が繰り返されるおそれがあるため、初回条件を外して安易に変更しないでください。

この例は画面内の観察用です。事前レンダリング時にOnAfterRenderは呼ばれません。ブラウザー側のDOMを用いる操作やJavaScript interopを初期化中に実行してよいと判断しないでください。対話接続が利用できる描画後の段階を理解した上で、後の学習順041でJS interopを扱います。

## WinForms＋Dapperとの比較
| WinFormsの経験 | Blazorの対応 | 注意する違い |
| --- | --- | --- |
| Form.Load | OnInitialized | 事前レンダリングと対話型で別インスタンスになる場合がある |
| Form.Shownに近い画面表示後の処理 | OnAfterRender | 事前レンダリング中は実行されず、描画のたびに呼ばれ得る |
| ボタンのClick | @onclickとAdd | この教材ではサーバーのC#メソッドを呼ぶ |
| フォームを閉じて開き直す | 再読込と新しいコンポーネント | メモリ状態は引き継がないことがある |
| Dapper.Executeで永続化 | ここには処理なし | フィールドの変更回数はDBの更新件数ではない |

WinFormsではプロセス内にUIとイベントの処理があることが一般的ですが、この教材のC#はWebサーバー上で実行されます。画面の描画やボタン操作のたびに必ず新しいコンポーネントになるわけでもありません。`OnInitialized` と `Add` を分けて観察すると、表示の更新と初期化の境界がわかります。

## 実画面で確認する手順
1. `/learn/017`を開き、初期化回数、初回の描画後処理、変更回数の三つを記録します。対話型表示で初期化1、描画後1、変更0を確認してください。
2. 「状態を変更する」を一回押し、変更回数が1になることを確認します。初期化回数はそのままです。
3. もう一度押し、変更回数が2になることを確認します。OnInitializedがクリックごとに実行される構成ではないことがわかります。
4. ChromeのNetworkでDocumentのHTMLにある`runtime03-instance`の識別子と、対話開始後のElementsで表示される識別子を比較します。このアプリでは両者が異なり、初回HTMLの描画後処理0・対話開始後1となることを確認します。表示があっても対話通信が失敗する場合があることを整理します。
5. ページを再読込して、変更回数が0から始まることを確認します。新しい画面のフィールドであり、ブラウザーストレージやDBへ保存していません。
6. 事前レンダリングの実際の総実行回数を確認したいときは、表示中の三つの数字だけで判断せず、実行構成とサーバー側のログを用いる必要があります。

## 副作用のある初期化を避ける理由
`OnInitialized` に一度だけ実行すべきDBのINSERT、メール送信、承認などを直接入れると、事前レンダリングと対話型起動の両方で行われる可能性があります。再読込、別タブからのアクセス、再接続後の再生成でも回数は変わります。「初期化だから一回だけ」という説明では業務上の重複処理を防げません。利用者の明示的な操作に対応するサーバー側の処理として設計し、必要なら一意制約、冪等な要求、トランザクション、監査などで結果を保証します。

## 障害・誤解の切り分け
| 症状 | 先に確認すること | 説明 |
| --- | --- | --- |
| 初期化処理のログが二つある | 事前レンダリングと対話型の設定 | 別インスタンスの初期化である可能性 |
| 初期化表示が1なのに二度実行されたと聞いた | 表示値がどのインスタンスの値か | 画面は全体の合計ではない |
| ボタンを押しても変更回数が増えない | SignalR、Network、サーバーログ | HTMLの取得成功と対話成功は別 |
| 初回の描画後処理が1のまま | firstRenderの条件 | OnAfterRender全体の回数を数えていない |
| 再読込で変更回数が0に戻る | フィールドの初期化 | 永続化していないので正常 |
| 描画が終わらず繰り返される | StateHasChangedを無条件で呼んでいないか | 描画後処理による循環を避ける |

見えている数字の意味がわからないときは、それぞれのフィールドがどのメソッドで増えるかをコードから追ってください。画面内の回数は現在のインスタンスの状態です。別インスタンスで実行された回数を集計する必要があるなら別の観測方法を設けるべきで、静的なHTMLから逆算してはいけません。

## 演習と詳しい解答
**演習A：** 変更ボタンを二回押した後、初期化回数、描画後処理、変更回数の関係を説明してください。

**解答A：** 表示中の対話型インスタンスは既に初期化されています。Addによって増えるのはchangesだけなので、通常は初期化1、初回描画後1、変更2です。OnAfterRender自体は別の描画でも呼ばれますが、この画面はfirstRenderの場合しかafterFirstRenderを増やしません。サーバー全体でOnInitializedが実行された総数とは異なります。

**演習B：** 事前レンダリングを利用している画面のOnInitializedで業務DBへ同じ内容を登録する処理を置いても安全ですか。

**解答B：** その方法で一度限りの登録を保証することはできません。静的HTML用と対話用のコンポーネントが別々に初期化され得るからです。明示的な要求でのみ更新し、入力検証、AD本人認証、既存DB台帳の認可、重複防止、監査までサーバー側の処理として設計します。この教材の画面はDB操作を実装していません。

**演習C：** 画面が表示されたのにクリックできないとき、OnInitializedの不具合と決めてよいでしょうか。

**解答C：** いいえ。DocumentのHTML生成だけが成功し、対話接続に失敗している場合があります。ブラウザーのNetworkとConsole、サーバーログを確認し、接続障害、例外、画面イベント処理を切り分けます。HTMLが見えたことはサーバー側イベントの成功証拠になりません。
