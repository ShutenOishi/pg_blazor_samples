## WinForms＋Dapperからの移行で考えること

| 観点 | WinForms | Interactive Server |
| --- | --- | --- |
| イベント | クライアントPC内のC# | ブラウザーが通知しサーバーC#が処理 |
| newによる生成 | Form内で直接生成もできる | DIに生成を委ねる選択肢がある |
| 状態の共有 | Form/staticの寿命で考える | circuit・スコープ・利用者分離で考える |
| DB処理 | Dapperの接続・SQL | DIを使ってもDBの認可は別途必要 |
| 単体テスト | 固定入力と置換できる依存が便利 | IClockを固定して同様に検証できる |

## 最初の画面とサービスの接続を読む

```csharp
// Program.csの登録抜粋
builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddTransient<GreetingService>();
builder.Services.AddScoped<ScopedCounter>();
```

```razor
@inject ScopedCounter Counter
<p>値：@Counter.Count</p>
<button @onclick="Increase">親から1増やす</button>
@code {
    private void Increase() => Counter.Increment();
}
```

このコードの登録はサーバー起動時の構成であり、利用者がボタンを押すたびに新しい登録を追加するものではありません。クリックでサーバー側のCountを変更しても、永続DBへの書き込みは起こりません。表示が変化するのは、イベントを処理したコンポーネントがRazorの値を描画し直すためです。子コンポーネントにも同じScopedCounterを渡したい場合は、単に共有するだけで親の再描画まで保証されないため、EventCallbackなどの通知が必要です。

## 症状から確認場所を選ぶ

| 症状 | 最初に調べる場所 | 判断に必要なこと |
| --- | --- | --- |
| 画面を作れない | Program.csとコンストラクター | 必須の型が登録されているか |
| 再描画後も識別子が変わらない | DI解決の呼び出し | 再描画と再解決を区別 |

## 確認問題と解答

**問1：** ScopedCounterに入れた値はサーバー再起動後も残るでしょうか。

**解答1：** 残るとは限りません。ScopedCounterはインメモリの練習用状態です。永続化する業務データはDBで保存し、毎操作の認可を別に設計します。

**問2：** IClockをDIに登録しなかった場合、GreetingServiceは動くでしょうか。

**解答2：** コンストラクターで必要とするIClockを解決できず、DIでGreetingServiceを生成する際に失敗します。画面より先に登録を確認します。

**問3：** WinFormsでのnewを全部禁止すべきですか。

**解答3：** そうではありません。表示用の短命な値などの生成は適切です。交換やテストが必要な依存先を外から受け取ることで、責任と寿命を明確にするのが狙いです。

## 安全な業務開発との境界

ここでの時計・識別子・カウンターは架空の学習用です。DIの成功を、AD本人認証、既存DB/外部台帳による都度認可、監査永続性、IIS・Kerberosの実機受入と同一視しません。後続のDB学習では操作単位のDbContextFactoryを使用し、長命なScoped DbContextを前提としません。学習内容と本番受入の証拠を分離して記録してください。
