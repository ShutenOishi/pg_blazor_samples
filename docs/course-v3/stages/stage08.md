## WinForms＋Dapperの経験を生かす

WinFormsでは`WindowsIdentity`により本人を取得しても、業務データへの権限は別の台帳で判定します。Dapperの`IDbTransaction`を使った更新でも、認可と監査を別々の接続へ分離してしまうと一貫性を保証できません。Blazor Interactive Serverではクライアントのボタン状態を認可の根拠にせず、サーバーサービス内で再認可します。`DbContext`の寿命とトランザクション境界を明確にし、SignalR再接続や別タブも想定します。

| 観点 | WinForms＋Dapper | Blazor＋EF Core |
| --- | --- | --- |
| 本人情報 | 検証済みWindowsIdentity | IIS/Negotiate/ASP.NET Core認証主体 |
| 入力UI | ボタンのEnabled状態は認可ではない | Razorの表示とサービス認可を分離 |
| DB更新 | SQLとIDbTransactionで対象を限定 | DbContext、Visible、xmin、監査の同時確定 |
| 失効 | 業務実行の直前に正本を読む | circuit再接続後も操作ごとに認可 |
| 診断 | アプリログと業務監査を分離 | ILoggerと永続監査表の役割を分ける |

### 実コード例1：読み取りでも正本の認可を要求する

```csharp
var permit = await AuthorizeAsync(ct: ct);
if (permit.Unit is null)
    return new([], 0, permit.Message);
var query = Visible(db, permit.Unit).AsNoTracking();
var rows = await query.OrderBy(x => x.Id).Take(100).ToListAsync(ct);
await audit.WriteRequiredAsync(db, "task.list",
    permit.Unit, 0, rows.Count, "success", ct);
```

この断片は認可と監査の順序を示すもので、実際のフィルタ・ページング・DTOは`SecuredLearningService`で確認します。台帳照合や監査が失敗したときは業務データを返しません。

### 実コード例2：書込みの安全な初期設定

```json

  "WindowsAuthentication": { "Enabled": true, "ExplicitLoginEnabled": false },
  "Authorization": {
```

`false`は確認されていないトランザクション・監査の本番運用を許可しない状態です。承認前に真へ変更せず、台帳ロックと同一トランザクション、監査INSERTのロールバック、鍵共有、IIS/Kerberosの受入を実施します。

## 障害の切り分け

| 症状 | 判断する証跡 | 取るべき対応 |
| --- | --- | --- |
| 認証はできるが一覧が拒否 | 台帳0/1/2件、閲覧権限、監査INSERT | 本人認証を業務許可へ変えず正本を修復 |
| Cookieが別ノードで無効 | Data Protection鍵とACL、ローテーション | 鍵の保護・復元手順を実地検証 |
| FDWが遅い・ロックできない | EXPLAIN、pushdown、FOR UPDATEの保証 | 原子性不明なら更新停止 |
| 更新競合 | 最新xmin、権限行ロック、DBトランザクション | 再読込を促し旧版の上書きを拒否 |
| 監査保存が失敗 | 永続監査SQL、接続、ロールバック | データ非公開・保存取消 |
| 高負荷で接続が枯渇 | circuit・Npgsql物理接続・P95/P99 | 登録人数と同時接続を分けて改善 |

## 演習と詳しい解答

**演習1．** 明示ログインCookieに編集権限を保存した場合、権限剥奪時にどうなりますか。

**詳しい解答1．** Cookieが期限切れになるまで古い権限を利用してしまうおそれがあります。Cookieは本人情報の認証に限定し、操作時に既存DB台帳の正本で部署・操作・対象行を都度再認可します。

**演習2．** FDW原本に`SELECT FOR UPDATE`が使えず、業務DB側だけトランザクションを張れます。更新はできますか。

**詳しい解答2．** 原本の権限失効と業務更新の原子性が保証できないため、この構成では更新を拒否します。正本側APIへの設計変更や実機で保証できる方式を受け入れるまで`TransactionalLedgerConfirmed`を有効にしません。

**演習3．** Chrome E2EとPG18実DBテストが通ったので1万人同時利用のSLOも達成したと評価できますか。

**詳しい解答3．** 評価できません。台帳登録者数、同時ブラウザー数、circuit数、NpgsqlプールとDB実接続は異なります。実機で合意した負荷と復旧操作を行い、P95/P99・失敗率・メモリ・接続待ちを保存します。

**演習4．** 監査書込みが失敗した業務更新を、ログだけ別サーバーへ送信して成功扱いできますか。

**詳しい解答4．** できません。永続監査が業務の成功条件であり、更新と監査の同一トランザクションが必要です。インフラログは診断用に残しても、更新と業務データ公開を許可する理由にはなりません。
