# 第3組の復習：入力・部品・対話回線の復習

## この組で確認すること
学習順011〜015では、入力欄からC#の値へ、値から表示内容へ、親から子へ、子から親へ、そしてブラウザーからサーバーへと、情報が流れる経路を段階的に学びました。この復習は、個々のRazor構文を暗記するための問題集ではありません。WinForms＋Dapperの経験をもつ学習者が、Webの画面で「何を誰が保持し、いつ更新され、何が保存されないのか」を自分で説明できるようにします。ネットワークが切れても画面に文字が残ることと、業務DBに情報が保存されたことは同じではありません。

実行環境はVisual Studio 2026、.NET 10、Chromeで、AD・業務DBは使用しません。以下の学習順どおりに画面を開き、操作後の数字・選択・表示件数を記録してください。

| 学習順 | 開く画面 | 主な構文 | 実際に起きること |
| --- | --- | --- | --- |
| 011 | /learn/011 | @bind、@bind:event="oninput" | 入力した文字を即時表示し、消去する |
| 012 | /learn/012 | @if、@foreach、@key | 固定4件から未完了2件を表示する |
| 013 | /learn/013 | [Parameter] | 親の入力が1枚目の子カードにだけ届く |
| 014 | /learn/014 | EventCallback<string> | 子が親へ選択を通知し、回数が増える |
| 015 | /learn/015 | @onclick、SignalR、circuit | 対話回数を一時保持し、再読込で0に戻る |

## WinFormsとの対応を説明する
| WinForms＋Dapper | このBlazor演習 | 違いを意識する点 |
| --- | --- | --- |
| TextBox.TextChanged | @bind:event="oninput" | Interactive Serverでは入力イベントが通信を伴う |
| CheckBox.Checkedと行のフィルター | showOnlyIncomplete、VisibleTasks | 今回はメモリー配列を選ぶだけでSQLを実行しない |
| FormからUserControlへ値を渡す | [Parameter] | 親が渡した値の所有権を子へ移さない |
| UserControlのイベントをFormが受ける | EventCallback<string> | 子から通知し、親が状態を更新する |
| Formのフィールド | circuit内のコンポーネント状態 | 接続断・サーバー再起動時の復元を保証しない |
| Dapper.Executeによる明示的保存 | 今回の5画面には存在しない | UI状態は保存結果でも監査結果でもない |

### 1. 入力から表示までをコードでたどる
```razor
<input id="learner-name" class="text-input" type="text"
       autocomplete="off" maxlength="40"
       @bind="learnerName" @bind:event="oninput" />
```

入力した文字列は`learnerName`へ反映され、`@if (string.IsNullOrWhiteSpace(learnerName))`の条件と表示へ使われます。これはサーバーのコンポーネントが保持する一時値です。空白だけの入力と空文字列では、案内とボタンの無効状態が異なります。これを「想定外の不具合」と決めつけず、`IsNullOrWhiteSpace`と`IsNullOrEmpty`の条件の違いとして説明してください。

### 2. 条件付き一覧の根拠を読む
```csharp
private LearningTask[] VisibleTasks => showOnlyIncomplete
    ? tasks.Where(task => !task.IsCompleted).ToArray()
    : tasks;
```

元の固定配列4件は、画面側で2件に見えても削除されません。チェックボックスの状態だけを変え、抽出対象を決めています。後のEF Core学習では、権限条件も含めたSQL側の検索が必要なことを学びます。現在の`Where`はあくまでC#の配列操作であり、PostgreSQLの`WHERE`ではありません。

### 3. 親子の入力と通知を区別する
```razor
<GreetingCard LearnerName="@learnerName" Topic="親が入力した名前" />
<TopicPicker SelectedTopic="@selectedTopic" OnSelected="OnTopicSelected" />
```

```csharp
[Parameter]
public EventCallback<string> OnSelected { get; set; }

private Task ChooseAsync(string topic) => OnSelected.InvokeAsync(topic);
```

`GreetingCard`の`[Parameter]`は親の値を受け取ります。一方`TopicPicker`は選択結果を`EventCallback`で親へ返します。親→子と子→親のどちらも、子が親のフィールドへ直接アクセスする構成ではありません。画面へ同じ部品を何回置いても、その部品の入力と通知の契約が明確になっていれば再利用しやすくなります。実DB更新を追加するときは、画面から通知があった事実だけで完了扱いせず、サーバーで認可・保存・監査の成功を確認します。

## 5画面を通した実習
1. `/learn/011`で「テスト太郎」を入力し、同じ文字が挨拶に反映されることを確かめます。消去ボタンを押すと案内が戻ります。
2. `/learn/012`で初期4件を確認し、未完了チェックを入れると2件になることを確かめます。元データの削除は起きていません。
3. `/learn/013`で「練習花子」を入力します。1枚目のカードだけが変化し、2枚目の「架空の利用者」はそのままです。
4. `/learn/014`で「Razor構文」「イベント処理」「双方向バインディング」の順に押します。選択回数は3です。すでに選んだテーマを再び押しても回数は増えます。
5. `/learn/015`でカウンターを2回増やし、2であることを確認します。開発者ツールのNetworkで最初のHTML要求と対話通信を見比べます。
6. 再読込して回数が0に戻ることを確認します。一時的な回線切断時に同じcircuitへ戻れるかは環境に依存し、再現結果を一般化しません。
7. 5つの画面を並べて「URL」「所有する状態」「操作すると動くメソッド」「保存先」の4項目を書き出します。保存先がないものは「サーバー側コンポーネントのみ」と記録します。

## 失敗・誤解の切り分け
| 症状・疑問 | 確認先 | 説明 |
| --- | --- | --- |
| 入力中の文字が表示へ届かない | @bind:eventと通信、サーバーログ | oninputであるかと対話接続を確認 |
| 絞り込み後の件数がおかしい | VisibleTasksとIsCompleted | 固定配列を変更したかを確認 |
| 子カード2枚とも同じになった | 親のGreetingCard引数 | 2枚目へ固定値ではなく変数を渡していないか |
| 子のボタンを押しても回数が増えない | OnSelectedと親メソッド | 通知から状態変更までの経路を確認 |
| SignalR再接続後に回数が消えた | circuitの寿命とサーバー状態 | 必ず復元される仕様ではない |
| 画面で名前が見えるのでDB登録済みと思う | 保存処理の有無 | 今回の5画面にはDB呼び出しがない |
| 画面から隠せば業務認可になると思う | サーバー側の権限確認 | 表示フィルターだけでは情報を保護できない |

## 理解を確かめる問題と詳しい解答
**問題A：** 学習順011の文字入力で、スペースのみを入れた場合はどのように表示されますか。

**解答A：** `IsNullOrWhiteSpace`の判定では未入力扱いとなり「まだ名前が入力されていません。」と表示されます。`IsNullOrEmpty`は空白のみを空と判定しないため消去ボタンは有効です。この違いを条件の不一致と呼ぶ前に、要件上どちらの判定が必要かを決めるべきです。

**問題B：** 学習順012の一覧が4件から2件へ変わったら、DBの2行を削除したことになりますか。

**解答B：** なりません。`tasks`は4件の架空配列であり、`VisibleTasks`で未完了を抽出するだけです。DBには接続しておらず、SQLも発行しません。将来の業務システムで「画面から消しただけ」を削除や非公開扱いにしないよう注意します。

**問題C：** 学習順013の子カードが親の`learnerName`を変更したくなったとき、直接`LearnerName`へ代入するのがよいですか。

**解答C：** 避けます。親が所有する状態は親で変更します。子は値を受け取り表示する役割とし、変更が必要なら通知の契約を設けます。次の親描画で値が上書きされる不整合を防ぐためです。

**問題D：** 学習順014で同じ「Razor構文」を2回押したとき、選択回数はいくつですか。

**解答D：** 初期状態からなら2です。`OnTopicSelected`は通知が来るたび`selectionCount++`を実行し、別の値になったかは検査しません。選択変更件数を計測したい要件では追加条件が必要です。

**問題E：** SignalR接続が再開したら、以前の`count`が必ず残っていると説明してよいでしょうか。

**解答E：** いけません。保持中のcircuitへ再接続できた場合は残る可能性がありますが、再起動・保持期限・通信条件に左右されます。画面状態の永続化が必要なら、データの性質に応じた保存先を別途設けます。

**問題F：** `EventCallback`で業務登録を通知できれば、ユーザーの業務認可も監査も自動的に保証されますか。

**解答F：** 保証されません。`EventCallback`はコンポーネント間の通知契約です。業務操作を実装する際はADで得た本人のドメインユーザー名と既存DB台帳を照合して都度認可し、権限・排他・監査を必要な範囲で原子的に成立させます。この復習の固定データとカウンターには業務登録処理がありません。
