# 学習順007：URLと画面遷移を理解する

## 到達目標と前提

WinFormsではボタンを押して別のFormを開きます。Webでは利用者がURLを指定しただけでも対象の画面が選ばれます。`@page`の値、リンクの`href`、ルーティングの解決結果を分けて観察すると、画面名とアドレスの不一致を早い段階で発見できます。今回のページは、戻る・進む・目次へ移動する3つのリンクを備えています。リンクをクリックした場合だけでなく、URLを直接入力した場合も同じページへ到達できることが目標です。

この章の対象は .NET 10、Visual Studio 2026、Blazor Web App（Interactive Server）です。第1段階のHTTPとブラウザーの役割を学習済みであることを前提とします。教材画面の操作にはActive Directory・PostgreSQL・業務データを必要としません。実際の画面は **`/learn/02`** です。前のテーマから順に進んでも、この章だけを開いて確認できるよう、コードと操作方法を以下に示します。

## 1. WinForms＋Dapperとの対応を確認する

| 観点 | WinForms＋Dapper経験者の見方 | 本教材のBlazor | 
| --- | --- | --- |
| 画面移動 | Show/ShowDialogでフォーム表示 | URLとリンクを使ったルーティング |
| 現在地 | ActiveFormや選択状態 | 現在のURLとNavLinkの一致判定 |
| 移動先の指定 | フォームの型やインスタンス | hrefのパス |
| 見つからない画面 | 自作エラー画面等 | 一致するルートがない場合の404/NotFound |
| ブックマーク | 独自実装が必要な場合が多い | URLを直接保存できる |
| 認可 | 業務フォームの起動前後で確認 | URL非表示だけに頼らずサーバー側で確認 |

比較する際は、WinFormsで自分が操作するPCと、業務アプリのサーバー側に配置されるC#が同じ場所とは限らない点を意識してください。ここに示すDapperは経験上の比較対象です。今回のサンプルはDapperやEF Coreを実行しません。後続のDB編では、業務データを取得する際に認可を行った上でサーバー側からアクセスします。

## 2. 実際のRazor画面コードを読む

次は実装中の主要部分の抜粋です。コンポーネント全体の他のHTMLや見出しは省略していますが、掲載した要素・表示文字列と識別子は現行実装に対応します。

```razor
@page "/learn/02"

<PageTitle>ステップ02：画面遷移｜Blazor ステップアップ学習</PageTitle>
<h1>URLとルーティング</h1>
```

`NavigationPage.razor`の`@page "/learn/02"`がこのコンポーネントのルート定義です。`NavLink`はリンクの宛先を`href`に持ち、`Match="NavLinkMatch.All"`ではアドレス全体が一致したときに現在地の判定をします。`aria-label`はこの`nav`領域が何をする場所かを読み上げ側へ説明するためのものです。トップページと共通メニューからも同じ学習先に進めます。リンクの表示文字列を変更しても、`href`を変更しない限り移動先は変わりません。

## 3. C#または関連する実コードを確かめる

次も現行実装から抜き出した部分です。画面や状態の理解に必要な部分を残しています。先のコードと照らして、HTMLが担当する表示とサーバー側の処理を切り分けてください。

```razor
<nav aria-label="画面遷移の練習" class="practice-nav">
    <NavLink href="/" Match="NavLinkMatch.All">学習の目次</NavLink>
    <NavLink href="/learn/01" Match="NavLinkMatch.All">ステップ01へ戻る</NavLink>
    <NavLink href="/learn/03" Match="NavLinkMatch.All">ステップ03へ進む</NavLink>
</nav>
```

画面遷移の失敗には種類があります。ブラウザーのアドレスが正しくても、サーバーが起動していなければページは開きません。サーバーに到達しても該当する`@page`がなければルートは解決できません。URLが正しく、HTMLが表示されていても、対話型イベントを使うページではその後の通信が切れて操作できない場合があります。この段階では404と接続不可、画面は見えるが操作できないという3種類を混同しないことが大切です。また、URLを知っている人が画面を開けることと、その人に業務データを表示する権限があることは別です。本教材のナビゲーションは学習用で、将来の実業務では各検索・更新・出力をサーバー側で認可します。

## 4. ブラウザー・サーバー・状態の境界

今回扱う値や表示は、画面が提供する学習用の例です。Interactive ServerのC#はサーバー上で動き、ブラウザーがHTMLを描画します。初期のHTTP応答で文字が見えることと、対話型イベントに対応するC#が実行できることは同じ確認ではありません。ブラウザーのNetwork、Consoleと、Webサーバーの実行ログやVisual Studioのブレークポイントは、それぞれ調べられる範囲が異なります。

また、画面を開けたことをDB保存の完了や業務権限の成立と取り違えないでください。実業務では利用者のAD本人認証に加え、既存DB台帳を正本とした権限判定、必要な操作記録が別に必要です。ここで扱うサンプルには、それらの業務処理を追加したとは主張しません。

## 5. 順番に操作して確かめる

1. 起動中のWebアプリで`/learn/02`をアドレス欄に直接入力する。
2. ページ内の「学習の目次」を押し、URLがトップへ移ることを確認する。
3. 戻って「ステップ01へ戻る」、続いて「ステップ03へ進む」をそれぞれ開く。
4. 開発者ツールのElementsでリンクの`href`を調べ、画面の表示文字列と宛先が別であることを確かめる。
5. 左側の学習メニューで現在地に応じて表示が変わるかを確認する。
6. 存在しない学習URLを新しいタブで開き、日本語の見つからない画面へ進むことを確認する。

画面の文言を変更する演習では、保存後に表示が更新されたことだけを確認するのではなく、**どのRazor/C#の行を変えたことで、どのHTMLや表示状態が変わったか**を説明してください。学習用データには架空の値を使用し、実在する利用者の名前・認証情報は入力しません。

## 6. 症状別の切り分け表

| 症状 | 確認箇所 | 判断と対応 |
| --- | --- | --- |
| リンクを押しても期待した画面に移らない | hrefの値と@pageの値 | 文字列を照合し、表示ラベルだけで判定しない |
| 直打ちだけ404になる | URLのルート定義と起動先 | 末尾のパス、ホスト、ポートを照合 |
| 選択中の強調がない | 現在URLとNavLinkMatch.All | 一致条件とCSSを別々に確認 |
| リンクは動くが次画面のボタンが動かない | 接続状態・サーバーログ | ルーティング成功と対話接続の問題を切り分け |
| 画面は開くが必要なデータが拒否される | 認証・台帳認可のサーバー側判断 | リンク表示やURLを権限の根拠にしない |

診断の順序は、まずサーバーへ接続できるか、次にURLとHTMLが一致するか、その後に対話型接続とC#イベントが働くか、最後に表示・値の仕様が正しいかという順番です。ChromeのConsoleに表示がないからといって、サーバー側のC#が正常だったとは判断できません。逆に、意図的に無効化したボタンの動作を通信障害と決め付けることも避けます。

## 7. 演習問題と詳しい解答

### 問題1

`NavLink`と単純な`a href`は同じですか。

**解答と根拠：** どちらも遷移先を示しますが、NavLinkには現在のURLとの一致に基づく選択表示の仕組みがあります。

### 問題2

ラベルを「次へ」に変えても遷移先は変わりますか。

**解答と根拠：** `href`を変更しないなら移動先は変わりません。ナビゲーションの説明文字とリンク先の指定は別だからです。

### 問題3

URLを秘密にすると業務画面を保護できますか。

**解答と根拠：** できません。WebのURLは利用者が直接指定できます。機密データの取得・更新・出力は認証と既存DB台帳の権限判定をサーバー側で行います。
