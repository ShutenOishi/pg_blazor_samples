# ステップ77：キャッシュの有効期限と権限失効

## 到達目標

Blazor Interactive ServerのScopedがcircuitごとであることを踏まえ、キャッシュがあるからといって既存DBの認可を省略してはいけない理由を実装で確認します。

## このステップの実装

Step77の画面は、まずSecuredLearningService.AuthorizeAsyncで本人・DB正本の有効性を確認し、さらにWindowsUserAccessServiceから**現在の**所属部署とauthorization_versionを取得します。この2回目の照会は教材として境界を見せるためであり、業務一覧を取得する場合は業務サービスが認可と監査を担います。認証・部署・権限版が不整合ならキャッシュを破棄して拒否します。

AuthorizedLessonHintCacheはScopedの小さなクラスで、キーに本人の正規化ログイン名・部署コード・権限版を使い、保存時刻から30秒を超えるとヒットしません。格納するのは**公開してもよい学習用ヒントだけ**です。実データの行・CSV・件数を保存したり、キャッシュから返したりはしません。

## 操作手順

1. 匿名の学習環境で「最新の権限とキャッシュを確認」を押すと拒否になり、ヒントは保存されません。
2. 認証済みの架空CI利用者では初回は再生成、同じ正本のまま再操作すると再利用となることを確認します。
3. 既存台帳の所属・authorization_versionを変更すると、以前のキーを再利用できなくなることを確認します。
4. 30秒以上経過した場合と「表示用キャッシュを消去」後は再生成になります。
5. ブラウザーを分けて同じヒントを共有しないことを確認します。

## なぜ業務一覧はキャッシュしないのか

利用者に見せる行・集計・CSVは操作ごとに現在の権限が必要です。さらにStep74の永続監査は**応答前に**保存されなければなりません。単純に「先ほど許可したから」と一覧のキャッシュを返すと、権限剥奪や監査停止を迂回する恐れがあります。実業務でのキャッシュ導入はトランザクション・失効イベント・監査を設計してから行います。

## 確認問題と解答

**Q1. 30秒未満なら権限再照会を省略できる？** いいえ。キャッシュTTLは権限の有効期間ではありません。

**Q2. authorization_versionだけで本人を特定できる？** いいえ。本人と部署もキーに含めます。

**Q3. Singletonへ変えれば1万人のユーザーに対応できる？** いいえ。別利用者へ情報が混ざる危険があります。キャッシュ対象・共有範囲・失効方式を先に決めます。
