# 学習順90：既存台帳の業務権限を確認する

**実装ソース：** [対応するRazor実装](../../src/PgBlazorSamples.Web/Components/Lessons/Stage07/L090RolePermissionPage.razor)。画面の正規URLは `/learn/090` です。

**第7段階・第18組／正規URL /learn/090**

## 到達目標

有効利用者であってもcan_read、can_editは別々です。ReadCurrentAsyncは許可コードlearning.read、learning.editを既存台帳の列から導出しますが、can_editだけが真でcan_readが偽なら閲覧操作は許可しません。現在の学習順090は判定表示の学習画面であり、全業務サービスへの強制実装が完成したという意味ではありません。

unit_codeは部署単位で対象データを絞る材料です。しかし画面に部署を表示するだけでは行単位認可ではありません。Count、Items、詳細、CSV、集計、更新で同じ対象条件をSQLへ付け、URL直打ちや外部API呼出しでも業務サービスが拒否する必要があります。学習順091〜70でこの処理を実装上の必須入口とします。

## 学習環境と安全性の前提

Windows Server 2025とIISを本番配置先の候補とし、Visual Studio 2026、.NET 10、MudBlazor、EF Core 10、Npgsql、PostgreSQL 18の開発環境で学習します。ここで使うブラウザーとDBは学習用です。実AD・IIS・Kerberos・FDW・一万人超の実機負荷は未受入であり、CIでコードを実行できることと現地の本人認証を通過したことは区別します。既存台帳を権限の正本とし、アプリから利用者を登録・停止解除・権限付与する処理を作りません。

Windows認証の本人確認に使う情報と、業務DBにアクセスしてよいかの判定は違います。サーバーの認証ハンドラーが信頼できる本人情報を作ります。その後、既存台帳からその名前に一致する行を一件だけ取り、利用者が有効か、要求操作が許可されているか、対象行が許可範囲かを確かめます。操作・行単位で都度判定し、本人認証が通っただけではDB一覧やCSVを返しません。

| 比較する対象 | WinForms＋Dapper | Blazor Interactive Server |
| --- | --- | --- |
| 本人の取得 | 端末・プロセスの実行者と操作ユーザーを区別 | 検証済みのClaimsPrincipalを参照 |
| 利用者名 | 画面入力を本人情報と混同しない | DOMAINとユーザー名を認証済み主体から取得 |
| 台帳参照 | WHEREつきのDapperクエリ | DbContextFactoryとAsNoTrackingを使用 |
| 権限 | ボタン非表示だけに依存しない | サーバー側で正本を操作ごとに再評価 |
| 対象行 | 部署条件をSQLに含める | Count・Items・CSV・更新でも同じ行条件 |
| 障害 | DBに問い合わせられなければ許可しない | 未登録・重複・失効・障害を安全に拒否 |

## 操作手順

1. 開発用の構成を選び、本番の人事・業務データベースに接続していないことを確認します。CIで使う架空台帳は本番台帳の代理ではありません。
2. 指定された正規URLをChromeで開き、ページ見出しを読みます。最初は認証と照合の結果を表示する前の状態です。
3. 「現在の認証・既存台帳照合状態を確認」を押します。匿名の開発環境では「Windows認証されていません。業務利用は拒否します。」と表示されることが正しい挙動です。
4. 比較表を読み、Windows端末にサインイン済みであること、Blazorの画面が表示されたこと、業務認可が成立したことを混同しないよう確認します。
5. ブラウザーのNetworkとサーバーのログを照合して、画面操作がサーバーへ到達したか確かめます。エラー時も許可に変えず、既存の拒否文言と原因を区別して記録します。
6. 正規利用者・無効利用者・未登録利用者の検査は隔離された開発DBのfixtureだけを使います。実ADと業務FDWの受入は別工程として残します。

## 障害の切り分け

| 画面の症状 | 確認する原因 | 判定 |
| --- | --- | --- |
| anonymous | Windows認証未成立 | 業務利用を拒否 |
| no-login | 認証スキームや名前の形式不一致 | 補完せず拒否 |
| no-db | PostgreSQLの接続設定なし | 権限を推定せず拒否 |
| unknown | 既存台帳に該当行なし | 自動登録しない |
| ambiguous | 同じ正規化名が二件以上 | 任意の一行を採用しない |
| inactive | is_activeが偽 | 過去の許可を使わない |
| forbidden | can_readが偽 | 閲覧を返さない |
| db-error | SQL・FDW・接続・権限障害 | 古い照合結果を使わない |
| allowed | 現在の有効性と閲覧権限を確認 | 対象行や実操作の認可は別途必要 |

画面へ例外のスタックトレースや接続文字列を表示しない設計にします。運用でログを調べるときもログイン名や秘密の扱いに注意します。ブラウザーが再接続できたという事実だけで権限の復旧を推定しません。失効や取消しが発生したときの扱いは画面状態でなくサーバー側の現在の正本に基づきます。

## 認可を画面表示と混同しない

学習画面に結果が表示されても、学習順047〜60の一覧・CSV・更新が自動で保護されるわけではありません。学習順091〜70では、画面から直接サービスへ到達する経路も含め、実業務の操作単位と行単位の認可を実装します。部署条件が異なる利用者がCountを要求したとき、一覧だけ絞っても件数が漏れるため、SQLのWHEREはCount、Items、詳細、CSV、集計で統一します。編集では権限版とxminを保存直前に確認し、必要な監査に失敗した操作は成功としません。

DB側の読み取り専用ビューはソース上でHasNoKey/ToViewとして設定されています。ただしToViewは本番DBにSELECTだけを自動設定する機能ではありません。実運用ではDB管理者が既存正本との対応、権限、正規化後の一意性を受け入れる必要があります。CI用の一万一件の架空台帳は検索条件の試験用であり、同時接続や実FDWの遅延、Kerberosチケットを検証するものではありません。

## 実Razor・C#・DB照合を読む

WinForms＋DapperでもボタンのEnabled=falseだけに頼らず、DapperのSQL実行前に権限を確認すべきでした。Webでは複数タブや再接続によりUI状態の信頼性がさらに低くなるため、正本への都度照合が必要です。監査不可、権限版の失効、xmin競合、FDW原子性不明は許可を継続する理由になりません。

画面ボタンのイベントからWindowsUserAccessService.ReadCurrentAsyncを呼ぶ流れを追い、画面が受け取るCodeとサーバー側の判定が一致するか確かめます。

```csharp
var permissions = new List<string>();
if (user.CanRead) permissions.Add(ReadPermission);
if (user.CanEdit) permissions.Add("learning.edit");
if (!user.CanRead)
    return new("forbidden", "閲覧権限なし", hint, user.DisplayName,
        Permissions: permissions, UnitCode: user.UnitCode,
        AuthorizationVersion: user.AuthorizationVersion);
```

最初のコードは判定の入口です。サーバー上で認証済み主体と既存台帳の照合を確認し、ブラウザーからの自由な入力を利用者キーへ変換しません。失敗分岐を飛ばして許可を返す実装は安全条件に反します。

```csharp
var snapshot = await userAccess.ReadCurrentAsync(cancellationToken);
if (!snapshot.CanRead || snapshot.Permissions?.Contains("learning.read") != true)
    return Results.Forbid();
// 実業務のデータ照会では unit_code の行範囲条件をさらに適用する。
```

二番目のコードは同じ処理を別の境界から示します。サンプルで省略した条件や後続の更新確認は、利用者の識別・認可・対象行の照合を経てから業務サービスで適用します。

## WinForms＋Dapperとの違いを考える

有効利用者であってもcan_read、can_editは別々です。ReadCurrentAsyncは許可コードlearning.read、learning.editを既存台帳の列から導出しますが、can_editだけが真でcan_readが偽なら閲覧操作は許可しません。現在の学習順090は判定表示の学習画面であり、全業務サービスへの強制実装が完成したという意味ではありません。

WinForms＋DapperでもボタンのEnabled=falseだけに頼らず、DapperのSQL実行前に権限を確認すべきでした。Webでは複数タブや再接続によりUI状態の信頼性がさらに低くなるため、正本への都度照合が必要です。監査不可、権限版の失効、xmin競合、FDW原子性不明は許可を継続する理由になりません。

## 補足：実機とテストを分けて確認する

認証済み利用者を模擬した単体テストは、コードの分岐や入力形式を検査するために必要です。一方で、署名付きCookieの検証、IISでのネゴシエーション、認証要求の転送経路、ドメインコントローラーとの通信は実機で確認します。CIの成功を本番構成の認証保証として書き換えません。業務の秘密情報、ユーザー名、元の台帳データはブラウザー側の自由な入力やログへ露出させないようにします。

クライアントの表示やボタンの可否は補助であり、サーバーのサービスが最終判断します。正本の照合ができなければその場で拒否し、すでに表示済みの画面や永続化されていないキャッシュを権限の根拠に使いません。DB側の一意制約、索引、外部表の検索条件を受け入れた後でも、業務操作の監査・失効・競合を検査するまで正式な許可フローの完成とはしません。

## 演習

**問1。** 有効かつcan_read=true、can_edit=false、unit_code=Aの利用者が部署BのCSVを出せるか説明してください。

**問2。** 権限が過去には有効だったものの、現在は台帳を参照できない状況を想定します。ボタンを押したときに以前の許可を流用できますか。

**問3。** 一覧のSQLだけに部署条件があり、CSVとCountには部署条件がないときに生じる問題を説明してください。

## 詳しい解答

**問1の解答。** 編集権限はないので更新できません。閲覧権限があっても部署Bのデータは対象範囲外ならCSVもCountも取得できません。UI非表示だけでなくサービスの条件とSQLのWHEREで拒否します。

**問2の解答。** 流用できません。本人認証と業務認可を区別し、既存台帳が正本として提供する現在の有効性と操作権限を都度確認します。DB/FDWの照合障害、監査失敗、権限失効、競合では操作を中止し、過去の許可を持ち越しません。

**問3の解答。** 他部署の件数やCSVが漏れるため不適切です。サーバーのサービスで同じ対象行条件を付けて一覧、Count、詳細、CSV、集計、更新を保護します。ボタンを隠すことは認可の代わりになりません。
