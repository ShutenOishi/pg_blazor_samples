# ステップ76：二人の編集競合とxmin

## 到達目標

二つのブラウザーが同じ課題を読み込んだとき、後から保存する側が古い更新版を使って他人の変更を上書きしないことを確認します。Step54の一般的なxmin検査を、Step73〜74の既存台帳ロックと永続監査へ接続します。

## 実際に操作する

1. Windows認証・既存台帳・監査DBの環境がない場合は「更新の認可を確認する」で安全に拒否されることを確認します。
2. 管理者が同一PostgreSQLに置いた**架空課題**とロック可能な台帳で受入を終えた場合だけ、二つのブラウザーで同じ課題IDの「現在の課題とxminを読む」を押します。
3. 一つ目のブラウザーで課題名を編集し、チェックボックスに同意して保存します。
4. 二つ目は古いxminのまま保存し、結果が「競合」であることを確認します。UIは同じ版を再利用せず、再読込を促します。
5. 片方の利用者の編集権限を変更してから保存し、権限失効時の更新拒否も確認します。

## 対応するC#の考え方

画面は取得時のID・xmin・IsDoneをまとめてDTOとして保持し、保存時に本人入力の課題名を渡します。業務サービスのSaveAsyncでは、認可を照会してから**同一トランザクションの中で**台帳行をFOR UPDATEでロックし、対象の部署とxminを再検査して更新・永続監査を一緒にCOMMITします。成功や失敗を問わず画面上の取得済み版を破棄します。

~~~
if (task.Version != input.Version)
    return new(LearningEditStatus.Conflict,
        "別の利用者が更新しました。再読込してください。");
~~~

## 安全に実行するための注意

- 画面は書き込み動作があるため架空データだけを操作します。外部台帳・FDWの原子性が未確認ならAuthorization:TransactionalLedgerConfirmedをtrueにせず更新を拒否します。
- 更新の成功と監査INSERTの成功は同じトランザクションです。監査できないときに更新だけを許しません。
- xminはDB内の更新版であり、利用者の権限そのものではありません。画面を非表示にすることもセキュリティ境界ではありません。
- 楽観排他の競合メッセージは別ユーザーの変更内容を無断で表示しません。

## 確認問題と解答

**Q1. ページを開いたとき編集可なら、保存は必ず許可？** いいえ。保存時の台帳を同一トランザクション内で再確認します。

**Q2. 競合した古いxminのまま再送してよい？** いいえ。最新状態を取得して利用者が変更内容を確認します。

**Q3. 本文と監査を別々のDBへ保存してよい？** 原子性を確保できない場合は同時確定したと主張せず、業務の要件に応じて更新を拒否します。
