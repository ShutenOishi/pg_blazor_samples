# 学習順101：二人の編集競合とxmin

**実装ソース：** [対応するRazor実装](../../src/PgBlazorSamples.Web/Components/Lessons/Stage08/L101ConcurrentEditPage.razor)。画面の正規URLは `/learn/101` です。

**第8段階・第21組／学習順101・正規URL /learn/101**

## 到達目標

二つのブラウザーが同じ課題を読み込んだとき、後から保存する側が古い更新版を使って他人の変更を上書きしないことを確認します。学習順074の一般的なxmin検査を、学習順098〜74の既存台帳ロックと永続監査へ接続します。

## 実際に操作する

1. Windows認証・既存台帳・監査DBの環境がない場合は「更新の認可を確認する」で安全に拒否されることを確認します。
2. 管理者が同一PostgreSQLに置いた**架空課題**とロック可能な台帳で受入を終えた場合だけ、二つのブラウザーで同じ課題IDの「現在の課題とxminを読む」を押します。
3. 一つ目のブラウザーで課題名を編集し、チェックボックスに同意して保存します。
4. 二つ目は古いxminのまま保存し、結果が「競合」であることを確認します。UIは同じ版を再利用せず、再読込を促します。
5. 片方の利用者の編集権限を変更してから保存し、権限失効時の更新拒否も確認します。

## 対応するC#の考え方

画面は取得時のID・xmin・IsDoneをまとめてDTOとして保持し、保存時に本人入力の課題名を渡します。業務サービスのSaveAsyncでは、認可を照会してから**同一トランザクションの中で**台帳行をFOR UPDATEでロックし、対象の部署とxminを再検査して更新・永続監査を一緒にCOMMITします。成功や失敗を問わず画面上の取得済み版を破棄します。

~~~
if (task.Version != input.Version)
    return new(LearningEditStatus.Conflict,
        "別の利用者が更新しました。再読込してください。");
~~~

## 安全に実行するための注意

- 画面は書き込み動作があるため架空データだけを操作します。外部台帳・FDWの原子性が未確認ならAuthorization:TransactionalLedgerConfirmedをtrueにせず更新を拒否します。
- 更新の成功と監査INSERTの成功は同じトランザクションです。監査できないときに更新だけを許しません。
- xminはDB内の更新版であり、利用者の権限そのものではありません。画面を非表示にすることもセキュリティ境界ではありません。
- 楽観排他の競合メッセージは別ユーザーの変更内容を無断で表示しません。

## 確認問題と解答

**Q1. ページを開いたとき編集可なら、保存は必ず許可？** いいえ。保存時の台帳を同一トランザクション内で再確認します。

**Q2. 競合した古いxminのまま再送してよい？** いいえ。最新状態を取得して利用者が変更内容を確認します。

**Q3. 本文と監査を別々のDBへ保存してよい？** 原子性を確保できない場合は同時確定したと主張せず、業務の要件に応じて更新を拒否します。

## 実装・運用の詳しい検証

この教材はWinForms＋Dapper経験者が、Blazor Interactive Serverのサーバー側処理と既存業務DBの境界を理解するためのものです。ADは本人を認証し信頼済みのドメイン付きログイン名を取得します。業務の閲覧・編集、部署・行単位の認可は既存DB台帳を操作ごとに照合します。Cookieやcircuitの保持値、画面に表示されたボタンだけでは業務権限を証明できません。

### 実コード例1：画面の入口

```csharp
var result = await Business.SaveAsync(new LearningEditInput { Id = item.Id, Version = item.Version, Title = _title, IsDone = item.IsDone });
_message = result.Message;
_snapshot = null; _confirm = false;
```


この抜粋は、実際の呼出し経路を追うためのものです。画面で実行するC#は業務サービスを呼ぶ入口にすぎません。認可を通ったように見えても、対象行の部署、現在の権限、監査書込みを確認できなければ結果を公開しません。特に非同期操作をキャンセルした場合やDBから例外が返った場合、古い許可に戻して成功にする処理を追加しないでください。

### 実コード例2：安全な境界の確認

```csharp
var rows = await db.ExistingUserAccess.FromSqlInterpolated($"SELECT * FROM learning_user_access_v WHERE login_name = {login} FOR UPDATE").AsNoTracking().Take(2).ToListAsync(ct);
bool allowed = rows.Count == 1 && rows[0].IsActive && rows[0].CanRead && rows[0].CanEdit && rows[0].UnitCode == unit;
```

### 実装と判断の詳しい説明

二つのブラウザーが同じ架空課題のIDとxminを読み、Aが先に保存すると、Bは古いxminでの保存が競合になります。Razorは成否にかかわらず取得したスナップショットを破棄します。保存前の権限と台帳行をFOR UPDATEでロックし、本人の部署、対象行の部署、編集権限、xminを同じDBトランザクションで再確認します。既存正本がFDWで同等の行ロックを保証できない場合、更新を拒否します。監査INSERTが失敗した場合は更新だけ確定してはいけません。

### WinForms＋Dapperとの比較

| 観点 | WinForms＋Dapper | Blazor Interactive Server |
| --- | --- | --- |
| 操作イベント | 各端末のFormで受け付ける | サーバーのRazorとサービスで処理する |
| 権限の正本 | Dapperで既存DBへ毎回照会する | SecuredLearningServiceで操作・行単位を都度判定する |
| 表示状態 | フォーム内の値は古くなり得る | circuitの状態も権限の代わりにならない |
| 監査 | SQLの実行結果と本人・操作を記録 | 永続監査に失敗する場合は業務を安全に拒否 |
| 本番受入 | Windows端末とDB接続を確認 | IIS、Kerberos、SignalR、DBプールと鍵の管理を別途確認 |

### 操作手順

1. 新学習順の目次から正規URLで画面を表示し、前後リンクを確認します。
2. 匿名の開発用ブラウザーで業務の確認ボタンを押し、本人とDB台帳の権限が確かめられないときに拒否されることを確認します。

4. 操作前後の期待結果、実際の画面表示、相関ID、実行日時、コミットSHAを記録します。再操作時もDB正本を確認します。
5. 実AD/IIS/Kerberos/FDWおよび1万人超負荷は、CIとは別に現地で受入票を作ります。

### 障害の切り分け

| 現象 | 最初に確かめる内容 | 合格条件 |
| --- | --- | --- |
| 匿名・台帳未登録・重複 | 認証ハンドラー、ドメイン付き名、照合の0/1/2件 | データを返さず拒否 |
| 権限変更・部署違い | 正本の有効状態、can_read/can_edit、部署 | 過去の許可を再利用しない |
| 競合・行ロック不可 | xmin、トランザクション、FDW条件 | 古いデータを自動上書きしない |
| 監査INSERT・DB障害 | 監査権限、接続、相関ID、ロールバック | 機密の行やCSVを公開しない |
| CI成功・実機未検証 | IIS、SPN、Kerberos、FDW、復旧と負荷 | 現地受入は未完了のままにする |

利用者へSQLエラー、認証Cookie、接続文字列、他部署のデータを表示しません。運用ログは利用者画面と切り分けて保護します。権限失効は再ログインだけで直す問題と決めつけず、現在の正本を確かめます。成功、拒否、競合、通信障害を別の結果として記録してください。

### 演習

A/Bの双方が版10を取得し、Aが更新して版11となった後Bが保存する。さらにBの編集権限を剥奪した場合、正しい結果は何か。

### 詳しい解答

Bの版10は競合のため自動上書きされず、Bに再読込と変更内容の確認を求めます。can_editが失効していれば最新版でも更新を拒否します。監査不能なら同時確定できずロールバックします。

### 現場での確認票

WinForms＋Dapperから移行しても認可の根拠は変わりません。本人を確かめたことと、その本人がどの行へどの操作をできるかを分け、監査が不能な場合は安全に拒否します。設定フラグだけで行ロックや監査の原子性が保証されるわけではありません。実AD、IIS、Kerberos、FDW、鍵の管理、1万人超登録アカウントと同時circuit、DBプールの負荷、復旧手順は現地実機で受入します。CI成功の意味を超えて運用を承認しないでください。
