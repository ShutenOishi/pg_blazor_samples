## 学習目標と実行環境

WinForms＋Dapperで開発してきた学習者が、初めてWebのBlazor Interactive Serverで操作する想定です。Visual Studio 2026、.NET 10、MudBlazor、EF Core 10、Npgsql、開発用PostgreSQL18を前提にします。今回の主題はScopedキャッシュと権限版です。ブラウザーの入力とWebサーバーのC#、SQLが実行されるPostgreSQLの責任を切り分け、サーバー側の結果だけを根拠に表示を更新します。操作を繰り返す場合の二重送信、回線切断、取消も設計に含めます。

## 実Razor/C#/SQLでの処理を追う

LearningCacheLessonServiceの辞書キーは架空利用者A/Bと整数の権限版の組です。A・版1を二回読むと二回目はCacheHitですが、B・版1やA・版2は別のキーです。項目は固定文字列の架空データで、DBからの認可済み業務行ではありません。画面でA/Bを選択することと本人認証は全く別の動作です。

Blazor Interactive ServerのScopedは通常のHTTPリクエスト1回の寿命ではなくcircuit内で保持されます。同じcircuit内でキャッシュがヒットする理由を説明してください。権限版を増やすボタンは表示行を空にし、以後新しい版のキーを使うだけです。古い辞書項目が物理的に削除されたわけではありません。Clear()が辞書全体を削除します。

実業務の権限失効にこの版番号デモは使えません。ADは本人とユーザー名を識別し、既存DB/外部台帳の有効利用者・部署・操作・対象行をサービスで都度認可します。機密の業務行をキャッシュするときは失効通知、寿命、利用者ごとの分離、複数サーバーの整合、再接続の扱いを含めて安全性を実証しなければなりません。

サービスと画面を照合するときは、UIの成功表示から逆方向に追うのではなく、入力値を受けた順に確認してください。Razorのイベントハンドラー、サービスが検査する境界値、IDbContextFactoryで生成する短命DbContext、DBへ送信する絞り込み、返却するDTO、画面の状態メッセージを記録します。複数の利用者が同時にアクセスできるWebでは、ブラウザー側の状態を業務上の正本と扱わず、サーバーで必要な検証を繰り返します。

LearningCacheLessonServiceの辞書キーは架空利用者A/Bと整数の権限版の組です。A・版1を二回読むと二回目はCacheHitですが、B・版1やA・版2は別のキーです。項目は固定文字列の架空データで、DBからの認可済み業務行ではありません。画面でA/Bを選択することと本人認証は全く別の動作です。

同じ画面を別タブで開いて操作した場合、古い結果や取得済みの項目が残ることがあります。操作を続ける前に対象データの状態を確認します。Web画面を正しく描画できたこと、データを読み込めたこと、権限を持つこと、更新が確定したことを同じ成功条件にまとめないでください。エラー表示の文面だけを見ず、サービスの戻り値とログを照合します。

## 実コード例1：Scopedキャッシュと権限版の主要処理

```csharp
private readonly Dictionary<(string Actor, int PermissionVersion),
    IReadOnlyList<string>> _cache = new();
var key = (actor, permissionVersion);
if (_cache.TryGetValue(key, out var rows)) return (rows, true);
rows = Items.Where(x => x == "共通の連絡" || x.Contains("部署" + actor)).ToArray();
_cache[key] = rows;
return (rows, false);
```

上のコードは既存サービス／Razorの処理を学習用に抜き出しています。入力検査は画面で一回行えば足りるものではなく、サービス側でも拒否条件を再確認します。UIの値が正しい形式でもアクセスしてよい対象とは限りません。実業務では行・操作の認可をDB台帳で検査する処理を別途実装する必要があります。

| 症状と否定試験 | 確認する箇所 | 適切な判断 |
| --- | --- | --- |

## 演習と詳しい解答

**演習1：** A・版1を二回、B・版1を一回、A・版2を一回読むと、どれがキャッシュヒットですか。版変更で旧エントリは削除されますか。

**詳しい解答1：** 同じcircuitのA・版1の二回目だけがヒットします。B・版1とA・版2は別キーで新規格納されます。版変更で辞書の旧項目を削除する処理はありません。Clearで辞書を破棄します。これは本番業務認可や失効を保証しません。

**演習2：** この学習用の画面から正常な結果が得られたことを理由に、実業務でのAD本人認証、既存台帳による行認可、監査まで実装済みと判断してよいでしょうか。

**詳しい解答2：** 判断できません。ADは本人とユーザー名を確認し、業務操作の許可と対象行の可視性は既存DB/外部台帳で都度判定します。Count、Items、詳細、CSV、更新の各経路を通じて同じ権限条件を強制します。更新前に権限・xminを再検証し、監査に失敗した場合やFDWの原子性が不明な場合は安全拒否します。ボタンが非表示であることは権限がないことの証明にも、権限があることの証明にもなりません。

## 本番業務への適用前に必要な判断

これは開発用の架空データを使う学習画面です。認証済みのADユーザー名を得ることと業務上の行・操作の許可を得ることは別です。利用者登録用の新しい表を勝手に作って認可の正本にせず、既存DBまたは外部台帳の有効利用者・操作権限・対象行をサービス側で都度照合します。表示・Count・詳細・CSV・更新で同じ権限条件を適用します。権限失効、xmin競合、監査の永続化失敗、FDWや別DBの原子性が証明できない場合は安全拒否します。画面のボタン非表示やフィルターは認可ではありません。

Windows Server 2025/IIS、実AD/Kerberos/SPN、証明書・鍵共有、接続切断、FDWの原子性、監査永続化、1万人超の実機負荷の受入は開発用CIとは別です。PostgreSQL18、xUnit、Chromeが成功しても現地の運用条件を満たすとは限りません。例外時に成功を返さない設計と、失敗を追跡できるログを保持し、機密データを学習用のログやキャッシュへ残さないことも確認します。
