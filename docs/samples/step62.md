# ステップ62：認証済みドメインユーザー名

## 到達目標

AuthenticationStateProviderから取得した認証済みPrincipalのDOMAIN\\userを既存台帳のキーに合わせる。 Visual Studio 2026・.NET 10・MudBlazor・EF Core 10・PostgreSQL 18を前提にします。

## 画面で操作する

1. ステップ62のページを開き、「現在の認証・既存台帳照合状態を確認」を実行する。
2. CIの匿名環境では**Windows認証されていません**と拒否されることを確認する。
3. 認証成功時にはユーザー名だけが既存DB台帳の読み取りへ進むことを説明する。

## ソースコードを読む

- 認証ハンドラーが確定した本人はAuthenticationStateProviderのClaimsPrincipalとして参照する。
- WindowsUserAccessService.ReadTrustedLoginNameは**サーバー側で認証済みのDOMAIN\\user**だけを使用する。入力欄・URL・HTTPヘッダーの名前は使わない。
- EF Core 10のLearningDbContextにはキーなし・読み取り専用のlearning_user_access_vを登録する。
- DbContextFactoryから操作単位で短命DbContextを取得し、単一ログイン名で最大2件だけ検索する。該当0件、重複2件以上は拒否する。
- 認可判断は既存台帳のis_active、can_read、can_editを用い、部署などの対象データ範囲はStep67で適用する。

## 想定する失敗と安全な扱い

ログイン名の変更・再使用と別ドメインの同名を考慮する。UPNへの変換は仕様なしに行わない。 SQLや外部テーブルが利用不可の場合も拒否します。

本サンプルのdatabase/schema/002_app_access.sqlは**CI専用の1万1人の架空台帳**です。業務環境で利用者を登録したり、ビュー名をそのまま本番の権限源として使うものではありません。実際の列名はDB管理者が既存の正本から読み取り専用ビューに射影します。

**Step66〜70の業務サービス認可完成前は開発用DB以外に接続しないでください。**

## 確認問題

**Q. Windowsでログイン済みなら全業務を利用してよい？**

A. いいえ。既存台帳の該当行・有効状態・業務別権限・対象データの条件をサーバーで確認する必要があります。

## 演習

1. 匿名・不正なユーザー名・既存台帳にない名前は拒否されることを説明する。
2. ドメインを省略したユーザー名にする危険性を説明する。
3. ログイン名の変更・再使用と別ドメインの同名を考慮する。UPNへの変換は仕様なしに行わない。
