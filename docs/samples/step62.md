# ステップ62：ドメイン付きユーザー名の安全な取得

## できるようになること

Windows利用者の安定キーを識別する。Visual Studio 2026、.NET 10、Blazor Interactive Server、PostgreSQL 18、EF Core 10を前提にします。

## 画面で確認する

1. ステップ62を開き「現在の認証・DB照合状態を確認」を実行する。
2. Windows認証を使わない開発環境では匿名として**拒否**されることを確認する。
3. 取得した状態と、認証・業務認可の違いを説明する。

## ソースコードのポイント

利用者名は変更されるためDB照合キーにしません。認証済み主体のPrimarySidまたはWindowsIdentity.Userを検証します。

- WindowsUserAccessService.ReadCurrentAsyncはAuthenticationStateProviderから**サーバーが認証した**ClaimsPrincipalを取得します。
- ドメイン付きユーザー名は表示用に末尾4文字へマスクし、利用者の認証情報をログへ出しません。
- DB照合はDbContextFactoryから操作ごとに作る短命DbContextで行い、未登録・無効・権限不足は許可しません。
- DB接続不良・定義不整合はフェイルクローズします。UIから渡されたドメイン付きユーザー名は使用しません。

## 実務上の境界

画面入力のドメイン付きユーザー名やX-Userヘッダーは決して信用せず、ドメイン付きユーザー名欠落は拒否します。

DBの既存テーブルまたは外部テーブルを投影した learning_user_access_vは認可構造の教材です。利用者登録をこの画面からは行いません。

**注意：Step61〜65は認証とDB照合の骨格です。既存の一覧・更新・CSVへのサービス側認可はStep66〜70で適用します。実データへ接続しないでください。**

## 確認問題と答え

**Q. 認証された利用者名だけで権限を判断してよい？**

**A. いいえ。** 信頼できるドメイン付きユーザー名でDB登録・有効性・権限を判定し、DB障害や未登録は拒否します。

## 自分で試す演習

1. 匿名の拒否結果を確認する。
2. ドメイン付きユーザー名が使えないときに名前へフォールバックしてはいけない理由を説明する。
3. 有効な利用者でも閲覧権限がない場合の結果を確認する。
