## 実Razor/C#/SQLでの処理を追う

CountByDoneAsyncはAsNoTracking、GroupBy(t => t.IsDone)、CountをSQLへ渡し、グループごとの件数だけを受け取ります。すべてのEntityをToListしてからメモリで集計する方式ではありません。DBのGROUP BYを使う場合でも、実業務では集計する元行の認可条件を適用し、未許可の部署の件数が漏れるのを防ぎます。

ExportSmallCsvAsyncは検索語の長さが100文字を超えれば拒否します。条件に一致する行をId順でTake(101)し、101件目があればCSVを一切生成せずBase64=nullで返します。100件だけ出して「全件」と説明する誤りを避けます。件数超過時に得られた101は総件数の確定値ではありません。大量データの出力は別の認可済み経路に分けます。

CSVにはUTF-8 BOM、CRLF、二重引用符と引用符内のエスケープを使用します。Excel系の式注入を防ぐため、先頭の=,+,-,@や制御文字をEscapeCsvで確認します。Razorでは生成前に以前のダウンロードリンクを消し、成功時のみ小さなdata URLを表示します。DB未設定・例外時に古いファイルを新しい成功として見せないでください。

サービスと画面を照合するときは、UIの成功表示から逆方向に追うのではなく、入力値を受けた順に確認してください。Razorのイベントハンドラー、サービスが検査する境界値、IDbContextFactoryで生成する短命DbContext、DBへ送信する絞り込み、返却するDTO、画面の状態メッセージを記録します。複数の利用者が同時にアクセスできるWebでは、ブラウザー側の状態を業務上の正本と扱わず、サーバーで必要な検証を繰り返します。

CountByDoneAsyncはAsNoTracking、GroupBy(t => t.IsDone)、CountをSQLへ渡し、グループごとの件数だけを受け取ります。すべてのEntityをToListしてからメモリで集計する方式ではありません。DBのGROUP BYを使う場合でも、実業務では集計する元行の認可条件を適用し、未許可の部署の件数が漏れるのを防ぎます。

同じ画面を別タブで開いて操作した場合、古い結果や取得済みの項目が残ることがあります。操作を続ける前に対象データの状態を確認します。Web画面を正しく描画できたこと、データを読み込めたこと、権限を持つこと、更新が確定したことを同じ成功条件にまとめないでください。エラー表示の文面だけを見ず、サービスの戻り値とログを照合します。

## 実コード例1：GroupBy/Count・101行目の拒否の主要処理

```csharp
var grouped = await db.Tasks.AsNoTracking().GroupBy(t => t.IsDone)
    .Select(g => new { Status = g.Key, Total = g.Count() })
    .ToListAsync(ct);
var rows = grouped.OrderBy(x => x.Status)
    .Select(x => new LearningCountRow(x.Status, x.Total)).ToArray();
```

上のコードは既存サービス／Razorの処理を学習用に抜き出しています。入力検査は画面で一回行えば足りるものではなく、サービス側でも拒否条件を再確認します。UIの値が正しい形式でもアクセスしてよい対象とは限りません。実業務では行・操作の認可をDB台帳で検査する処理を別途実装する必要があります。

## 障害の切り分け

| 症状と否定試験 | 確認する箇所 | 適切な判断 |
| --- | --- | --- |
| 検索語が101文字 | 入力と形式検査 | 原因を切り分け成功と拒否を区別する |
| CSVが100件 | Razorが保持する状態 | 原因を切り分け成功と拒否を区別する |
| CSVが101件以上 | サービスの事前条件 | 原因を切り分け成功と拒否を区別する |
| セルが=1+1で始まる | LINQとSQLのWHERE・件数 | 原因を切り分け成功と拒否を区別する |
| 引用符を含むタイトル | キャッシュ・版・索引・接続 | 原因を切り分け成功と拒否を区別する |
| DB未設定で以前のCSVリンクが残る | 障害ログと利用者への応答 | 原因を切り分け成功と拒否を区別する |
| 学習用DBが未設定 | LearningDbService.Configured | NotConfiguredを成功とみなさない |
| DB接続に失敗 | サービスの警告ログと結果 | 空結果として隠さず失敗を表示 |

診断は画面の文字だけで結論を出さず、サービスの正常系・拒否系を分けて調査します。互換URLを維持した状態でも、データ・アクセス権・通信状況が変わると同じ操作の結果が変わります。失敗した操作を無条件で再試行すると二重更新や古い表示の問題を引き起こすため、DBで確定した内容を確認してから復旧を判断します。

## 演習と詳しい解答

**演習1：** 101件一致した検索で100件分だけCSVを返してよいでしょうか。=1+1で始まるタイトルの扱いも答えてください。

**詳しい解答1：** 101件目が存在した場合はCSVを生成せず拒否します。部分出力を全件と呼ぶことはできません。=から始まるタイトルはEscapeCsvで式注入対策を行い、引用符付きCSVセルにします。大規模・機密データの出力には専用の認可と監査が必要です。

**演習2：** この学習用の画面から正常な結果が得られたことを理由に、実業務でのAD本人認証、既存台帳による行認可、監査まで実装済みと判断してよいでしょうか。

**詳しい解答2：** 判断できません。ADは本人とユーザー名を確認し、業務操作の許可と対象行の可視性は既存DB/外部台帳で都度判定します。Count、Items、詳細、CSV、更新の各経路を通じて同じ権限条件を強制します。更新前に権限・xminを再検証し、監査に失敗した場合やFDWの原子性が不明な場合は安全拒否します。ボタンが非表示であることは権限がないことの証明にも、権限があることの証明にもなりません。

## 本番業務への適用前に必要な判断

これは開発用の架空データを使う学習画面です。認証済みのADユーザー名を得ることと業務上の行・操作の許可を得ることは別です。利用者登録用の新しい表を勝手に作って認可の正本にせず、既存DBまたは外部台帳の有効利用者・操作権限・対象行をサービス側で都度照合します。表示・Count・詳細・CSV・更新で同じ権限条件を適用します。権限失効、xmin競合、監査の永続化失敗、FDWや別DBの原子性が証明できない場合は安全拒否します。画面のボタン非表示やフィルターは認可ではありません。

Windows Server 2025/IIS、実AD/Kerberos/SPN、証明書・鍵共有、接続切断、FDWの原子性、監査永続化、1万人超の実機負荷の受入は開発用CIとは別です。PostgreSQL18、xUnit、Chromeが成功しても現地の運用条件を満たすとは限りません。例外時に成功を返さない設計と、失敗を追跡できるログを保持し、機密データを学習用のログやキャッシュへ残さないことも確認します。
