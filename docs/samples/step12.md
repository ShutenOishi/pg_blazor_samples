# 学習順022：インターフェイスで部品を交換する

**実装ソース：** [対応するRazor実装](../../src/PgBlazorSamples.Web/Components/Lessons/Stage03/L022InterfaceClockPage.razor)。画面の正規URLは `/learn/022` です。

## 学習の目的と対象

前の第2段階で学習したRazorイベント、コンポーネントとcircuitを前提に、インターフェイスで部品を交換するを実際に操作しながら理解します。Visual Studio 2026と.NET 10のInteractive Serverアプリを起動し、ブラウザーで`/learn/022`を開いてください。DB接続・実AD認証・IISの現地構築は不要です。最後には設計上の理由をWinForms＋Dapperとの違いを含めて説明し、失敗の切り分けと演習解答まで実施します。

## まず観察すること

IClockはGetNowという操作の約束で、SystemClockは実際のサーバー時刻、FixedClockはUTC+09:00の2026年1月1日午前8時を返します。どちらもGreetingServiceに渡せるのは同じ契約を実装するからです。この画面のuseFixedは選択状態であり、SelectedClockはその場で二つの注入済み時計から一つを選びます。DI登録そのものはボタンで変更されません。

「固定時計（午前8時）」を操作したときは、操作前後の表示だけを比べるのではなく、サーバーのC#が何を実行したのかをコードと照合してください。ブラウザーは結果を表示し、入力やクリックを通知します。サービスのメソッドはサーバー側で動き、ブラウザー内のJavaScriptがC#のクラスを生成するわけではありません。回線が不安定で結果が更新されなかった場合も、登録、サーバー例外、接続を分けて確認します。

## WinForms＋Dapperと比較する

WinForms＋DapperでIRepositoryを作り、試験版と実DB版を選ぶのに似ています。ただし画面例はあえてnew GreetingService(SelectedClock)としており、アプリ全体のDI構成切替を実装した例ではありません。時刻を選ぶUIは認証済みユーザーの権限を選ぶ仕組みではありません。

| 観点 | WinFormsでの考え方 | 今回のBlazor画面 |
| --- | --- | --- |
| 画面と処理 | Formのイベント処理でC#を実行 | Razorの入力をサーバー側C#へ届ける |
| 部品を作る場所 | newやコンストラクターで用意 | Program.cs登録と注入で責任を分ける |
| 表示を変える方法 | プロパティ代入や画面更新 | Razorの状態とレンダリング |
| DBアクセス | Dapperを明示的に呼び出す | この課題はDBへアクセスしない |
| 本人認可 | 個別業務処理で判定 | この画面は権限判定の実例ではない |

## ソースを読んで動作を理解する

次の実コード抜粋は今回のRazor画面、Program.cs、または対応するサービスの実装と同じ型・処理を示します。掲載順は依存先、利用箇所、実行順を理解しやすくするために整理しました。見出し、見た目のスタイルなどは省略しています。サンプルにないDB保存や認証処理を実装済みとして解釈しないでください。

```csharp
public interface IClock
{
    DateTimeOffset GetNow();
}

public sealed class SystemClock : IClock
{
    public DateTimeOffset GetNow() => DateTimeOffset.Now;
}

public sealed class FixedClock : IClock
{
    public DateTimeOffset GetNow() =>
        new(2026, 1, 1, 8, 0, 0, TimeSpan.FromHours(9));
}

public sealed class GreetingService(IClock clock)
{
    public string GetMessage() => clock.GetNow().Hour < 12
        ? "おはようございます"
        : "こんにちは";
}
```

```csharp
builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddSingleton<FixedClock>();
builder.Services.AddTransient<GreetingService>();
```

```razor
@page "/learn/022"
@inject IClock SystemClock
@inject FixedClock FixedClock

<button @onclick="() => useFixed = false">実際の時計</button>
<button @onclick="() => useFixed = true">固定時計（午前8時）</button>
<p>選択中：@(useFixed ? "固定時計" : "実際の時計")</p>
<p>取得した時刻：@SelectedClock.GetNow().ToString("yyyy/MM/dd HH:mm")</p>
<p>挨拶：@(new GreetingService(SelectedClock).GetMessage())</p>

@code {
    private bool useFixed;
    private IClock SelectedClock => useFixed ? FixedClock : SystemClock;
}
```

### イベントから描画まで

1. `/learn/022`を開くと、Blazorがページを表示します。事前レンダリングがある構成では、静的HTMLの生成と対話用コンポーネントの生成を区別します。
2. 必要な依存先はProgram.csのサービス登録に従って渡されます。この段階で登録が足りなければ、イベント処理以前にサービス解決が失敗する場合があります。
3. 「固定時計（午前8時）」を操作すると、対話可能な状態であればイベントがサーバーへ届きます。C#のイベント処理が画面状態やサービスを変更します。
4. Razorは新しい値を評価し、変更された表示をブラウザーに反映します。再描画が発生しただけで全サービスが新規作成されたわけではありません。
5. 必要に応じて再操作・別ウィンドウで観察しますが、異なる結果を得たらタイミング、接続、プロセス再起動の有無を先に比較します。

## 対象の理解を深める

このテーマで最初に確かめるべきなのは`IClock`の役割です。C#やRazorの記法を一度覚えるだけでは、なぜ実装を分離しているか判断できません。サービスを登録するときは、型、依存する型、ライフタイムの三つを確認します。画面がサービスを受け取るときは、それを作る責任が画面に残っていないか確認します。結果を表示するときは、計算をどこで実行し、表示の更新がいつ通知されたかを確認します。

たとえば、WinFormsの画面に複数のDapperクエリを書いたまま、画面をRazorへ移すだけでは保守しやすい構成になりません。一覧検索、保存、認可、監査の処理をサービス側へ分けたとしても、依存サービスの寿命や失効への対応を設計しないと、Webで複数利用者が同時に操作するときに不具合が起こります。この段階では小さな時計とカウンターを使い、複雑な業務データを持ち込む前に生成と共有の仕組みを確認します。

### サーバー、circuit、DBの境界

サービスの解決と業務データの保存は独立しています。Interactive Serverでは、接続が再確立して以前と同じcircuitが維持される場合と、新しく作られる場合があります。Scopedの値が残ったかどうかだけでDBの永続性を評価できません。ブラウザーが表示したユーザー名や部署番号も業務認可の正本になりません。今後扱う業務処理では、信頼できる認証機構で本人を確認し、事前整備済みDB台帳または外部ビューの権限を操作ごとに確認します。監査の成功を保証できない更新は拒否します。

### 設計上の判断を文章にする

このサンプルで共有が必要な値は何か、コンポーネント内だけで完結する値は何か、DIへ登録する理由は何かを説明してみてください。インスタンス識別子や固定時計などの教材用データを実業務の利用者情報と混同してはいけません。重要な点は、画面を表示できたという事実から、本人認証・監査・DB保存まで受け入れたと判断しないことです。

## 操作手順と再現条件

1. 初期画面の文字列と数値を記録します。起動直後か同じタブの再訪問かを書き分けます。
2. 「固定時計（午前8時）」を実行し、表示が期待通りか確認します。操作で変わるのは何か、変わらないのは何かを説明します。
3. もう一度操作し、結果が同じ場合も失敗と即断せず、今回のサービスやイベントの条件式を調べます。
4. 可能であればプライベートウィンドウを用意して同じURLを開きます。異なる回線の影響を観察します。
5. 結果が想定と異なる場合は次の症状別の表を使います。Visual Studioの例外とサーバーログを優先し、必要ならブラウザーのNetwork/Consoleも調べます。

## 症状別の切り分け

| 症状 | 考えられる原因 | 調べる場所と対処 |
| --- | --- | --- |
| 固定時計にしても時刻が違う | useFixedの選択が変わっていない | 選択中の表示とSelectedClockを確認 |
| DI解決で失敗する | FixedClockの具象登録不足 | AddSingleton<FixedClock>の登録確認 |
| GreetingServiceが差し替わらない | 注入済みサービスは自動交換しない | 選択した時計でnewしている箇所を読む |

ブラウザーからクリックしただけでは、サーバーに例外が生じていないことまでは分かりません。サーバーログはC#サービス、ブラウザーConsoleはJavaScript、Networkは接続の観測に使います。未登録の型が原因なら、再読込だけでは直りません。反対に、表示内容が同じという観測だけではDI失敗を意味しません。問題の発生した処理段階を区別するのが切り分けの基本です。

## 演習と詳しい解答

**演習1：FixedClockを15時に変更したら。**

**解答1：** 時刻は15:00で、GreetingServiceの条件式は午後として『こんにちは』を返します。 説明した結果がどのコード行から生じるか、実装と照合します。

**演習2：IClockの利点は。**

**解答2：** 呼び出し元が時計の具象型に依存せず、同じGetNowで複数実装を使えます。 説明した結果がどのコード行から生じるか、実装と照合します。

**演習3：IClockを二つ登録したらどうなる。**

**解答3：** 単一サービス取得とIEnumerableの取得で登録の使われ方が異なるため、どの型で解決するか明確に設計します。 説明した結果がどのコード行から生じるか、実装と照合します。

## さらに確認する課題

次に、サービスの登録だけを変えた場合に、コンポーネントを修正しなくてもどこまで結果を変更できるか考えてください。設定を変更しただけで自動的に既存オブジェクトが入れ替わるとは限らず、利用中のインスタンスの寿命を考える必要があります。画面のコンストラクターと普通のC#クラスのコンストラクターを見比べ、どちらが依存先を決めているか説明してください。実装を大きな階層のプロジェクトへ分ける必要はありません。今はWebプロジェクトと小さなサービスで役割を説明できれば十分です。
