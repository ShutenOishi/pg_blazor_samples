# 学習順025：injectとコンストラクター注入

**実装ソース：** [対応するRazor実装](../../src/PgBlazorSamples.Web/Components/Lessons/Stage03/L025InjectionPatternsPage.razor)。画面の正規URLは `/learn/025` です。

## 学習の目的と対象

前の第2段階で学習したRazorイベント、コンポーネントとcircuitを前提に、injectとコンストラクター注入を実際に操作しながら理解します。Visual Studio 2026と.NET 10のInteractive Serverアプリを起動し、ブラウザーで`/learn/025`を開いてください。DB接続・実AD認証・IISの現地構築は不要です。最後には設計上の理由をWinForms＋Dapperとの違いを含めて説明し、失敗の切り分けと演習解答まで実施します。

## まず観察すること

Razor画面は@inject GreetingFormatter Formatterで依存先を受け取ります。GreetingFormatterはプライマリコンストラクターでGreetingServiceを受け取り、GreetingServiceはIClockを受け取ります。Program.csに三つの登録があるのでDIが連鎖を解決できます。inputの@bind:event="oninput"は入力ごとにlearnerNameを更新しFormatter.Formatで挨拶を表示しますが、文字入力のたびに必ずサービスを生成し直すわけではありません。

「練習用の名前」を操作したときは、操作前後の表示だけを比べるのではなく、サーバーのC#が何を実行したのかをコードと照合してください。ブラウザーは結果を表示し、入力やクリックを通知します。サービスのメソッドはサーバー側で動き、ブラウザー内のJavaScriptがC#のクラスを生成するわけではありません。回線が不安定で結果が更新されなかった場合も、登録、サーバー例外、接続を分けて確認します。

## WinForms＋Dapperと比較する

WinFormsでFormのコンストラクターからサービスを受け取る設計と共通点があります。通常のC#クラスではコンストラクター注入、Razorでは@injectが読みやすい基本です。Dapperの接続・SQL実行は別のサービスへ配置できても、認可や監査はサービスの処理として明示する必要があります。

| 観点 | WinFormsでの考え方 | 今回のBlazor画面 |
| --- | --- | --- |
| 画面と処理 | Formのイベント処理でC#を実行 | Razorの入力をサーバー側C#へ届ける |
| 部品を作る場所 | newやコンストラクターで用意 | Program.cs登録と注入で責任を分ける |
| 表示を変える方法 | プロパティ代入や画面更新 | Razorの状態とレンダリング |
| DBアクセス | Dapperを明示的に呼び出す | この課題はDBへアクセスしない |
| 本人認可 | 個別業務処理で判定 | この画面は権限判定の実例ではない |

## ソースを読んで動作を理解する

次の実コード抜粋は今回のRazor画面、Program.cs、または対応するサービスの実装と同じ型・処理を示します。掲載順は依存先、利用箇所、実行順を理解しやすくするために整理しました。見出し、見た目のスタイルなどは省略しています。サンプルにないDB保存や認証処理を実装済みとして解釈しないでください。

```csharp
public sealed class GreetingService(IClock clock)
{
    public string GetMessage() => clock.GetNow().Hour < 12
        ? "おはようございます"
        : "こんにちは";
}

public sealed class GreetingFormatter(GreetingService greeting)
{
    public string Format(string name)
        => $"{name}さん、{greeting.GetMessage()}。";
}
```

```csharp
builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddTransient<GreetingService>();
builder.Services.AddTransient<GreetingFormatter>();
```

```razor
@page "/learn/025"
@inject GreetingFormatter Formatter

<label for="learner-name">練習用の名前</label>
<input id="learner-name" maxlength="20"
       @bind="learnerName" @bind:event="oninput" />
<p role="status">@Formatter.Format(learnerName)</p>

@code {
    private string learnerName = "練習太郎";
}
```

### イベントから描画まで

1. `/learn/025`を開くと、Blazorがページを表示します。事前レンダリングがある構成では、静的HTMLの生成と対話用コンポーネントの生成を区別します。
2. 必要な依存先はProgram.csのサービス登録に従って渡されます。この段階で登録が足りなければ、イベント処理以前にサービス解決が失敗する場合があります。
3. 「練習用の名前」を操作すると、対話可能な状態であればイベントがサーバーへ届きます。C#のイベント処理が画面状態やサービスを変更します。
4. Razorは新しい値を評価し、変更された表示をブラウザーに反映します。再描画が発生しただけで全サービスが新規作成されたわけではありません。
5. 必要に応じて再操作・別ウィンドウで観察しますが、異なる結果を得たらタイミング、接続、プロセス再起動の有無を先に比較します。

## 対象の理解を深める

このテーマで最初に確かめるべきなのは`GreetingFormatter`の役割です。C#やRazorの記法を一度覚えるだけでは、なぜ実装を分離しているか判断できません。サービスを登録するときは、型、依存する型、ライフタイムの三つを確認します。画面がサービスを受け取るときは、それを作る責任が画面に残っていないか確認します。結果を表示するときは、計算をどこで実行し、表示の更新がいつ通知されたかを確認します。

たとえば、WinFormsの画面に複数のDapperクエリを書いたまま、画面をRazorへ移すだけでは保守しやすい構成になりません。一覧検索、保存、認可、監査の処理をサービス側へ分けたとしても、依存サービスの寿命や失効への対応を設計しないと、Webで複数利用者が同時に操作するときに不具合が起こります。この段階では小さな時計とカウンターを使い、複雑な業務データを持ち込む前に生成と共有の仕組みを確認します。

### サーバー、circuit、DBの境界

サービスの解決と業務データの保存は独立しています。Interactive Serverでは、接続が再確立して以前と同じcircuitが維持される場合と、新しく作られる場合があります。Scopedの値が残ったかどうかだけでDBの永続性を評価できません。ブラウザーが表示したユーザー名や部署番号も業務認可の正本になりません。今後扱う業務処理では、信頼できる認証機構で本人を確認し、事前整備済みDB台帳または外部ビューの権限を操作ごとに確認します。監査の成功を保証できない更新は拒否します。

### 設計上の判断を文章にする

このサンプルで共有が必要な値は何か、コンポーネント内だけで完結する値は何か、DIへ登録する理由は何かを説明してみてください。インスタンス識別子や固定時計などの教材用データを実業務の利用者情報と混同してはいけません。重要な点は、画面を表示できたという事実から、本人認証・監査・DB保存まで受け入れたと判断しないことです。

## 操作手順と再現条件

1. 初期画面の文字列と数値を記録します。起動直後か同じタブの再訪問かを書き分けます。
2. 「練習用の名前」を実行し、表示が期待通りか確認します。操作で変わるのは何か、変わらないのは何かを説明します。
3. もう一度操作し、結果が同じ場合も失敗と即断せず、今回のサービスやイベントの条件式を調べます。
4. 可能であればプライベートウィンドウを用意して同じURLを開きます。異なる回線の影響を観察します。
5. 結果が想定と異なる場合は次の症状別の表を使います。Visual Studioの例外とサーバーログを優先し、必要ならブラウザーのNetwork/Consoleも調べます。

## 症状別の切り分け

| 症状 | 考えられる原因 | 調べる場所と対処 |
| --- | --- | --- |
| 入力しても表示が変わらない | oninputのイベントやcircuit | 入力イベント・ブラウザー接続を調べる |
| Formatterを解決できない | GreetingServiceかIClockが未登録 | 依存グラフを内側までたどる |
| 名前がDBへ保存されない | 画面に保存処理がない | Formatが文字列を返すだけと確認する |

ブラウザーからクリックしただけでは、サーバーに例外が生じていないことまでは分かりません。サーバーログはC#サービス、ブラウザーConsoleはJavaScript、Networkは接続の観測に使います。未登録の型が原因なら、再読込だけでは直りません。反対に、表示内容が同じという観測だけではDI失敗を意味しません。問題の発生した処理段階を区別するのが切り分けの基本です。

## 演習と詳しい解答

**演習1：Formatterだけ登録したら。**

**解答1：** 内側のGreetingServiceとIClockの登録がなければ解決できません。 説明した結果がどのコード行から生じるか、実装と照合します。

**演習2：DOMを直接操作する必要があるか。**

**解答2：** ありません。Razorがバインディングと再描画を担当します。 説明した結果がどのコード行から生じるか、実装と照合します。

**演習3：全部Singletonでよいか。**

**解答3：** 依存先の寿命や共有状態を考慮せず統一すると利用者間の状態混在の原因になります。 説明した結果がどのコード行から生じるか、実装と照合します。

## さらに確認する課題

次に、サービスの登録だけを変えた場合に、コンポーネントを修正しなくてもどこまで結果を変更できるか考えてください。設定を変更しただけで自動的に既存オブジェクトが入れ替わるとは限らず、利用中のインスタンスの寿命を考える必要があります。画面のコンストラクターと普通のC#クラスのコンストラクターを見比べ、どちらが依存先を決めているか説明してください。実装を大きな階層のプロジェクトへ分ける必要はありません。今はWebプロジェクトと小さなサービスで役割を説明できれば十分です。
