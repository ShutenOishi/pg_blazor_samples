# 実装・日本語表記規約

## 言語と命名

- README、ガイド、Issue本文、PR説明、コメント、XMLドキュメントコメント、画面表示、ログメッセージは**日本語**を原則とする。
- C#の型名・メソッド名、NuGet名、API名、DBテーブル・列名、ファイル名は一般的な英語識別子を使用してよい。
- コメントは「何をしているか」の繰り返しではなく、「なぜそうするか」「どういう制約があるか」を説明する。
- Markdown見出しは日本語、ファイル名は参照・リンクのしやすさを優先して英数字を使用する。
- 説明に必要な専門語は初出で意味を示す。表示は日本語環境のみを前提とし、多言語切り替え機構を教材に持ち込まない。

## 機能実装

- `nullable`を有効にし、警告を放置しない。非同期APIと`CancellationToken`を活用する。
- 画面にSQLを直接書かず、サービス経由でデータへアクセスする。
- 非同期ハンドラーで`async void`を使わない（イベント仕様上必要な場合は理由を記載）。
- 既存機能のコピーペーストで共通コードを増やさない。教材ごとの差分はそのステップの学習目標にする。
- コンポーネント破棄時にイベント購読・JS資源・中断トークンを適切に整理する。
- MudBlazorは公開APIを使用し、内部実装への依存を避ける。
- ADとDBの権限は毎回信頼できるサーバー側の情報で確認し、UI表示の有無に依存しない。
- パフォーマンスを理由にSQL、認証、監査の安全性を削らない。

## ユーザー体験

文字サイズ、十分なコントラスト、フォーカス表示、キーボード操作、読み上げでの意味、入力エラーの対応関係に配慮します。日本語の日付・時刻・数値表示を統一します。危険な操作には確認と失敗時のフィードバックを設けます。

## レビューの観点

1. そのステップの学習目標が1つに絞られているか。
2. 前提条件、操作手順、期待結果が日本語で再現できるか。
3. 関連ステップの実装を壊していないか。
4. 外部データを取得・変更する場合に検証と拒否経路があるか。
5. ビルド・テスト・依存監査の結果がPRで示されているか。

各ステップの完成定義は[サンプル作成テンプレート](sample-specification.md)に記載します。
